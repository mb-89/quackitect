## detail

Two guards decide a holder is gone by counting pulls, and both got the same live worker wrong inside one minute.

In .se/log/session.jsonl, session 20260904-164423: worker-dvorak took wk-37bfa974e3 at 16:58:00 and was still writing to it at 17:05:38, src/mcp/schema_test.go. At 17:04:18 the engine's start sweep put wk-02e2f3ac8f and wk-37bfa974e3 back to the queue as "work held by agents that are gone", and dvorak went on writing to the same token for eighty seconds after being declared gone. Separately, se pull raised an investigate notice on it, because 11 pulls had gone past since dvorak last pulled, past a window of 10.

Neither guard reads liveness. Both read pull count, which is a proxy for a worker that stops between tokens, not for one working inside a single one. A worker on one long token pulls once. dvorak also had no shell: its se run calls at 17:00:39 and 17:01:01 both exited 1 on the WSL stub wk-e51c579664 names, so everything it did went through se apply, which makes no pull. A broken shell reads as death.

The signal is already written. Every call goes in the log with an actor and a timestamp, and limits.heartbeat_seconds says what stale looks like.

The sweep is the worse half, because it acts alone. The notice stops and asks a person to look; the sweep releases the hold, and a released hold is one another worker can take mid-change.

## proposed action

Decide gone on the time since the actor's last call in the session log, and give the sweep and the pull notice one function that answers it.

## done when

- a holder is judged gone by the time since its last call in the log, not by the pulls that went past: se find --regex 'pulls_before_hold_is_stale' shows no use that decides gone on its own
- the sweep that releases work held by agents that are gone and the notice se pull raises read the same signal, through one function
- a test drives an actor that calls without pulling, past the pull window, and the holder is neither released nor called gone; watched red before the change
