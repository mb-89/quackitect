## detail

se --swap builds src/engine and nothing else. buildNext at src/engine/swap.go:77 names that one folder.

.bin holds three programs. util/setup/manifest.json builds se, se-mcp from src/mcp, and logview. The installer makes all three and the swap makes one.

So after a swap .bin is half new. Measured today: .bin/se.exe was written at 13:16:21 and .bin/se-mcp.exe at 10:45:35, with src/mcp changed between them.

The standing check for the lane drives the binary in .bin. It runs green against a program the build door never refreshes, so it can pass on code that is not in the tree. That happened today.

And the swap hides the staleness from the other door. RUNME rebuilds when the command it runs is older than the newest write under src/engine, src/viewer and src/mcp. The swap makes .bin/se.exe the newest thing there is.

So a swap after a change to src/mcp leaves a stale lane that RUNME then reads as current. Nothing rebuilds it, and nothing says so.

## proposed action

buildNext builds every source the manifest names, not src/engine alone.

The handover stays as it is. Only the engine hands over, because only the engine is a running program the swap owns.

- a swap builds the lane too: a test changes src/mcp, swaps, and reads the lane binary newer than the change
- a swap still hands over only the engine: the same test reads the running build and finds it changed once
