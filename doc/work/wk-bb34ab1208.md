## detail

A PRESS ON A ROW TICKS IT. Every column ticks, the first one included: not
being editable is not a reason not to be selectable, and somebody ticking four
rows should not have to aim at the second column.

THE TITLE TEXT IS THE DOOR, and only the text. It underlines under the pointer,
and that underline is the promise: press the underlined words and the note
opens, press anywhere else on the row and the row ticks. Today the whole cell
is a link, so there is no way to tick a row at all.

v3 did this with a double press on the row rather than an underlined word. The
owner asked for the underline, which is the clearer promise, so this is not a
verbatim port of that part.

TICKED ROWS MAKE A GROUP. With rows ticked, one control files them into a
bucket, and a bucket is the person's own name for a group.

A BUCKET DOES NOT MOVE THE WORK. The status stays exactly as it was and only
the grouping changes. That is the whole difference between a bucket and a
state, and it is why the view groups by if(bucket, bucket, status).

THE BUCKET IS MADE FIRST AND NAMED AFTERWARDS. A webview refuses a browser
prompt, so v3's control that asked for a name did nothing at all when pressed.
An empty name asks the engine for a fresh one, because the engine knows what is
already taken and the client would have to guess.

RENAMING NEEDS A BUCKET AND NOT MERELY A SELECTION. A row grouped by its status
has no bucket to rename, and a status is the system's word rather than the
person's.

Ported from v3 engine/workclient.ts, the ticking and the two acts that need a
selection, lines 190 to 345.

## lesson 1 · round 1 · by reviewer

**the class:** Checking a behaviour token with the check that reads the artefact, and proving that check red against a defect in the artefact. The demonstration looks rigorous and is sound on its own terms: the assertion really does go red for the thing it tests. What it never touches is the class the token is about, so the guard and the work are about different things, and every real regression in the handlers lands green. It is easy to fall into when the markup check is the one that already exists and the behaviour check has to be extended.

**instead:** Ask what a defect in this clause would look like, then ask which existing check could see it. If the clause is about what happens when somebody presses something, only a check that presses can see it, and a project that already owns one has no excuse for a markup proxy. When you prove a check red, restore the defect the clause forbids rather than a defect the check is good at: if the defect you can think of restoring is the one the check already catches, you have chosen the check first and the defect afterwards.

## lesson 2 · round 2 · by reviewer4

**the class:** A selector standing in for a set, written from the one place the author had in mind. Both of these are the same mistake pointing opposite ways. '.pane tr.ticked' means 'the rows the person ticked' and reaches only half the places a row is drawn, so half the rows tick and do not count. '.bs-group' means 'the button that files them' and reaches every group in the filter builder as well, so editing a filter files them. In both cases the selector was written while looking at one example of the thing, and in both cases the check that shipped presses that same one example, so the check and the code share the author's blind spot exactly. The row-tick checks added this round are real and I proved both of them red against their own defects; they still pass with both of these on screen, because they press the row the author was thinking of.

**instead:** When code selects a set of elements by a selector, ask two questions of the selector before trusting it, and answer both by counting on the real page rather than by reading. Where else is this thing drawn that the selector will not reach -- a pinned copy, a second pane, a header, a template. And what else on the page answers to this name that is not this thing -- grep the class across the file and count how many of the hits mean the thing you meant. A class name that is both a look and a handle for a delegated listener is the shape that goes wrong, because a stylesheet is happy to share a name and closest() is not. Then choose the fixture deliberately: a check that reaches for the first element it finds is testing whatever the data happens to put first, so name the case -- a row in the pinned box AND a row in the scrolling box, the button AND a look-alike -- and assert the negative as a rule ('nothing but the button sends this') rather than as a list of the controls that exist today.

## lesson 3 · round 3 · by reviewer4

**the class:** A finding answered by fixing the other one. The round closed finding 1 cleanly, proved it red, and wrote a real check for it, and finding 2 is not fixed, not attempted and not mentioned -- not declined with a reason, which would have been a legal answer, simply absent. A submission that answers some of the findings reads exactly like one that answers all of them, because the evidence names what it did and nothing names what it did not, so the gap is invisible until somebody re-runs the reproduction. And the fix that did land widened the reach of the defect that did not.

**instead:** Answer every finding by name in the evidence, including the ones you are not fixing. Write one section per finding, headed with its number, and let its body be closed with what proves it, or not taken with why and what owes it. A finding with no section is the failure mode, and it costs a whole round to discover. Before submitting, list the findings from the last round, tick each against a section, and re-run the reviewer's own reproduction where it named one, because the reviewer will. And when two findings touch the same code, check whether fixing one widens the other: here, making more rows count made the accidental control file more of them.
