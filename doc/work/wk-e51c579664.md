## detail

batteryShell in src/engine/tests.go asks exec.LookPath for sh, then for bash. It does that before it looks beside the git the probe found. On Windows without a POSIX sh on PATH, LookPath("bash") answers a launcher. That launcher starts a WSL distribution rather than running a command. Where WSL is not installed it exits 1 before the command runs. It prints WSL_E_WSL_OPTIONAL_COMPONENT_REQUIRED in UTF-16, which no caller reads as a missing shell. So every se_run on this machine fails, and shellsBesideGit never runs although Git\bin\sh.exe is there.

TWO FOLDERS HOLD SUCH A LAUNCHER, and this was first written naming only one. system32 holds bash.exe. WindowsApps holds the app execution aliases. A probe of this machine said that is the one LookPath answers: C:\Users\mb\AppData\Local\Microsoft\WindowsApps\bash.exe. A guard naming system32 alone was green in its table and left the box as broken as before.

## proposed action

Reject a PATH hit that is a Windows launcher. Skip a resolved path whose directory is system32, sysnative or WindowsApps, so the walk falls through to shellsBesideGit. No POSIX shell is installed in those folders, so the folder tells a launcher from a shell. Keep the order otherwise, a real sh on PATH still wins.

## done when

- batteryShell answers the Git shell where the only bash is a launcher. A table test drives it past a stub bash in system32, in sysnative and in WindowsApps
- se_run answers exit 0 and the word hello for the command echo "$(echo hello)", run from the root. The substitution is what says a POSIX shell ran it, and cmd did not
- the places it looked, returned beside the name, carry a row naming the launcher it skipped. A reader then sees why it was passed over
