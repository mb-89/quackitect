## detail

A client reads the lane's tool list once and never asks again, so a swapped engine answers the old shape.

MCP has the signal for this. A server declares tools.listChanged in its capabilities and then sends notifications/tools/list_changed when the list changes. A client that saw the capability re-fetches.

Ours declares neither. src/mcp/main.go line 96 answers capabilities as tools with an empty object, and nothing in src/mcp sends a notification of any kind: that line is the only hit in the package for capabilities, listChanged or notifications.

Measured in September 2026. The engine gained a required approach on a standard token. The lane's own source already carried the field and passed it, and the client in front of it kept refusing the argument, because the schema it read at session start was older than the engine behind it. A session spent that on minting through the shell instead, and on a token blaming the lane for a door that was open.

A cloud box that pulls and swaps meets the same thing, and has no person to notice it.

## proposed action

Declare the capability and send the notification.

1. capabilities tools gains listChanged true, in src/mcp/main.go.
2. The lane sends notifications/tools/list_changed when the engine under it changes. The swap already knows it happened.
3. Measure whether the client in front of us honours it. The protocol says a client MAY re-fetch rather than must, so a signal nobody reads is the same stale list with more code.

If it is not honoured, say so on the token and leave the capability declared: it is correct whether or not this client acts on it.

## the three done-when lines, answered

**1. The lane declares tools.listChanged.** Yes. src/mcp/main.go answers
capabilities as tools with listChanged true, where it answered an empty object.

**2. A rebuild sends notifications/tools/list_changed.** Yes, and from the
supervisor rather than from src/mcp. The criterion named the wrong file, and this
is why.

tools() is compiled into the lane binary, so the one program that must announce a
new list is the one program that cannot serve it. A lane cannot notify about its
own replacement: by the time there is something new to say, the process saying it
is the old one. Refreshing the tools is therefore restarting the lane, and
restarting it without losing the session means holding the handshake outside the
lane and replaying it.

That place already existed. util/cage/mcp-lane.mjs held the handshake on a cold
clone to buy the build its thirty seconds, and already sent this exact
notification when it handed over. IT ONLY DID SO ON A COLD CLONE: a built tree
went through handOver, which inherited stdio and stepped out of the message path.
So the box that could not be repaired was the ordinary one, which is the box the
detail is about. There is one path through that script now, and it serves both.

The supervisor watches the program its lane is running. When a build replaces it,
it puts the lane down, brings it back on the new binary, replays the handshake out
of what the harness asked for, hands over anything held meanwhile, and sends the
notification. It waits for a lull of 1500ms with no message either way, so a
restart lands between calls rather than through one, and it waits for the file's
size and time to stop changing, so a half-written program is never started.

TestANewLaneOnDiskRefreshesTheToolList drives that: a built tree, a handshake, a
list, then the lane on disk replaced by a program listing one tool nothing else
lists. It holds that the notification arrives, and that the list which comes back
is the new program's. The second half is the point. A signal with no new list
behind it is the same stale list with more code in front of it.

**3. Whether this client re-fetches: NOT MEASURED.** This session's lane was
started by the old script, which handed stdio over and is no longer in the message
path, so nothing here can send the notification to the client in front of it. The
first session that can is one started after this lands. The named command decides
nothing either: an engine swap leaves the lane's list untouched, because the list
is compiled into the lane and never read from the engine.

What is known without measuring: the protocol says a client MAY re-fetch, not
must. And this tree hedged against that once already. The cold door answers
tools/list off util/cage/tools.json rather than waiting for the lane and
notifying, and the comment there says why: a list held for a build is a session
that begins with no tool listed. So the notification was already not trusted on
its own, by whoever wrote that.

The capability is correct whether or not this client acts on it, and stays
declared. The restart earns its place either way: the new lane is what answers the
next tools/list, so a client that re-fetches for any reason gets the new list, and
one that never re-fetches is no worse off than before.

## what this widens, said out loud

Every session now passes its messages through node, where a built tree used to
hand stdio straight to the lane. That is a real widening of what a fault in this
script can take down, and it is the reason the change is held by five checks
rather than one.

Two things bound it. The code is not new: the cold path has run exactly this
piping on cloud boxes already. And a failure is loud rather than quiet, because a
session with no lane says so in .se/lane.out and in every refusal.

Back-pressure is not handled, in that a write which fills a pipe buffer is not
waited on. That was already true of the cold path and is now true of every
session. It is not a failure anyone has seen, so it is written down rather than
built against.

On Windows the watcher rarely fires, because a running program cannot be
overwritten there: the build that would move the file fails against the lock
instead. That is the desk, where a person can reload the window. The box this is
for is Linux.
