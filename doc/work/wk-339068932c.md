## detail

One command collects everything a retro needs and drains it into one folder.

THE OWNER'S WORDS: a mechanical command that collects everything a retro needs
to know about what happened since the last retro. Look at v3, how retros work
there.

WHAT IT COLLECTS: the log since the last retro, the harness transcripts, and
the scratchpad with every script written in it.

IT DRAINS. The owner wants the collected things gone from where they were, so
the next retro starts empty and nothing is counted twice.

THE FOLDER IS MADE MECHANICALLY, and a person opens it and reads. What a retro
then does with the backlog is theirs.

CLAUDE FIRST AND COPILOT AS FAR AS IT GOES. The transcripts are the harness's
and each harness keeps them its own way.

WHAT V3 DID, READ RATHER THAN REMEMBERED. Its retro prompt says to start from
the engine call log, aggregate it, and then DELETE it, because retention is
retro-bound. Then read the session logs and ask which scripts the agent wrote
that a tool could own. So draining is v3's rule too, and the scripts are one of
the things a retro is for.

THE ORDER THE OWNER SETTLED: rotate the log first, so the session that is
running becomes an old file, then drain every old file. The retro then sees
everything up to the moment it ran and nothing is counted twice.


WHAT IS DRAINED AND WHAT IS COPIED, decided here because round one did not.

THE LOG AND THE SCRATCHPAD ARE DRAINED. They are inside the folder being worked
on, they are this machine's rather than the project's, and the owner asked for
them gone so the next retro starts empty.

THE HARNESS TRANSCRIPTS ARE COPIED. They are not in this tree: the one in use
is under the harness's own folder and it is being appended to while the command
runs. Deleting another program's file is not this verb's to do, and a retro
that truncates a running transcript takes the session down with it.

THE CHECKS MOVE OUT OF THE SCRATCHPAD FIRST, and that is part of this work
rather than a caveat on it. Fifteen scripts sit there and eleven of them are
what the battery runs, and seventeen tokens name the battery as their evidence.
A command whose whole job is to empty that folder cannot also be trusted to
leave them, and every criterion phrased as the source is empty is satisfied best
by deleting more.

So the ones that have earned it go to util/checks, which is the method's, and
the scratchpad keeps what it is for: working files. The guidance already says
this is how it goes, that the ones that earn it become part of the method. This
is the day they earned it.

WHAT MUST STILL BE THERE WHEN THE RETRO HAS FINISHED is therefore a criterion of
its own, because every other criterion pushes the other way.

WORK IN FLIGHT, AND THIS IS THE THIRD THING ROUND TWO ASKED FOR. Several actors
run in this tree at once and each keeps its files directly under the scratchpad,
in a folder named for itself. A sweep is the one operation with no undo, so a
retro that runs while a reviewer is mid-review deletes what that reviewer is
reading.

THE RETRO REFUSES WHILE SOMEBODY ELSE IS WORKING, and it names who. A skip list
would be the other answer and it is the worse one: it leaves the retro half
done, so the next retro takes what this one skipped and the drain stops meaning
anything. A retro is a cycle boundary. Nothing else running is what a boundary
is.

THE ENGINE ALREADY KNOWS WHO IS WORKING. A token in work or in review names its
holder, and StillPulling in src/engine/arrival.go says whether that holder is
still pulling. The refusal reads the tokens rather than a new file.

THE PRECONDITION IS ITS OWN TOKEN, wk-964cd3a1d4, checks leave the scratchpad.
Until the standing checks live in util/checks, a sweep of the scratchpad takes
battery.sh and run-criteria.py with them, and this token's criteria 10 and 11
cannot go green. It is a sub-token of this one and it goes first.
