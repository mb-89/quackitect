## detail

A person on a cloud box can move every control from a chat and cannot write anything down.

KEYWORD:NAME=VALUE reaches eighteen controls. The panel's mint box is not among them, because a control that carries a message is one thing and a control that mints a token is another. The mint box takes a title and a detail, and the schema wants more than either: a process, whether it travels, and a done-when line before it is accepted.

So the owner sees something worth a token on a box they are not sitting at, and the only thing they can do is remember it. What is not written down at the moment it is seen is a thing nobody works.

The line the owner asked for is KEYWORD:MINT=four words / everything the next hand needs, which is the same shape the panel's box already takes. What the token looks like on the other side is the open question. A token with no criteria is refused, and one minted with criteria nobody wrote is a token that lies about being ready.

## proposed action

Read the panel's mint box first. It already turns a title and a slash and a detail into a token, so the shape exists and this is a second adapter onto it rather than a second mint.

1. KEYWORD:MINT=title / detail goes through whatever the mint box goes through. One door.
2. Decide what a chat-minted token is. A note is private and takes no criteria, which fits a thing seen and written down. A tracked token wants criteria nobody typed.
3. Whatever it mints, the answer says the id, so the person knows what to claim.

The keyword transport is done and this is the one control left off it.

## approach

The open question is what a chat-minted token is, and this answers it: a note.

A note is private and takes no criteria, which is the shape of a thing seen and written down. A tracked token wants criteria, and criteria nobody typed would be a token lying about being ready. So the person promotes it later, at a desk, where the done-when can be written.

One door. KEYWORD:MINT=title / detail calls the same function the panel's mint box calls. The keyword handler shapes the message into the arguments that door already takes, and decides nothing else.

The answer carries the id into the record, because a person who cannot see the folder needs it to claim what they just wrote.

Refusals are the handler's, before the door: no slash, or a title over four words. Each is refused with its reason in the record rather than dropped.

## done when

- KEYWORD:MINT=four words / a detail mints a token and the record names its id, decided by: a Go test in src/engine driving KeywordSaid with that message and reading the record
- the chat and the panel mint through one function, decided by: se find --regex for the mint call, which answers one caller in the engine
- a message with no slash, or with a title over four words, is refused with a reason in the record, decided by: the same Go test
- the mint control draws its line in the panel, decided by: the check tooltips-name-their-keywords, which already reads every reachable node
