## detail

A standard token whose step 3 verdict is written and committed but never submitted sits at the head of the reviewer queue forever, and a put-down hands it straight back. The reviewer lane cannot get past it.

Measured on 2026-09-05 as reviewer-schnittke. se pull with role reviewer answered wk-6b12a25abb "urgent goes out first" three times running. Its step 3 checklist is answered on all five rows, its finding wk-ef7d0af942 exists, and the verdict is in git as 9fb3836b "The verdict on the urgent flag, and the one finding". Only the submission is missing, so the engine still counts the verdict step as owed. Between each pull, ./RUNME.sh work --put-down wk-6b12a25abb --by reviewer-schnittke exited 0 and cleared the holder, and the very next pull returned the same token. Each round only appends another pair of snapshots to began and ended.

It is not one token. doc/work holds five standard tokens at status done whose step 3 is fully answered and unsubmitted: wk-30821724fc, wk-5e2c601cce, wk-6b12a25abb, wk-6d74c93848, wk-97a144fdc6. reviewer-berg recorded the same loop on wk-30821724fc in its stop reason, and reviewer-ligeti's stop reason says its verdict on wk-30821724fc was written and pushed. So at least two reviewers have already burned a whole session on this, and every later reviewer meets it first.

The cost is that a reviewer told to stay off a subject can never reach the tokens it may judge, because the queue never advances past a head it cannot close.

## proposed action

Either the queue skips a token whose verdict step is already answered, or a verdict written into the note counts as given so the token closes without a second submission. Whichever is chosen, a put-down of a token a pull cannot advance past must not return that same token to the same actor.

## done when

- a reviewer pull, given a done token whose step 3 checklist is fully answered, answers another token or wait, proved by a Go test in src/engine that fills step 3 without submitting and then pulls with role reviewer
- the five tokens named in the detail are off the head of the reviewer queue, decided by se pull --role reviewer answering none of them
- a put-down followed by a pull never returns the same token to the same actor twice running, proved by a Go test in src/engine
