## detail

The states a work token can be in, named and enforced in one place.

THE OWNER'S WORDS, and the list is theirs. Backlogged. Then the spec half: spec
open, spec in work, spec submitted, spec in review. THERE IS NO SPEC DONE,
because a spec that is agreed IS implementation open. Then the implementation
half: imp open, imp in work, imp submitted, imp in review, imp done.

ELEVEN STATES, NOT TEN. The owner named the ten a token passes through. The
eleventh is aborted, and it is the engine's rather than the owner's: the owner
named where work goes, and this is where a dropped token stops. Whatever the
engine's list holds is what the abort walks, what the view draws and what a
check searches for, so the number is written here rather than counted twice.

TWO HALVES, ONE SHAPE. Each half runs open, in work, submitted, in review. The
same four verbs twice, so a person who has learned one half has learned the
other, and the engine can carry one set of rules rather than two.

WHAT THE ENGINE HAS TODAY is nearly this and spelled differently: backlogged,
spec, spec_in_review, open, in_work, submitted, in_review, closed. Two of the
owner's states have no name at all. There is no spec in work, so a draft being
written and a draft nobody has touched are the same state. And there is no spec
submitted, so a draft goes from the drafter's hands into a reviewer's with no
state in between, which is the state a queue is counted in.

AN ABORT COMES OFF ANY STATE, WITH A REASON. Deferred, obsolete, a duplicate of
another token. That is what closing does today and it stays available from
everywhere, spec half included. A reason is not optional: an aborted token with
no reason is a token somebody re-mints six weeks later.

WHY THIS IS WORTH THE RENAME. A state is what the whole system counts, queues,
refuses and draws. Today the same word means different things in the two halves
and two of the halves' states are missing, so the queue cannot say how much
specifying is waiting.

THE PROCESS ITSELF IS NOT DECIDED HERE. The owner has said a process comes and
that submitted specs count into a reviewer's workload. This token names the
states and makes the engine hold them. What flows between them is drawn in the
SIPOC token.

A STATE AND A DISPOSITION ARE TWO FIELDS AND THEY STAY TWO. The engine already
has three exits and no fourth, on the disposition: done, became and dropped.
A token that closes without saying what became of it is how work disappears.
The state says which half of the machine a token ended in. The disposition says
what became of it. Neither replaces the other.

    disposition   state it ends in   what happens to the disposition
    done          imp_done           stays as it is
    became        imp_done           stays, with its successors
    dropped       aborted            stays, and its reason is the abort's

WHAT AN ABORT IS. One ending, and it carries why, which is what dropped already
refuses to be without. So aborted is the state a dropped token ends in rather
than a fourth exit. Deferring is not an ending at all: a deferred token goes
back to backlogged, where it is visible and nobody is doing it, which is what
backlogged already means.

WHAT THE CHECK OVER THE TREE COVERS, COUNTED. The .base filter shape finds
eight lines, all in util/views/work.base. A status: line in frontmatter finds
nothing once doc/work and .se/work are excluded, because those two directories
are the only places frontmatter carries one, so that shape is not a shape. A
status in util/*.json finds nothing either, and worse than nothing: the icon
table declares an icon whose key is open and the parameter tree has a node
typed status, and neither is a status.

THE ICON NAMED open IS A NAME AND NOT A STATUS. src/extension/editor.ts
calls icon("open") and icon("shut") for a group that is open or shut on the
page, so the name is load-bearing in the icon table and it stays whatever the
engine calls its states.

THE DESIGN DOCUMENTS ARE LEFT ALONE, and that is a ruling rather than an
oversight. doc/levels and doc/use-cases describe the engine in ordinary
English: open and closed are words about work there, not statuses, and a search
over the words would be red forever because those sentences are correct English
whatever the engine calls its states. They carry no machine status: the only
one anywhere in doc is spec_in_review in a sentence in specifying.md, and the
rename keeps that name.

WHAT HAPPENS TO THE TOKENS THAT EXIST. They are read under the new names, and
that is why the check above excludes them. About fifty notes in this tree spell
an old status in their frontmatter today, and on the day this work is finished
they still will, because nothing rewrites them. A note saying status: open
reads back as imp_open, which the migration criterion asks for, and that is what
makes the exclusion safe rather than a hole.
spec becomes spec_open, open becomes imp_open, in_work becomes imp_in_work,
submitted becomes imp_submitted, in_review becomes imp_in_review, and closed
becomes imp_done or aborted according to the table above. spec_in_review keeps
its name. No token is rewritten by hand, and nothing sorts on a fact this
engine does not record: there is no duplicate disposition and there never was,
so a settled duplicate is a dropped token with that reason.

## lesson 1 · round 1 · by reviewer3

**the class:** A rename whose criteria only look for the new name. Every command asks has the new word arrived and none asks has the old word gone, so a rename that is one third done is green everywhere. It is a comfortable shape to write because the new names are what the author has in mind, and the arrival of a new name is easy to grep for; the trouble is that arrival is the half that happens by itself, in the file the author was already editing, while departure is the half that gets missed in the files they were not. The same blind spot covers the vocabulary the rename lands beside: a new set of names is checked against itself and never against the names already there, so two words for one fact survive in different fields and nothing notices.

**instead:** For a rename, write the criteria against the old names first, as searches that must come back empty, and only then add the ones for the new. That is the pair a rename actually needs, and the empty-search half is red today for the right reason, which the arrival half never is. Search the whole tree for the old names before writing any of them, so the criteria are scoped to what is really there rather than to the files you happened to edit, and rule explicitly on anything you are leaving behind rather than leaving it unmentioned. And before adding a vocabulary, grep for the fact it names to see what already carries it, because a system that already records the same thing under another word will now record it twice and disagree with itself.

## lesson 2 · round 2 · by reviewer3

**the class:** A criterion written as a closed universal with its exemptions left outside it. No file in this tree spells a status the engine does not know, the ten states and no others: both read as strong and complete, and both are only true with a carve-out that lives somewhere else in the spec, or nowhere. A criterion is read literally, because that is what makes it a criterion rather than an intention, and a literal universal either forbids something the same document requires or hands the worker the job of inventing the exception. The shape hides because the exemption is obvious to whoever wrote it - of course the old notes keep their words, of course aborted is a state - and obvious is exactly what does not survive being written down somewhere else.

**instead:** When a criterion says no, none, every or a count, write the exception into the same sentence, and get the count by listing the members rather than by remembering the number. Then read the criteria against each other before the detail: a rename spec states its vocabulary at least twice, once as the list and once as the rule that nothing outside it survives, and the cheapest defect to find is the two disagreeing. And check the criterion against the finished state, not only the starting one: run it in your head on the day the work is done and ask whether it is green, because a criterion that cannot go green is as useless as one that cannot go red and much more expensive, since nobody discovers it until the work is finished.

## lesson 3 · round 3 · by reviewer3

**the class:** Widening a criterion's scope without widening what it looks for. The scope was too narrow, so more files went in, and the thing being matched stayed a vague verb - spells a status - that was only ever precise for the file it started in. In a config file a status is a literal the machine compares; in prose it is a word people use for work. The same sentence now covers both, and the two readings it allows point opposite ways: one can never go green because ordinary English is full of the words, the other covers nothing because prose contains no literals. Neither is visible from the criterion, and both are cheap to see from the files.

**instead:** When you add files to a criterion's scope, open one of the new files and run the check in your head against a real line of it. If the answer changes depending on what spells means, the verb is doing work the criterion has not paid for, and the fix is to write the form being matched - the operator, the key, the frontmatter line - rather than the concept. And when a reviewer's finding asks for wider coverage, check whether the wider place contains the thing at all before extending the same command over it; coverage of a directory with nothing to find reads as thoroughness in the criteria and is a sweep nobody performed.

## lesson 4 · round 4 · by reviewer

**the class:** A criterion whose scope is written from the definition outward instead of from the data inward. The words are precise and the shapes are carefully enumerated, and nobody opened the files to see what each shape would actually match. Three ways it goes wrong and all three are here: a shape with no true matches, which reads as thoroughness and is a sweep nobody performs; a shape whose only matches are false ones, which will be red for the wrong reason and then quietly narrowed; and a case scoped to real data that the real data contains no example of, which is green by absence. None of the three is visible from the criterion, and all three are one count away from being visible.

**instead:** Before fixing a criterion's scope, count what each clause of it matches today and write the numbers down beside it. Zero is a signal and not a pass: a clause matching nothing is either aimed at the wrong place or is describing something that cannot occur, and a clause matching only things that are not the subject will be resolved by narrowing it after the work, where nobody reviews it. Do the same for the cases a criterion is meant to distinguish, and where the data holds no example of the one that matters, build the example inside the check rather than scoping the check to the data. A criterion is a claim about what will be found; counting is how you tell whether anything is there to find.

## lesson 5 · round 5 · by reviewer5

**the class:** A check whose ability to fail depends on data that the ordinary running of the system consumes. It is watched failing, the evidence is filed and is true at the time, and then normal use eats the data it stood on. It keeps passing, reports nothing, and nobody is told it has stopped being able to fail -- which is worse than never having written it, because the record says this was proved. A migration check is the sharpest case: it is fed by exactly the old records the migration exists to eliminate, so it is strongest on the day it is least needed and dead on the day the last old record is converted. Here the guard on the alias map went quiet for in_work the moment the token carrying that spelling was submitted -- the token being reviewed was its own last data point -- and went quiet for submitted during the review itself, when pulling another token rewrote the last note that spelled it.

**instead:** Ask of every check what would have to be in the tree for it to go red, then ask whether the system removes that thing in the course of working. If it does, the check has a half-life and cannot be the guarantee. Keep the sweep over live data for what it is good at -- catching shapes nobody enumerated -- but put the guarantee in a fixture you control, and enumerate it from the code rather than from the tree: iterate the keys of the map, the members of the list, the cases of the enum, and build one case per entry, so coverage is a function of the thing being guarded and a new entry adds a case instead of a hole. Where a sweep over live data is kept, make an empty population a loud failure rather than a pass. And before filing a run as evidence, ask whether a reviewer can reproduce it tomorrow; if reproducing it needs the tree to be in the state it was in that afternoon, it is a screenshot rather than a check, and it should be labelled as one.
