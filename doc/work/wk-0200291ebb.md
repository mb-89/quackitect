## detail

land.sh now asks the proxy where it is before pushing, on wk-aa9c98250a. The engine's own claim relay does not, so it still pushes through whatever HTTPS_PROXY names.

MEASURED, 2026-09-07, on the pull that handed out wk-aa9c98250a. The notice read that the token is claimed here and published here, and then: the push did not run, fatal, unable to access, Failed to connect to 127.0.0.1 port 43603. The land through the fixed script on the same box, minutes later, corrected the port and pushed.

This is the failure the claim relay exists to prevent. A box takes a claim, believes it published, and no other box sees it. Two boxes can then hold one token and neither knows. That is written in the header of util/checks/pushes-name-a-branch as the reason the check exists.

The fix is the same shape as the one in land.sh, and the two must not each carry their own copy of it.

## proposed action

Give the port lookup one home and have both doors read it. land.sh holds it in shell and the engine needs it in Go, so what is shared is the rule rather than the code. Ask the status endpoint whether the named port answers, and where it does not, take the port the proxy's own README names. Write it once in Go, have the claim push use it, and say in land.sh where the other half lives.

## done when

- a claim push over a tree whose HTTPS_PROXY names a dead port reaches a fed remote, and a Go test drives it
- a claim push leaves a live HTTPS_PROXY alone, proved by the same test over both
- the pull notice names the corrected port where it corrected one, rather than reporting a connect failure
