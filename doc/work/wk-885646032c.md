## detail

The removal guard added on wk-2ef79848eb reads a command for a remover run as a program: rm(1), rmdir, unlink, shred, del, erase, rd, remove-item. git is not one of them, so git clean walks past both halves of it.

FOUND BY USING IT. Minutes after writing the guard I had left src/engine/engine.exe in the source folder, which the binaries-live-in-bin check fails on. A plain removal would have been refused, correctly, because nothing had read a 13MB binary. git clean -fx src/engine/engine.exe took it away with nothing said. The right answer was reached through the one door the guard does not watch.

git clean is the larger deletion, not the smaller one. With -fdx and no pathspec it removes every untracked and ignored file under the tree, which is the shape wk-2ef79848eb is about: a command that deletes what its own scan names, with none of the files in the command for anybody to check.

IT IS NOT THE SAME RULE, WHICH IS WHY IT IS A TOKEN AND NOT A WORD ADDED TO A LIST. A removal names its files, so the read set answers it. git clean names a pathspec, and with none it names everything, so what it will take is not in the command at all. That is the loop half's question rather than the read half's.

## proposed action

Read git clean as a removal. With a pathspec, put its paths through the read rule. With no pathspec, or with -d, refuse it the way a loop is refused, because what it takes is not in the command. Its cases belong beside TestARemovalNeedsARead and TestALoopThatDeletesIsRefused in src/engine/removal_test.go.

## done when

- git clean naming a path inside the tree that the turn has not read is refused naming that path, and git clean with no pathspec is refused outright: go test -C src/engine -run TestGitCleanIsARemoval
