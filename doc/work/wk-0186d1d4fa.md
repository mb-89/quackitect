## detail

FindRoots takes the work root as an argument and works the method root out on its own:

    method := filepath.Dir(filepath.Dir(exe))

So the method root is whatever sits two levels above the running program. That is a fact about where the installer puts the binary, not a fact about the tree, and nothing can override it. The flag form carries --method. The nine verbs do not, so they take the guess.

WHAT IT COSTS. Run the engine from anywhere but <method>/.bin and every path it derives is wrong, quietly. Measured: a build placed in .se/scratchpad gave

    util/parameters.json  the declaration  cannot be read, so nothing about it was
    checked: open <work>/.se/util/parameters.json: no such file or directory

The finding names util/parameters.json. The file is fine. The root was wrong, and the check reported against an innocent subject, which is worse than staying quiet: a reader takes it as a fact about that file.

IT HAS ALREADY HAPPENED HERE. .se/.se/scratchpad exists in this tree, dated 31 August. That is the shape a mis-resolved root leaves behind.

WHAT TO DO.

Name the roots. --work and --method on every verb, through the same door the other flags come through, and both defaulting to exactly what they do now. Nothing changes for anybody who does not pass them.

Then find the method root from the root rather than from the binary. Walk up from the program to the folder that carries the marker of a method root, the way projectRoot already walks up to the nearest .se. Counting two directories assumes the binary is in .bin. Walking up asks the tree.

And when the method root cannot be found, say so and stop. Do not carry on and file findings against whatever was missing as a result.

Raised from outside the working session.
