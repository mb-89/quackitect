## detail

A PINNED GROUP IS A GROUP. It draws like every other one, with the same
columns, the same heading and the same fold. The one difference is a pin icon
in its heading.

Every group carries that pin, and clicking it pins or unpins that group. So a
person who wants the backlog at the top pins the backlog.

A FUNCTIONAL GROUP NEVER GOES AWAY, even with nothing in it. Functional means
the system decided it exists: yours, here, and every value the status field can
hold. Only a group somebody invented disappears when it empties, because
nothing lists what those could be.

So a view declares its functional groups, and the pin list only says which of
them sit at the top:

    groups:
      - name: yours
        filter: assignee == "human" && (status == "open" || status == "in_work")
      - name: here
        filter: status == "open" || status == "in_work"
    pinned:
      - yours
      - here

UNPINNING LEAVES THE GROUP WHERE THE GROUPING PUTS IT. Today a pin is the only
thing drawing yours and here, so unpinning one deleted it and its rows had
nowhere to go. Moving the declaration out of the pin list is what fixes that.

YOURS and HERE are pinned by default, and they are the only two that start
that way.

WHAT HERE MEANS: everything that is open or in work. There are no states above
the token yet, so here is everywhere.

The drawing this replaces had YOURS and HERE as a separate kind of thing above
a header row, with no columns of their own.

## evidence: the fix

THE FILE'S ORDER DECIDES WHO TAKES A ROW, AND A PIN DOES NOT. A pin moves a group to the top of the drawing and nowhere else. The owner wrote the declaration order, and a person clicking a pin is not rewriting it. So the partition runs once over v.Groups in declaration order; a pinned one is held aside and drawn at the top afterwards, in the order it was pinned. Ad-hoc pins on groups the data made take what is left, after the declared ones.

**satisfies:** Drop the `key != ""` guard at view.go:553 and let an empty key pin like any other -- `level.Text + " == " + strconv.Quote(key)` already produces `holder == ""`, which the engine parses and which I confirmed keeps the right 8 rows. ## finding 6 · round 4 · Only a group somebody invented disappears when it empties, because nothing lists what those could be. · by reviewer

**wrong:** A PIN AND AN UNPIN PERMANENTLY DECLARES A GROUP NOBODY DECLARED, so an invented group stops disappearing when it empties. That is the one line the token draws, and this crosses it.

**satisfies:** AN UNPIN MUST LEAVE THE FILE AS IT FOUND IT WHEN THE PIN CREATED THE DECLARATION. Remove a declaration that AddPin minted; keep one the owner wrote. The simplest rule that needs no new bookkeeping: on unpin, drop the declaration if the grouping would still produce that group on its own, and keep it if it would not -- a functional group like yours or here has no value in the grouping to fall back on, so it stays, while backlogged on the right pane comes back from the bucket and does not need declaring. If you would rather be explicit, mark the declarations a pin minted in the file and have DropPinNamed remove only those.
