## detail

The adapter still decides two things about a column that the engine owns.

WHICH CELL MAY BE EDITED. src/extension/editor.ts, function locked(), lines 504 to 519, holds 8 property names and the engine's reason for refusing an edit on each: id, seq and type say "the engine decides this", status and holder say "a pull moves this", subs, depends_on and successors say "a list is edited in the note". Everything else about a column already comes from the engine. The pane answer carries columns, heads, widths and opens, and editor.ts draws all four from it: `t.widths?.[c]`, `t.heads?.[c]`, `t.opens?.[c]`.

READ THE PARENT'S SECOND CRITERION THIS WAY, and disagree here if you read it otherwise. util/checks/panel-draws-the-register.mjs rules that the DECLARATION chooses the sidebar table's columns: "a widget with the columns written into it is a second place the panel is decided, and util/parameters.json would no longer say what the panel shows." That ruling stands, so the sidebar's columns and titles stay in util/parameters.json and are not moved to an engine answer. What is left is the two decisions above, which the declaration does not make either.
