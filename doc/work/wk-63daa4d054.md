## detail

CLASS: A SNAPSHOT TAKEN AFTER THE WORK HAS ALREADY DRAINED PART OF THE SET IT
FREEZES, SO THE ITEMS THE WORK ACTED ON FIRST ARE THE ONES ITS OWN CHECK CANNOT
SEE.

The method already says to pin a one-time assertion to what existed when the
work started, by id or by a snapshot inside the token: doc/guidance/specifying.md,
A ONE-TIME ASSERTION WRITTEN AS A STANDING RULE. What it does not say is WHEN
the pin is taken. A worker opens the token, does the two or three easiest items
because they are obvious, and only then writes the list down. The list is now
the set MINUS the work already done, and it reads exactly like the set, because
the sentence above it says "as it stood when this started". Every criterion is
then written over the survivors, the finished items are outside the frame, and
the token closes with a record that shows fewer verdicts than it owed. Nothing
notices, because the check compares the detail against the list and the list is
internally consistent.

FOUND ON wk-2b78b911b1, drain the backlog, second pass. Derived rather than
retyped: at 6418d6a4, the commit that carries the token as spec_in_work with no
list, 15 notes in doc/work and 2 in .se/work say status: backlogged, so 17.
Eight minutes later commit ab4deed3 aborted four of them from backlogged --
wk-735138cd83, wk-84a8b68af9, wk-ce5d6865e4, wk-dbfb8efd7a -- as part of this
token's own work. The snapshot was written into the note after that and names
13. The four are not on it, all four are outside wk-61af3a054e's first-pass 22,
and so they are exactly the population the second pass exists to read.

WHY IT IS HARD TO SEE. A count that is derived is trusted, and this one was:
13 is the correct size of the live backlog at the moment it was counted. The
error is not in the counting, it is in the clock. Deriving the number harder
does not find it. Only asking WHEN against WHAT does.

WHAT TO DO INSTEAD. Take the pin from the state the work started in, not from
the state the work is in when you get round to writing it, and derive it from
something with a timestamp rather than from the working tree: the commit the
token was opened at, or the ids the engine reported the first time you asked.
Where items have already been settled before the pin was written, put them on
the list with their verdicts and say which they are, rather than letting the
pin close over them. And say in the detail which state the pin was taken from,
by sha or by the command and its answer, so a reviewer can re-derive it.

THE CHECK, RED TODAY: name the base commit in the detail and have the check
enumerate every note that said status: backlogged at that commit, across
doc/work and .se/work, and require each one to be on the snapshot. Against
wk-2b78b911b1 as it stands that is red and names four: wk-735138cd83,
wk-84a8b68af9, wk-ce5d6865e4, wk-dbfb8efd7a. Written as a comparison against
the live backlog instead it would be green today and red forever afterwards,
which is the shape doc/guidance/specifying.md already forbids.
