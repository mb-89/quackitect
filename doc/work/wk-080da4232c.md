## lesson 1 · round 1 · by reviewer4

**the class:** A field carried across a rewrite that was a fact about the value being replaced. The rewrite was written by asking, of each field on the record, whether it is about the position or about the thing -- and sets is about the thing, so it was kept. But 'about the thing' is exactly why it must go when the thing changes: a fact about the old property is a lie about the new one. The check written for the decision exercised the other branch of the same function, the append, where the question does not arise, so the branch the decision lives in shipped with no check on it at all and the reasoning was never tested against its own hardest case.

**instead:** When a write replaces one field of a record and preserves the others, sort the survivors by what each one depends on, not by whether it feels incidental. Anything whose meaning is derived from the field being replaced dies with it; only what is independent of that field survives. Write the dependency down beside the assignment in the code -- this is a fact about the property, so it goes when the property goes -- because the next reader sees a struct literal and cannot tell which fields were considered. And when a function has an append branch and a rewrite branch, a check that lands in one says nothing about the other: pick the arguments deliberately so the check reaches the branch the decision is in, and assert that it did, because a position past the end silently turns a rewrite into an append.

## lesson 2 · round 2 · by reviewer4

**the class:** A class that is a look, reused as the handle a wiring loop matches on. bs-add says how a button is spaced; it was then used to mean 'is a level-add button', and querySelectorAll swept up three controls that merely look the same. The damage is not the sweep itself but that onclick is a single slot: the loop silently replaced a handler set 27 lines above it in the same function, so the failure is an assignment quietly overwriting another rather than an error anywhere. This is the second time this exact shape has been found in this file in two days -- bs-group was one name for the bucket button and for every filter group -- so it is the file's habit and not one slip.

**instead:** Keep the name a thing is styled by separate from the name it is selected by, and when you must share one, select on what actually distinguishes the thing -- an attribute, a data key, a container -- rather than on the shared class. Before writing querySelectorAll('.x'), grep .x across the file and count how many hits mean what you mean; if the answer is not all of them, the selector is wrong. And treat onclick as a slot that can be silently taken: assigning it overwrites whatever was there with no error, so two wirings over one element leave the last one standing and no trace of the first. Prefer addEventListener where two things legitimately wire the same element, and in a driven check listen for uncaught errors as a standing assertion, because a handler that throws does nothing and says nothing.
