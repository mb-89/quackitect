RIPGREP IS NOT A DROP-IN, so no substitution. It defaults to recursive from the
current folder where grep reads a named file or standard input. It respects
gitignore where grep does not. Its dialect is Rust rather than POSIX, so a
backreference fails. And -c prints a different shape across several files.

WHAT REACHES WHAT IS IGNORED, and the owner has ruled on it. The default is
right for everything else. .se is the exception, because it holds the log, the
tokens and the scratchpad, and searching it is often the point.

WHICH SEARCH IS MISSING IT, measured rather than assumed. A search over the
tree with no path named does not reach .se at all, because .gitignore ignores
it, and that is the search a worker actually types. Naming .se as a path
reaches the tokens and still not the record, because the jsonl rule applies to
an explicitly named path as well. So both rules have to be lifted.

A FLAG NOBODY HAS TO REMEMBER. ripgrep reads .rgignore beside .gitignore, and a
negation there un-ignores a path. So the tree carries the negation and every rg
call gets it. A rule an agent has to remember is a rule an agent forgets, which
is the whole lesson of this queue.

IT TAKES TWO LINES AND NOT ONE, measured rather than assumed. .gitignore
ignores .se and separately ignores every jsonl file, and un-ignoring the
directory does not lift the second rule, so the record stays invisible while the
tokens become visible. !.se/ and !.se/**/*.jsonl together reach both. !.se/**
alone reaches neither, because the directory itself stays excluded and rg never
descends into it.

WHERE THE NAME IN THE REFUSAL COMES FROM. The guard reads the probe's list,
takes the entry whose purpose is searching file contents, and names whatever

with no edit to the engine, and the engine outside its tests carries no tool

## lesson 1 · round 1 · by reviewer

**the class:** Criteria that pass before the work begins, in two flavours that look different and are the same. One is a command whose tool reports success when it matched nothing, so absence reads as approval. The other is a command that runs a real assertion about a neighbouring fact, so it is green for a reason that has nothing to do with this token. Both are indistinguishable, at the moment of writing, from a criterion that will actually judge the work, and the only thing that tells them apart is running them while the work does not exist.

**instead:** Run every criterion the moment you write it, with nothing built, and require each one to fail. It is the cheapest test in the method, it happens before there is anything to argue about, and it is the only way to tell a criterion from a wish. When one comes back green, ask which of the two it is: a tool that cannot fail on absence, which needs the absence made explicit, or an assertion about something that was already true, which needs rewriting to name this work. And when you reuse an existing test as a criterion, check what it actually asserts rather than what its name suggests, because a name is written for the token that created it.

## lesson 2 · round 2 · by reviewer3

**the class:** A criterion whose sentence is wider than its command. The sentence names the thing that matters, reaches .se, carries both figures, nothing names a tool twice; the command underneath checks a cheaper neighbour of it, or checks nothing at all. Read down the list and it looks complete, because the sentences cover the work. Read across each pair and the command is judging a fraction of what the sentence claims, and the fraction is always the easy part, because the easy part is what was reachable when the command was written. Three of seven on this draft are that shape, and the class survives every fix aimed at one of them.

**instead:** Read the pair, not the list. For each criterion cover the sentence and ask what the command alone would let through, then say whether you would accept that at check time; if not, the command is not the criterion yet. Where a sentence names several things, the log and the tokens and the scratchpad, or both figures, give it one command per thing or accept that the unchecked ones are not being asked for. And run the command in the state the work will leave behind, not only in today's empty state: red on an empty tree tells you the thing is absent, while green in the half-built state is what tells you the criterion cannot judge the work.

**the class:** A number measured on the neighbouring case and quoted as the verdict on this one, protected by a sentence telling the next reader not to re-derive it. The measurement here is real, repeatable and honestly reported; what makes it wrong is that the command timed is the one the rule permits rather than the one the rule refuses, and nothing in the sentence says which command was run. The protective clause is what turns a slip into a lasting one: a figure nobody is expected to check has to be right the first time, and this one is off by a factor the rule's whole justification turns on.

**instead:** Write the command beside the number, always, in the detail and in whatever the work lands in the guidance. A number with no command is not a measurement, it is a memory of one, and a reader cannot tell a recursive search from a single-directory one by looking at 0.055. Then check that the command you timed is the command the rule is about: if the rule refuses form A and permits form B, time form A. And never write do not re-measure this beside a figure, because the instruction only ever protects the figure that turns out to be wrong; if re-measuring is expensive, say what was run and let the next reader decide.

## lesson 4 · round 4 · by reviewer4

**the class:** A grammar approximated by its separators. The rule needs to know which programs a command runs, and the code answers by cutting the string at the three characters that usually separate them. It is right for the shapes somebody had in mind and wrong in both directions for the rest: it misses the newline, which is the commonest separator of all, and it finds statements inside a here-doc, where the text is data. The tests were written from the same list of shapes as the splitter, so they agree with it exactly and cannot disagree with it anywhere.

**instead:** When you split a command, a path, a sentence or a file by its separators, write down the list of separators you are claiming is complete, and then go and find the ones you left out -- for a shell that is the newline before anything exotic. Then ask the mirror question, which is the one that gets skipped: where do these characters appear WITHOUT separating anything? Quoted strings, here-docs, comments and escaped characters all carry them as data, and a blind split turns data into commands. Build the check as a table of shapes rather than as a few examples, and put the shapes you decided NOT to catch in the table too, marked allowed, so the next reader can tell a decision from an oversight. And when a guard exists because a rule cannot be left to memory, the shapes it misses are exactly where memory is doing the work again.
