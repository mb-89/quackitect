## detail

With six agents on one cloud box, the engine stopped answering and had to be started again, over and over. A reviewer reported four se_start calls in one review of one token, and that the engine dropped requests whenever it issued several se_ calls at once while sequential calls worked. The main agent saw the lane answer "the engine over /home/user/quackitect answers no questions yet. Start it again" between two calls that both answered, and the lane's tool calls time out at 60 seconds while a se_test that ran six tests took longer than that.

Measured on 2026-09-05, sessions 20260905-103015 through 20260905-113031, on cf8e1d4e. Some of it is the two-engine race, wk-5e2c601cce, and the staffing guard, wk-bd82b39dcd. What remains after those is this token: concurrent calls from several agents are dropped or answered with a start remedy, and a long call is cut by the lane's 60 second ceiling with its work still running behind it.

## proposed action

Measure first: a test that fires twenty calls at one engine from four goroutines and asserts every call is answered or refused with a reason, never dropped. Then the fix the measurement names. Separately, a call that will outlive the lane's ceiling answers at once with where its result will land, the way the battery already does, so a long se_test never reads as a dead engine.

## done when

- twenty concurrent calls from four agents are all answered, decided by: go test -C src/engine -run 'ConcurrentCallsAreAllAnswered' ./... answers ok
- a se_test that runs longer than the lane's ceiling answers with where its result lands, decided by: go test -C src/engine -run 'ALongTestAnswersWhereItLands' ./... answers ok
- sh util/checks/battery.sh reports no new failure against the run before the change
