## detail

The engine keeps everything about the tree in an index. A fixture that is rows needs no temporary folder, no git repository, and no cleanup that can fail.

Under a parallel battery, many processes writing many small files contend on the disk as much as on the cores.

One test file seeds the index directly today. A search of the test files for the index writers is the command that answers it.

Not every test can go to rows. The engine walks the disk and drives git, and a test of that code wants a real tree. So the backing is a choice the builder makes, and never a rule over the whole suite.

The mechanism this wants is already in the database. A transaction nobody commits is seen by no other connection and leaves nothing behind, and a savepoint does the same nested inside one.

## approach

A second backing behind the builder, seeding rows where today it writes files.

A test needing only a tree the engine can read asks for rows. A test driving git or walking the disk asks for files, and says which it wants.

A row fixture runs inside a transaction that is rolled back when the test ends, so it sees its own writes and leaves nothing. Nesting is a savepoint inside an outer transaction.

The index is one file in WAL mode, which allows one writer at a time, so a shared file would serialise a parallel suite. Each row fixture takes a database of its own instead.

The suite is measured before and after, so the backing is decided by a number.

## done when

- a test can ask the builder for a fixture that writes no file, decided by: read the builder for its two backings
- a row fixture leaves nothing behind when the test ends, decided by: run one and read the index after it
- a test that drives git still gets a real tree, decided by: read what the git tests ask the builder for
- the suite time is recorded before and after, decided by: util/checks/benchmark.sh
