## detail

A container restart moves the agent proxy to a new port and leaves HTTPS_PROXY naming the old one. Every push and fetch then fails with Failed to connect, and land.sh reports it as a network error rather than as a stale variable.

MEASURED, 2026-09-07, after this box restarted. HTTPS_PROXY named 127.0.0.1 port 43603 and nothing listened there. The live proxy was at port 32897, which /root/.ccr/README.md names as the proxy and says is set via HTTPS_PROXY. So the README and the variable disagreed, and the variable was the stale half. git fetch origin v4 failed. The same fetch with the port corrected answered at once.

This costs work rather than time. The card says the unit is the finished thing, and a push is what makes it real. A box whose pushes all fail keeps working and loses everything at the reclaim. Six archived notes are already gone that way.

The diagnosis already finds it. It prints that HTTPS_PROXY names a port nothing listens on. Nothing acts on that, so it is found only by a session that runs the diagnosis after a push has already failed.

## proposed action

Have land.sh ask the proxy where it is before it pushes, and use that. The status endpoint answers its own port, so the live one is read rather than guessed. Where the variable and the endpoint disagree, the endpoint stands and land.sh says so on the line above PUSHED.

## done when

- land.sh pushes over a tree whose HTTPS_PROXY names a port nothing listens on, and says which port it used instead
- land.sh leaves HTTPS_PROXY alone where it already names the port the endpoint reports, and prints no extra line
- the endpoint being unreachable does not stop the push, and land.sh falls back to the variable as it stands
