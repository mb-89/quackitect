## lesson 1 · round 1 · by reviewer4

**the class:** A writer and a reader of one format, tested in one direction. Every check on this token drives the outbound leg: the control sends a message, the engine writes a file, the pane answers fewer rows. Not one of them reads the file back into the form the person will see next time, and that is where two of the three shapes the builder can produce are lost. The escape hatch meant for this -- keep anything unreadable exactly as written -- was aimed at filters a person typed by hand, so nobody asked whether the builder's own output could slip past it. It can, because the regex that reads a comparison happily swallows a whole compound expression.

**instead:** When code writes a format that the same code reads back, test the round trip, not the two legs. Enumerate every shape the writer can emit -- not the ones you had in mind, the ones the code can produce -- and for each one assert that reading it returns what was written, structure and values both. Do it through the real entry points, so the serialising and the file layer are in the loop. And when there is a fall-back for input the reader cannot understand, check that the writer's own output reaches it: a lenient pattern that matches too much will take a compound expression as a simple one and hand back something almost right, which is worse than the fall-back, because almost right gets written back.

## lesson 2 · round 2 · by reviewer5

**the class:** A defect removed from its caller and left in the thing that has it. A consumer misreads a shape; the fix changes the producer so it stops emitting that shape. The symptom disappears, every check goes green, and the defect sits exactly where it was -- now reachable only by the other producers, and for anything read back out of a file the other producer is a person with a text editor. That is the worst place to leave it, because the fall-back meant to protect hand-written input is the very thing being bypassed: a lenient reader does not fall back, it misreads, and something almost right is written back over what the person wrote. Here the two remedies with a visible symptom landed, and the third -- whose symptom the builder could no longer produce once the first two landed -- did not, while the token that tracked it was aborted as obsolete on the strength of a test covering the other two.

**instead:** When a fix works by stopping a producer emitting the shape that breaks a consumer, say plainly which of the two you changed. If the consumer still misreads that shape when it is handed it, the defect is open and what landed was a workaround. Write the check against the consumer using input the producer cannot make, because that is the only input the defect still lives on: a round-trip test seeded from the writer can never fail for it. For any format read back out of a file, treat a person with an editor as a producer with equal standing to the code -- every shape that is legal in the file is input, not only the shapes the writer happens to emit. Prefer refusing to guess: a reader that cannot structure something must fall to a lossless raw form, because almost right gets written back while unreadable gets preserved. And never retire a token carrying several remedies on evidence that covers one -- check each remedy it names against the code, and if one is outstanding leave the token open with that remedy as its whole content.
