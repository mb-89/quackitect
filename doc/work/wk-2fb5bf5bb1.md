## lesson 1 · round 1 · by reviewer10

**the class:** TWO CRITERIA, ONE COMMAND, SO THE SECOND SENTENCE IS AGREED AND NEVER DECIDED. A drafter splits one property into two lines because the two really are different claims, which is right, and then puts the same command under both, because one test is going to cover them. The list reads as two decided things. The gate has one. Whatever makes the first green makes the second green, so the second sentence can be false at every moment of the token's life and no run will say so. It is different from copying a command off a neighbouring token, which specifying.md already names, because there the command names a stranger's deliverable and a reader can see it does. Here the command is correct, current and green for a real reason, and the only thing wrong with it is that it is already spoken for. Nothing on the page marks it: the duplicate is only visible by putting the commands side by side, and a reader goes down the page sentence first. The cost lands hardest on the second of the pair, which is usually the subtler property, the one about HOW the check asserts rather than about what exists. Measured on wk-2fb5bf5bb1: criteria 2 and 3 carry byte-identical commands, and criterion 3's sentence is the anti-vacuity rule that a refusal must be asserted on what only it can say.

**instead:** Two halves, and the first is what stops it being made. Write the command as you write each criterion, not in a pass at the end, and when you find yourself about to reuse the command above, stop and ask which of the two sentences it decides. One command decides one sentence: if a single test really covers both properties, they are one criterion and the second sentence belongs inside the first, and if they are two criteria they need two test names, which costs one function. The second half is the check that catches it, and it is one line anybody can run on their own draft before submitting: pull the commands out of the done-when list and compare them for duplicates. Any repeat is either two criteria that should be one, or a criterion whose command has not been written yet. Do the same for the test names inside them, because two different commands running the same -run pattern is the same defect wearing different clothes.

## lesson 2 · round 2 · by reviewer11

**the class:** A LIVE NUMBER MADE PERMANENT BY A CRITERION THAT REQUIRES IT INTO STANDING GUIDANCE. A draft wants its argument to carry weight, so it measures the record and puts the figure in the detail, and then a criterion requires that figure to appear in a guidance file. The criterion is checkable and it goes green the moment the sentence is written, and the number stops being a measurement as it lands: the record it counted goes on moving, nothing re-derives it, no projection rewrites it, and the file is handed to every reviewer on every pull. A wrong number in a note costs a round. A wrong number in the method is read by everybody for as long as the file exists and nothing will ever say it has gone wrong. IT IS WORSE WHEN THE FIGURE IS A RATE, because a rate has two halves and the halves are usually taken from two instruments, so nobody can re-derive it even on the day. MEASURED ON wk-2fb5bf5bb1: the detail says 61 tokens reached a review with 122 rejections and a rate of 249 per cent, and a criterion requires all three into doc/guidance/reviewing.md. The 106 was right on the day and answers 121 today. The 61 answers 49 from the log and 48 from the notes and reproduces from neither. A round had already said so and the redraft carried the three through unchanged.

**instead:** WHAT WOULD HAVE STOPPED IT BEING MADE: before writing a number into a document somebody else will read later, ask who re-derives it, and if the answer is nobody the document may not carry it. Standing guidance carries the argument and the rule. The measurement that motivated it belongs on the token, where the token dates it and where it dies with it. Where the number must be in the guidance, it goes with the command that produced it and the commit it was taken at. And a rate is written only when both halves come from one instrument and what counts is a rule a command can apply. WHAT WOULD HAVE CAUGHT IT: run every number in the draft before submitting, paste the command and its answer beside each, and name the commit the reading was taken at. Where a number has no command, do not write it: say it is an impression and drop the words that make it sound counted, which doc/guidance/voice.md asks for under Claims. And a count whose set the sentence does not name is not a measurement at all, because nobody can tell what to count.
