## detail

src/engine/removal.go ALoopThatRemoves refuses a command when any part opens a loop and any part runs a remover. It never asks where the files are.

Measured in this tree on 2026-09-05. This was refused as a loop that deletes:

rm -rf /tmp/wt-berg2; git worktree prune; git fetch -q origin v4; for f in doc/work/a.md doc/work/b.md; do git cat-file -e FETCH_HEAD:$f; done

The removal names a path under /tmp, outside the work tree. It sits in its own part, before the loop, and the loop itself runs git cat-file and deletes nothing.

The file's own header draws the line: outside the tree the disk is the agent's own, and a removal there is not this rule's business. ARemovalWithoutARead honours that through anyInside. ALoopThatRemoves does not, so the rule is taught to one half of a mirrored pair.

The damage is that a worker cleaning up its own worktrees under /tmp cannot do so in the same command as any loop. The refusal names a shape the command does not have.

## proposed action

Ask ALoopThatRemoves the same question ARemovalWithoutARead asks: a remover whose files are all outside the work tree is not this rule's business. A loop that names no files at all stays refused, because that is the shape the rule was written for.

## done when

- a loop whose only removal names a path outside the work tree is not refused, decided by a case added to TestALoopThatDeletesIsRefused in src/engine, seen red first
- the loop that did the damage is still refused: the existing case in TestALoopThatDeletesIsRefused stays green
