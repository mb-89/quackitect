## detail

Found while working wk-32c0df8d1c, whose fourth done-when line reads that the queue hands out no work under unbound. It does. src/engine/pull.go never reads the binding, and nothing in the pull path calls LoadBinding or Unleashed. So an unbound agent that calls se pull is handed a token off the queue exactly as a bound one is.

What unbound actually turns off inside the engine is one thing: AStaffShortfall at src/engine/hook.go:790, so nobody is told to spawn. The rest of the queue is off only in the sense that the person stops pressing the panel, which is a habit rather than a rule.

The cost is that the one sentence unbound is described by is not true of the engine. A person takes the queue off to work on one specific thing, and the next pull hands their agent something else.

## proposed action

Have the pull answer wait under unbound, naming the rung, so an unbound agent takes up work by naming it with se work --on and never by being handed it. God is the same as it is: every refusal off.

## done when

- a pull under unbound answers wait and the notice names the rung: go test -C src/engine -run TestAnUnboundPullIsHandedNothing
- a token the unbound agent names with se work --on is still taken up: the same test's second case
- a pull under bound still hands out work: the same test's third case
