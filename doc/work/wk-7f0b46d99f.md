## detail

A criterion is not agreed until somebody has watched it fail.

THE OWNER'S RULE: before a worker submits, it has to have seen the test red.
Not red by some random thing. Red by the assertion it built, with the fix
absent. The reviewer then does the same: it checks the test is red, and if it
is not, or the test is not good, the work does not open for implementation.

RED BY ABSENCE IS NOT RED. go test -run on a name that does not exist answers
ok, no tests to run, and exits zero. A draft went to review with eight command
criteria and every one of them passed with nothing built and no test written. A
linter given a path it ignores does the same. So does a search over a folder
that is not there. Each one reports success for a run in which it asserted
nothing.

WHAT THE ENGINE HOLDS. A criterion carries what was seen when it failed and
what was taken away to make it fail. A criterion with a command and no red
observation is a criterion nobody has tested, and the gate refuses a submission
that rests on one.

TWO PLACES IT IS OBSERVED, and they are different observations. The worker sees
it before the work, with the fix absent. The reviewer sees it again, by putting
the defect back or by building the tree without the fix, and the verdict says
which it did. Neither one alone is enough: the worker's proves the check can
fail, and the reviewer's proves the check is still the one that guards the
behaviour after the work landed.

WHERE IT BITES FIRST. A spec whose criteria cannot go red does not open for
implementation. That is the cheapest place to catch it, because nothing has
been built yet to argue about.

This breaks down the token that put criteria on a token, so what a criterion is
is already agreed. What is added here is that a criterion has to have been seen
to fail.

WHERE THE OBSERVATION GOES, and this is not a detail. A criterion is stored as
a list item with its command under it, and the note is re-rendered from the
parsed token every time it is saved. Prose written into the done when section
is dropped on the next save. Three drafts said in that section that every
command had been run and seen red, and all three lost the sentence between
being written and being read.

So the observation is a field on the criterion and not a paragraph near it. A
criterion carries what was seen when it failed. A criterion with a command and
no red observation is one nobody has tested, and the gate refuses a draft that
rests on one.

## lesson 1 · round 1 · by reviewer6

**the class:** A VALUE WHOSE TYPE HOLDS MORE THAN ITS LINE IN THE RECORD, AND A ROUND-TRIP CHECK THAT ONLY EVER STORES THE EASY VALUE. A field is added to a struct and given a place in the note: one lead, one line. The Go type is a string, so it holds anything, including a newline; the line holds one line. Nothing refuses the mismatch and nothing reports it. The check is written at the same sitting as the format, from the same idea of what the value looks like, so it feeds the format exactly the shape the format survives: a true check of a false assumption. The loss happens on a SAVE, so the value is right in memory, right in the answer the tool prints back, and wrong the next time anybody reads the note; and the overflow does not vanish quietly, it falls through to whatever else the parser matches on a bare line. On wk-7f0b46d99f a two-line Red reads back as one line, a Red whose lines begin with a dash reads back as three criteria, and a two-line Runs is lost entirely -- which makes a command criterion a prose one, which Watched() answers true for, so the gate this token built switches itself off in silence.

**instead:** When a field goes into a line-oriented record, decide before writing the check what happens to a value that does not fit, and write the decision into the note: fold it onto continuation lines and read them back, or refuse it at the gate with a message saying why. Silence is not one of the choices. Then feed the round trip a value the format does NOT obviously survive -- a newline, the lead itself, the delimiter, an empty string -- instead of the value you had in mind when you drew the line. Ask what the value looks like in the wild before choosing its shape: what a check says when it goes red is several lines, so a one-line home for it was wrong on the first day, and the record already shows people squashing it by hand. This is the sibling of doc/guidance/behaviour.md, "A fix in the caller leaves the defect where it is", one step earlier: there a round trip is green because the writer stopped producing the shape, here it is green because the fixture never produced it at all.

## lesson 3 · round 3 · by reviewer8

**the class:** Half a mechanism ships, and the half left out is the one that audits the other. The part that produces gets built, checked and evidenced; the part that checks the first does not, and nothing downstream is visibly missing, because the producing half fills the field, writes the record and turns the gate green. The absence has no symptom until the producing half is wrong, which is the case the second half existed for. It is the auditing half every time, because it has no output of its own: it cannot be demonstrated by showing a thing it made, its tests are about somebody else's mistake, and it always looks like it can follow later -- so it is deferred, and being deferred it is not written down as deferred, because nothing was decided, it simply did not come up.

**instead:** When a detail names two halves, put both in the evidence even if the second one's answer is nothing yet, because the reviewing method allows that answer and the one that fails is silence, which cannot be told from having judged it out of scope. And read the detail for the part whose job is to notice that another part is wrong: that is the one that will be missing, and it goes missing quietly, so look for it by name rather than waiting for a symptom.
