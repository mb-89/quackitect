## detail

CLASS: A FIX SCOPED TO THE LEVEL THE FINDING NAMED, LEAVING THE SAME CLASS
STANDING ONE LEVEL UP.

A reviewer finds an instance and says what would satisfy it. The next draft does
exactly that and stops at the edge of the sentence. The instance is gone, the
finding is answered, and the class is alive one rung higher, wearing the
remedy's own clothes -- which is what makes it invisible, because the thing you
are looking at is the fix you asked for.

THE TELL IS THAT THE REMEDY STILL CONTAINS A LIST. If the answer to "you typed
the members" is a walk over a set that was itself typed -- three struct names,
two directories, four commands -- then the question was never about the members.
Ask the remedy the same question that produced it, once, before writing it down:
where is THIS set defined, and could the check ask for it.

MEASURED ON wk-24be1c06ae, "a line holds one", at round 2. Round 2's finding was
that a hand list of nine struct fields is a photograph of the set, and it was
right. The redraft answers it: "every exported string field of Criterion,
Rejection and Lesson is read with reflect, each must appear in the shape table".
The fields are now asked for. The three types are typed in. And the token's own
detail draws the boundary somewhere else entirely -- "The boundary is the parser
and not the Criterion struct, so the sweep is over every field the note writes
and reads back" -- which is wider than those three.

WHAT IT LEFT STANDING, MEASURED. Token.Detail and Token.Guidance are written to
the note and read back from it by the same parser, and neither is in the walk. I
saved and re-read a token whose detail carries a line beginning with two hashes,
which is what a detail quoting one of this note's own section names looks like:
"the token says / blank / two-hashes done when / blank / and then more" comes
back as "the token says". The same with a line naming a finding heading, the
same with a lesson heading, and the same for Guidance. Everything after the
heading is gone, silently, on the save. That is the very defect the token was
minted about, in a field the token's own boundary sentence covers and its walk
does not, and no field added to Token in future is covered either.

WHAT TO DO INSTEAD, and it is one habit rather than a rule about structs. WHEN
YOU ANSWER A FINDING, ANSWER THE CLASS AND SAY WHERE YOU STOPPED. Write the
level the fix reaches and the level above it into the draft: "the fields are
asked for, the types are named, and here is why the set of types is closed". A
boundary written down is one a reviewer can disagree with; a boundary that is
only the shape of the last sentence somebody wrote is one nobody can see.

AND DERIVE THE OUTER SET TOO WHERE THE LANGUAGE CAN. Reflect walks a graph, not
a struct: start from the type the record is written from and follow its exported
struct and slice-of-struct fields, so a fourth type added to the note joins the
walk without anybody remembering. Where the outer set really is closed, say so
in the table beside the members it excludes, with the reason, which is the same
rule this token already applies to an excluded field.

THE CHECK, RED TODAY: save a token whose detail contains a line beginning with
two hashes and read it back. It comes back cut at that line. A walk over
Criterion, Rejection and Lesson says nothing about it; a walk from Token
downwards names Detail and Guidance and asks what shape they are.
