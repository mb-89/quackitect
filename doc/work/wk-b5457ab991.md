## detail

The battery is 70 seconds on one machine and the whole engine suite alone, off the built binary, is 32. So roughly half the run is everything else plus contention, and the owner judges 70 a lot for a tree this size.

Already done and not to be redone: the lanes are bounded to the core count less one, the five shards were collapsed because the suite is parallel inside itself, and the four selection tests were fed a toolchain instead of compiling.

Not known: where the remaining 38 seconds go. The selftest builds a copy and swings between 16 and 39 seconds under load. go vet runs four times over four modules. The node checks are 27 processes. Nothing has profiled the run as a whole.

## proposed action

Profile the battery as one thing rather than lane by lane, and rank by cost times how often, as the refactoring guidance asks.

Report where the time goes before changing anything. Then say whether the selftest and the four vet lanes are paying for themselves at their price, and whether the node checks want their own pool.

## done when

- the battery is profiled as one run and the report ranks where the time goes
- the selftest and the vet lanes each carry a measured cost in that report
- the report says what would have to change to halve the run, without changing it
