## detail

TestTheQueueIsStaffed in src/engine/standard_test.go fails at the answerHook assertion, before any submission is reached.

The test sets ParallelAgents to 2 on a Config value of its own, then asserts the hook says spawn 2 subagents. answerHook loads the config itself from the tree it is given. The helper that builds that tree copies only src/processes and src/schemas, so no config file exists and the hook reads the default of 5 at src/engine/config.go:450.

The override the test believes in reaches StaffingOf, which takes cfg as an argument. It reaches nothing the hook does. So the assertion could never have held in this tree.

## proposed action

Fix what the hook is handed, or what the temporary tree carries. Do not loosen the assertion.

## done when

- TestTheQueueIsStaffed passes and the number the hook acts on is the one the test set
- the fix is in what the hook is handed or what the tree carries, and the assertion is unchanged

## evidence: the finding

THE FIX WAS IN THE TREE BEFORE THE TOKEN WAS TAKEN UP. The began snapshot
already stores the number with theParametersSay and reads it back with
LoadConfig, and origin's history begins at f9a2af95 with the same shape. What
was left was the evidence.

The mechanism was watched both ways over a worktree of 86b32874. With the
number stored in the tree the test passes in 0.34s. With the number set on the
test's own value only, at 2, the guard at line 261 fails first: the tree says
three parallel agents and the config reads 2. The hook and StaffingOf are
handed the same number, and the assertions are unchanged.

One thing the detail no longer describes: the default is 3 on origin, not 5.
Set at 3 on the test's own value, the old shape passes by coincidence, which
is why storing the number in the tree is the fix and not a wider assertion.
