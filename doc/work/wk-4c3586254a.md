## detail

CLASS: A REDRAFT CARRIES ITS OLD MEASUREMENTS FORWARD WITHOUT TAKING THEM
AGAIN, SO A ROUND TWO TOKEN DESCRIBES THE TREE OF ROUND ONE.

A draft is rejected, the findings are answered, and the parts nobody objected to
are left alone. That is the right instinct about the argument and the wrong one
about the facts. A detail's measurements are readings of a tree that has been
moving the whole time the round took, and the paragraph that says "red today"
or "three files" or "it is green over a live violation" is a reading with a
timestamp on it that nothing prints. The findings are answered, the numbers are
not re-taken, and the token goes out asserting a defect somebody already fixed.

WHAT IT COSTS, and it is not only tidiness. A worker reads the detail as the
frame, goes to watch the named check go red, and finds it green. The two
readings available then are both wrong: that the check cannot fail, which is the
class this project already refuses work over, or that the worker is looking in
the wrong place. Either way the round is spent on archaeology. And a stale
instruction with no criterion over it is indistinguishable from a live one, so
the reviewer cannot tell an oversight from work already done.

MEASURED ON wk-8573243384, "inherited checks are watched", at round 1. Its
detail says "THE FIX HERE, AND THE CHECK, RED TODAY: compare against
filepath.ToSlash(root) as well as root, in both
TestNoCommittedProjectionNamesTheMachine and
TestNoCagedFileNamesTheMachineItWasWrittenOn. That is red today on three files.
Then re-project them so they carry no machine path, and watch it green. The two
generated mcp files also carry an unexpanded {{mcp}} placeholder as the command."
Every word of that was true when it was written and none of it is true now.
Commit 2dd4c19d, "The inherited cage checks are run against the defect they name,
and one was dead", put both spellings into namesTheMachine in
src/engine/cage_test.go and re-projected .claude/settings.json, .mcp.json and
.copilot/mcp-config.json. I counted: fourteen lines of .claude/settings.json
named this machine at ecb7857b, none do at HEAD, no {{mcp}} survives in either
mcp file, and the check is green on zero files rather than red on three.
2dd4c19d is eleven commits before 694def52, the commit that wrote the redraft,
so the paragraph was already false when it was carried forward.

WHAT TO DO INSTEAD. RE-TAKE EVERY NUMBER AND EVERY "TODAY" IN THE DETAIL BEFORE
SUBMITTING A REDRAFT, not only the parts a finding touched. Run the command the
sentence rests on, count the lines again, open the file at the line it names. A
redraft is a new submission and its detail is a new claim.

AND SAY WHEN A READING WAS TAKEN, so the next reader can tell. Where a
measurement is about a state the work will change, pin it to the commit it was
read at -- "red at ecb7857b on three files" -- rather than to the word today,
which is a timestamp that ages without anybody noticing. Where the thing has
since been fixed, say so and name the commit that fixed it, so a reader can tell
work already done from work still owed.

AND ANYTHING THE DETAIL STILL INSTRUCTS HAS A CRITERION OR IT IS NOT ASKED FOR.
An instruction living only in the detail is decided by nobody, which is how a
stale one survives a round.

THE CHECK, RED TODAY: read wk-8573243384's detail against the tree. Its "red
today on three files" is green on zero, and no criterion names it. A redraft
that re-took its readings would have deleted the paragraph or dated it.
