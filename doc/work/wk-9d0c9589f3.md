## detail

The guard refuses a commit that names no path, and a merge commit cannot name one. So concluding a merge is refused, and the refusal tells the hand to do the one thing that would break the merge.

Measured here at 07:44 on branch v4. A merge of origin/v4 conflicted in doc/work/archive.jsonl. With the conflict resolved and staged, `git commit --no-edit` was refused with "A COMMIT CARRIES ONLY THE PATHS IT NAMES". Naming the paths would have made an ordinary commit rather than a merge one, leaving the branch still diverged and the push still refused.

The way through is `GIT_EDITOR=true git merge --continue`, which the guard does not read as a commit. That works, and nothing says so. A hand that does not find it either force-pushes, abandons the merge, or names the paths and makes the divergence worse.

The guard is right about the danger it names. A shared index means a pathless commit can carry another hand's work. A merge in progress is the one case where the index is the thing being committed on purpose.

## proposed action

Let a pathless commit through when a merge is in progress, which is when MERGE_HEAD exists, and say in the refusal otherwise that a merge concludes with git merge --continue.

## done when

- a pathless commit concluding a merge is allowed, decided by: a test with MERGE_HEAD present
- a pathless commit with no merge in progress is still refused, decided by: the same test without MERGE_HEAD
- the refusal names the merge route, decided by: read the refusal text for merge --continue
