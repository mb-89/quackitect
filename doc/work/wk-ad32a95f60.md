## detail

Every agent on a box, the main one and the subagents the engine asks for, works in one working tree with one git index. A commit made by any of them takes whatever the index holds at that moment, and the index holds what every other agent has staged since.

Measured on 2026-09-05, commit f0c20fa3 on v4: the main agent staged four paths by name and committed. A worker subagent had staged its move of src/engine/yaml.go and src/engine/version.go into src/engine/internal. Both deletions rode along in the commit, the additions did not, and origin/v4 stopped building with undefined Build and undefined ylist. cf8e1d4e put the files back. The commit message named none of it, because the committer never saw it.

The two files were the instance. The hazard is the shared index: a second agent's staged change reaches origin under the first agent's name, with no line in the commit saying so, and nothing in the engine refuses it.

## proposed action

A commit through se_run names its paths, and the engine commits those paths and nothing else, with git commit --only <paths>, so the index of the moment is not what is committed. A git commit that names no path, or a git add -A, is refused with this token's reason. A second half is worth a look and is not this token: whether a worker should stage at all when it does not commit.

## done when

- a commit made while another path is staged carries only the paths it named, decided by: go test -C src/engine -run 'ACommitCarriesOnlyItsOwnPaths' ./... answers ok
- a git commit with no path named, and a git add -A, are refused through se_run, decided by: go test -C src/engine -run 'ACommitNamesItsPaths' ./... answers ok
- sh util/checks/battery.sh reports no new failure against the run before the change
