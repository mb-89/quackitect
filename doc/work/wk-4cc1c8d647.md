## detail

RUNME is meant to wrap the command line interface and add nothing to it: check the dependencies, build what is missing, then run the same command with the same arguments and the same help. On a project it rewrites the arguments, and every verb is lost.

THE TWO PATHS. A vehicle's .se/runme.json carries a command, and that branch runs

    exec "$cmd" "$@"

which is the wrap done right. A project has no command, so RUNME resolves the driver through the register and runs

    exec "$engine" --work "$here" "$@"

The dispatch is os.Args[1]. With --work in front, the verb is no longer first, dispatch misses it, and the stray-argument guard ends the call:

    se reads nothing but its flags, and it was handed work --backlog --assignee main
    --title ... which nothing read. Name what you mean with a flag: se --help

MEASURED BOTH WAYS. On a vehicle, sh RUNME.sh work --help answers. Through the driver path, se --work . work --backlog is refused as above. RUNME.ps1 composes the same line, so Windows behaves the same.

The guard is right and the wrapper is wrong. A wrapper that adds to argv is not a wrapper.

WHAT TO DO. Carry the work root out of band rather than in the argument list. An environment variable the engine reads when --work is absent keeps argv untouched, so every verb, every flag and --help pass through unchanged and the person types the same thing whether they call RUNME or the engine. Changing the working directory would also work and is worse: it changes what a relative path in the person's own arguments means.

Whatever carries it, the rule to hold is that RUNME never adds an argument. A test that runs a verb through RUNME on a project, not only on a vehicle, is what keeps it true. The self-test walks the vehicle path today, which is why this stood.
