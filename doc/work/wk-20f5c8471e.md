## detail

An agent that has finished its work cannot hand it in while the queue is short-handed.

Submitting is an se_pull call carrying id and disposition. AStaffShortfall reads only the tool name, so it cannot tell a request for work from a submit of finished work, and refuses both.

The guard's own comment says the opposite. staffing.go line 204: it holds the pull and nothing else, because a write, a run, a test and a read are not the queue. A submit is not the queue either. It takes nothing and gives one token back.

Measured on 2026-09-06. wk-790dd7df91 was finished, green and written up, and its submit answered THE QUEUE WANTS MORE HANDS.

Worse on a cloud box: a finished agent must spawn two agents to file work it has already done, and a box that cannot spawn loses the work with it.

The shell door has it too. aPull matches the word pull anywhere, so a RUNME.sh submit is held the same way.

## approach

toolInput gains id and disposition, which se_pull already sends and the struct
drops. AStaffShortfall takes them and answers not held when both are present.
aPull reads the same rule, so both doors agree and the rule stays in one place.

One test drives both doors. Not done here: whether a claim release or a role pull
should also pass, which needs a case somebody has hit.

## proposed action

Read the id and the disposition, and let a submit through.

## done when

- a shortfall holds a bare se_pull and lets an se_pull carrying id and disposition through, decided by: se test on TestAShortfallLetsASubmitThrough
- the shell door reads the same rule, so a RUNME.sh submit is not held while a bare RUNME.sh pull is, decided by: the same test
- the tests already holding this guard still pass, decided by: se test on TestTheShortfallHoldsThePull
