## detail

src/engine/main.go:136 calls LinkBothNames with a literal list, []string{"se", "se-mcp", "logview"}. util/setup/manifest.json is the tree's list of what it ships, and this is a second copy of it in code.

wk-4ad110f94e ended the same drift in the swap door: buildNext and putInPlace read theBuilds and no longer name a program themselves. Startup is the one place left that still does.

A fourth program added to the manifest is built by the installer, built and put in place by a swap, and then left with only its suffixed name by the engine that starts. The cage names .bin/se with no extension because it travels, so the plain name is the one the hooks reach for, and a program that has only one of its two names fails with nothing saying why.

Nothing is wrong today, because the literal and the manifest happen to agree. What is wrong is that nothing holds them together, and the way this is found is a hook that stops firing.

## proposed action

Read the names from theBuilds at src/engine/main.go:136, the way the swap door now does.

## done when

- src/engine/main.go names no program in a list of its own: se find --regex 'se-mcp' --path src/engine/main.go shows no literal name list
- the names startup links come from theBuilds, the same call the swap door reads
- a test gives a tree a manifest naming a program the literal never had, starts the link step, and finds that program under both its names; watched red before the change
