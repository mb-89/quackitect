## detail

CLASS: THE SECOND NUMBER IS ALREADY IN THE CHECK, AND IT IS SPENT ON AN
ANTI-VACUITY GUARD INSTEAD OF ON THE COMPARISON.

A check that walks a set is told, rightly, that it must not pass by finding
nothing to walk. So it enumerates the set, takes the length, and asserts the
length is more than nothing. The enumeration -- the expensive part, the part
that asks the language rather than describing the set -- is then spent proving
the check has something to do, and nothing ever holds it against what the check
actually looked at.

WHY IT READS AS FINISHED. The guard is a real guard and it catches a real
failure: the set being deleted. It sits at the bottom of the file with a comment
saying why, it is the shape a careful author reaches for, and a reviewer who
knows the anti-vacuity rule sees it satisfied and moves on. The line between "it
found some" and "it found all of them" is one character of arithmetic and a
whole class of defect.

AND IT LEAVES THE AUTHOR BELIEVING THE GAP IS UNCLOSABLE. This is the part worth
saying. Having written the guard, the author knows the set cannot be enumerated
by the instrument they used to walk it -- a regular expression, a hand list --
and writes down honestly that no second number is available. Meanwhile the
second number is three lines below, in the guard.

MEASURED ON wk-1412093cd8, "controls reach the engine", round 2. Its evidence
says, plainly and to its credit: "A regular expression over TypeScript is still
a description of the set ... The honest remedy is the one the class names for a
set the language cannot enumerate: compare the count against something the check
did not produce. Nothing here produces that second number yet." But
util/checks/engine-args.mjs imports the builders module as A and computes
Object.keys(A).filter((k) => typeof A[k] === "function"), which is the language
enumerating the set, and then says only that builders.length > 5. I counted:
src/extension/engineargs.ts exports 26 builders and the two runners between them
ask 25, the twenty-sixth being readKind, which is not an argument builder. So
the check already holds the number that decides the token's sentence and asks it
whether it is bigger than five.

WHAT TO DO INSTEAD. WHEREVER YOU WRITE AN ANTI-VACUITY GUARD, ASK WHAT ELSE THAT
ENUMERATION COULD DECIDE. If you had to enumerate the set to prove the check has
work, you have the set: hold it against what the check covered and fail naming
what is in one and not the other. The guard then falls out of the comparison for
free, because a set with nothing in it and a set nothing covered are the same
failure.

AND WHERE A MEMBER IS DELIBERATELY OUT OF SCOPE, NAME IT WITH ITS REASON in the
same table, so a reader can tell an exclusion from an oversight, which is the
rule this project already keeps for fields and for backlog verdicts.

BEFORE WRITING DOWN THAT A GAP CANNOT BE CLOSED, READ YOUR OWN FILE FOR THE
VALUE THAT CLOSES IT. Saying what you did not do is right and it is not the end
of the work; it is the moment to look once more for the cheap answer, because a
gap named in the evidence is a gap a reviewer must either accept or reject, and
an unclosed one that was three lines away is rejected.

THE CHECK THAT IS NOT THERE: the guard asserts 26 > 5 today and would assert
27 > 5 tomorrow, so no builder added to src/extension/engineargs.ts can ever
make it speak. Hold Object.keys(A) against the builders the run actually asked,
and the twenty-seventh is named on the commit that adds it.
