## detail

Closing a VS Code window on this tree can leave the engine running.

deactivate() in src/extension/extension.ts calls stopEngine() with no argument. stopEngine(context?) kills the ChildProcess handle the window holds, and reads the pid in engine.json only when a context is passed. The comment above stopEngine says that path exists so stopping works on an engine this window did not start. deactivate is the one caller that does not use it.

1. A REATTACHED WINDOW HOLDS NO HANDLE. activate() calls reattach(context), which never sets the engine handle, so on close both branches of stopEngine are skipped and nothing is killed.

2. A SWAP SUCCESSOR IS NOT THE PROCESS THE WINDOW HOLDS. handOver starts a successor no window ever held, so engine.kill() reaches a pid already gone. Measured at 0f226364: session 20260904-132844 carried seven swaps, 14020 to 14672 to 912 to 18024 to 20496 to 9416 to 18864.

3. NOTHING ON THE ENGINE SIDE ENDS IT. The run loop in src/engine/main.go returns only on a signal, on a stop over the socket, or on a swap.

4. PASSING THE CONTEXT IS NOT THE WHOLE ANSWER. A second window reattaches, and killing the pid in engine.json when it closes takes the engine away from the first window, which is still watching. Ending it has to be the last window.

## proposed action

1. deactivate ends the engine through the path that reads engine.json, so a window that only reattached ends it too, and a swap successor is ended by its own pid rather than through a dead child handle.

2. It ends only when this is the last window on the tree. Nothing is shared across windows, so the count has to be written where every window can see it, under .se beside engine.json.

3. Pull the decision out of deactivate into a named function, the way liveness.ts pulled the light out of the timer, so a check can drive it. The check belongs under util/checks, beside no-loose-spawns.mjs and liveness.mjs, which already read the source of the extension.

## approach

WINDOWS SAY THEY ARE HERE THE WAY THE ENGINE DOES. The engine writes a pid to .se/engine.json and whatIsRunning proves it with process.kill(pid, 0). A window says the same: activate writes .se/windows/<pid>.json holding the extension host pid, and deactivate deletes it. A reader drops any file whose pid does not answer, so a crashed window needs no heartbeat.

THE DECISION IS A FUNCTION, NOT A BRANCH INSIDE deactivate. It goes in liveness.ts beside nextEngineState, where this tree already puts a decision a check must drive.

    export function endsTheEngine(others: number[]): boolean

others is every window pid but this one, filtered to those that answer. True when it is empty: the last window out ends the engine.

STOP BY THE PID, NOT BY THE HANDLE. stopEngine prefers the child handle, and after a swap that handle names a process already gone. It reads engine.json first and kills the pid there. It falls back to the handle only when engine.json says nothing. activate keeps the context, so deactivate has one to pass.

NOT TAKEN: the engine counting its own windows over the hook port. It also serves agents and the CLI, which are not windows.

## note

Closing the editor left the engine running.

deactivate called stopEngine() with no argument, and without a context that can only kill a child handle. A window that reattached holds none, and a swap successor is a process no window ever held.

Three parts now. stopEngine reads engine.json first and kills the pid there, with the handle as fallback. Windows say they are here in .se/windows, one file per extension host pid, swept when a pid stops answering. endsTheEngine in liveness.ts decides, and deactivate asks before killing.

THE RULE IS THE LAST WINDOW OUT. Passing the context alone would be worse than the leak. A second window closing would take the engine from the first.

WHERE IT LEFT THE APPROACH. endsTheEngine is handed the probe rather than a filtered list, so the rule about crashed windows sits where a check drives it.
