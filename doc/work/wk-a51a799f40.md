## detail

A hold nobody is behind sends somebody to look. It is not a timeout.

THE OWNER'S WORDS: if an item in review has not changed for ten minutes, the
walker is sent to investigate. The same for a sub-walker: an item held for the
limit and somebody investigates.

A TIMEOUT KILLS WORK. This raises an alarm and sends somebody to look, and a
person looking is what a stuck token actually needs.

ONE QUESTION HAS ONE ANSWER, AND THE ANSWER ALREADY EXISTS. The engine knows
when a holder has gone quiet: limits.pulls_before_hold_is_stale, ten pulls by
anybody without the holder pulling. The queue is its own clock, which is what
the owner asked for when they said they did not like timeouts. So no second
number is declared. Ten minutes and ten pulls would be two answers to one
question, and the state where they disagree would have to be decided by
somebody at check time.

THE INVESTIGATION ASKS MORE OF THAT PREDICATE THAN THE REFUSAL DOES, and the
difference has to be decided here. The refusal only fires when the queue is
already over its limit and it clears the instant any reviewer pulls. The
investigation fires under the limit and sends a walker away from its work, so a
false one costs somebody a trip. There are two states where the predicate says
quiet and nobody has gone anywhere.

WITH NO NAMED SESSION, NOTHING IS INVESTIGATED. Nothing arrives when no engine
is running, so the engine cannot tell a live hold from a dead one, and sending
somebody to look at a hold it cannot check is the same mistake as refusing on
one. The refusal already carves this out and this copies it.

A HOLDER THAT HAS NOT PULLED YET IN THIS SESSION IS NOT QUIET. Arrivals reset
at every session, so on the first pull after a restart every holder looks quiet.
The count is taken from the session's own pulls: a holder that has never pulled
in this session is quiet only once the session itself has seen more than the
staleness. So the first pull after a restart investigates nothing, and a draft
held across the restart by a reviewer that never comes back is investigated once
the session has run its ten pulls.

WHAT IS MISSING IS THE SECOND HALF OF THE OWNER'S SENTENCE. Somebody is sent to
look. Today a stale hold only makes the token count as waiting, and it only
changes anything when the queue is already over the limit. Under the limit,
a token held by a reviewer that died sits there and nothing says so.

WHAT THE ENGINE DOES: a worker's pull that would otherwise hand out work hands
out an instruction to investigate instead, naming the token, who is holding it,
and how far behind that holder is. One thing at a time, so a pull that raises
an investigation raises one.

WHO IS SENT. A walker that is not the holder. Telling the holder to investigate
its own stuck token is an instruction nobody can act on, and a sub-walker that
has gone quiet is not going to read anything at all.

WHICH STATUSES. in_review, spec_in_review, and in_work held by somebody other
than the walker. THE ONE THAT REALLY SITS FOREVER IS spec_in_review: Reclaim in
src/engine/arrival.go frees a token in review and a token in work when a
fresh actor arrives, and it does not cover a draft. That is the failure the
owner saw and it is the case with no other way out.

RAISING IT MOVES NOTHING. The token stays exactly where it is, with the same
status and the same holder, until somebody rules on it. What moves a held token
is an arrival, which is a decision this project already made the other way, and
a token an arrival has already freed raises no investigation however long its
old hold lasted. The investigation is raised against the hold as it stands at
the moment of the pull.

WHY THIS AND NOT ONLY THE STOP HOOK. The stop hook stops a reviewer LEAVING
with a token. It cannot help when a process dies without reaching its stop
hook, which is what happened.

WHY THIS AND NOT ONLY RECLAIM. Reclaim frees a hold when somebody new arrives.
It needs an arrival, so it does nothing at all while the walker goes on working
alone, and it never touches a draft.

## lesson 1 · round 1 · by reviewer

**the class:** A criterion written as a command, in a form whose failure mode is silence. The instinct was right and the shape is right, and the one thing not checked is the thing that makes a command better than a sentence: that it can come back non-zero. A filter that matches nothing, a linter given a path it ignores, a search over a directory that is not there, all report success for a run in which they asserted nothing, so a criterion built on one is a sentence wearing a command's clothes and passes with the work not started.

**instead:** Run every criterion at the moment you write it, before any of the work exists, and require it to fail. That is the only test that tells a command from a sentence, it costs one run each, and it is cheapest at the spec stage because nothing has been built to argue about yet. Where the tool cannot fail on absence, make absence explicit: pin the name and require the line that says it ran, or assert the thing exists before running it. And when a spec quotes a number a person said, write the number into the criteria rather than into the story, because the story is not what the work is judged against.

## lesson 2 · round 2 · by reviewer3

**the class:** A criterion that is red today for the wrong reason. Guarding a command with does this test function exist yet makes it red before the work starts whatever it goes on to assert, so running it and seeing red proves only that the code is absent. It says nothing about whether the assertion the criterion names can ever fail once the function is written. The sibling of this is an assertion pointed at a value the mechanism is not free to vary: the largest value a narrow-smaller parameter allows is its own default, so demanding that value comes back unchanged is a check that can only ever be green. Both read as commands, both go red on an empty tree, and neither can judge the work.

**instead:** Ask two separate questions of every criterion: is it red today, and would it be red for the defect. Prove the second the way this project proves a check, against the code that already has the same shape: write the assertion, put the defect in by hand, watch it go red, take it out, watch it go green, and report both. Point each assertion at a value the mechanism can actually change, never at one the rules pin to the default. And put a number a spec rests on, with its unit, into a criterion, because a criterion nobody can read the number out of cannot judge the number.

## lesson 4 · round 4 · by reviewer3

**the class:** Reusing a predicate without inheriting the tolerance it was built with. The engine already answers has this holder gone quiet, and reusing that answer instead of adding a second number was the right call. What travels silently is that the existing answer is allowed to be wrong in the cheap direction: its consequence is a refusal that clears itself, so false positives cost nothing and the code carries a hand-written carve-out for the one it could not tolerate. Hang a consequence on it that does not clear itself, and every state the old caller shrugged at becomes a defect. The predicate looks like one fact; it is a fact plus the error budget of whoever asked for it.

**instead:** When a spec reuses an existing answer, read the call site rather than the function, and write down what its consequence forgives. Then ask whether the new consequence forgives the same things: list the states where the predicate answers yes without the underlying thing being true, and for each say what the new caller does about it. The carve-outs already in the code are the map of those states, so a guard clause at the old call site is not noise to skip over, it is the previous author telling you which inputs this answer cannot handle. Add a criterion for every one of them, because a state the old caller tolerated is a state no existing test covers.

## lesson 5 · round 5 · by reviewer4

**the class:** A guard tested through a door that has already made it unreachable. The rule was true, the guard was written, and the check was pointed at the public entry point -- which is the right instinct almost always. Here the entry point does something first, Arrived stamping the puller, that makes the guard's condition impossible, so the check passes for a reason that has nothing to do with the guard and would go on passing if the guard were deleted. The evidence then reported it as a red that had been seen, which is the more expensive half: a false claim of a proof is worse than no proof, because nobody re-runs a proof somebody says they watched.

**instead:** When you write a check for a guard, delete the guard and run the check before you believe it, every time, and record what the run said rather than what you expected. If it stays green, ask what else in the path is already making the condition impossible -- usually something the entry point does before reaching the guard -- and then choose: test the guard at the level where its condition can still be true, or delete the guard and write down the sentence that makes it unnecessary. A guard nothing can reach is either dead code or an untested rule, and both are worth naming. And when a submission lists several checks as proved red, prove them in one pass at the end rather than one at a time during the work, because a fixture that moved after the red was seen turns a true observation into a false claim.
