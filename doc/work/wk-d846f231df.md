## detail

Nothing says in a test that taking a token off the queue leaves the rung where it was.

An unbound agent may pull. It is not made to, and the queue does not choose its work, but it may take a token if it wants one. What must not happen is that the pull binds it: an unbound agent holding a queue token is still unbound.

Today that is true by construction. SetBinding has three callers in the engine, and they are the keyword move, the bind flag on the command line, and the definition itself. The pull touches none of them.

True by construction is not the same as held. The rung and the pull are read by different people at different times, and the next hand to add a convenience to the pull has nothing telling them the rung is not theirs to move.

THE OWNER'S WORDS: an unbound agent is not converted into a bound agent just because he takes something from the queue.

## proposed action

One Go test in src/engine. Set the rung to unbound, pull a token, read the rung back and read the hand.

It asserts two things: the rung is still unbound, and the token is held by the actor that pulled it. The second half is there so a test that passes by the pull failing is caught.

## done when

- an unbound tree that pulls a token reads unbound afterwards, and the token is in the actor's hand, decided by: the new Go test in src/engine
- the same holds in god, decided by: the same test over both rungs

### the red was not the red expected

The first version pulled blindly. It failed, because an unbound queue hands out
nothing at all.

That is not a defect. Being handed the next token is the queue choosing, which
unbinding switches off. Naming a token and taking it is you choosing.
