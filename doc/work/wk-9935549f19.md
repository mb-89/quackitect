## detail

se_apply does not enforce the schema's size caps, and every other door does. So a write through apply can leave a token the engine will not load, and the holder is then locked out of the engine entirely.

Seen tonight, by doing it. I grew a note's detail to 2811 bytes through se_apply, against a cap of 1500. Apply accepted it. After that every engine call I made answered the same refusal naming that size. The calls were se_work on three different tokens, se_apply naming a different token, and se_run. Switching tokens puts the held one back, and putting it back validates it.

Two things make it worse than a bad write.

The refusal names a size belonging to a token the caller did not name. So it reads as though the token they asked for is the broken one. Three different tokens, the same 2811 each time.

And the guard measures the file as it stands, so it blocks the very edit that would shrink it. The only way out was se_apply naming the broken token itself, which puts nothing back.

## proposed action

Check the schema on the apply door the way the mint door checks it, so a token that cannot be loaded cannot be written.

Where a token is already over a cap, the refusal names the token it measured and says which section is over. And an edit that shrinks an over-long section is allowed through, because refusing it is a trap with no exit.

## done when

- A test writes a detail over the cap through apply and asserts it is refused: seen red before the change and green after
- A test writes a shorter detail onto a token already over the cap and asserts that write is allowed
- The refusal names the token id it measured, and a test asserts that id is in the message
