## detail

writing-go rule 11 says a goroutine has an owner and a context that stops it. Rule 12 says context.Context is the first parameter. The engine spawns processes, watches the filesystem, serves a socket and starts a detached battery, and it calls context.Background twice.

No test file under src/engine imports context at all. So rule 14 asking a test for t.Context has nothing to hand one to, and a sweep would write 110 unused variables.

The zero on that clause is not the tests. It is the code the tests call.

The symptom is on the record: two tests failed their own TempDir cleanup because a handle was still open. A context that ends with the test is what closes that handle.

## proposed action

Give the long-running things a context that stops them, first parameter, owner named. A test then hands them t.Context and what it started stops with it.

## done when

- the filesystem watcher, the socket server and the spawned processes each take a context as their first parameter
- each one stops when that context is cancelled, proved by a Go test that cancels and waits
- a test that starts one of them passes t.Context and leaves no handle open at cleanup
- src/engine has no call to context.Background outside main

## approach

Three owners, taken one at a time. The filesystem watcher, the socket server and the spawned processes each take a context as their first parameter and stop when it is cancelled.

Each one gets its cancel test first: start it, cancel, wait for it to be gone. That is the red the criterion needs, and it fails before the parameter exists.

Then the tests that start them hand over t.Context, and the handle that failed a TempDir cleanup is closed by the cancel rather than by luck.

main keeps its context.Background, because somebody has to make the first one.
