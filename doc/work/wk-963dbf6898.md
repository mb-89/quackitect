## detail

A submission piped to se pull at the command line is answered with the next token, and the caller may not be a worker at all.

Measured here: a submission typed at the shell closed a note, and the answer carried wk-6542703f66, a parked note. It stood held until a put-down by hand gave it back.

The engine cannot tell the two doors apart. The shell sends verbAsk at src/engine/client.go:27, the lane sends verbCall at src/mcp/lane.go:362, and both carry the verb, its arguments and standard input.

Handing the next token on is right for the lane, because an agent that submits is an agent asking for more. It is wrong for a person at a prompt, who asked for one thing.

## proposed action

The ask says which door it came through, and only the lane is handed the next token.

## approach

THE ASK CARRIES THE DOOR IT CAME THROUGH.

    type verbAsk struct {
        Verb  string   `json:"verb"`
        Args  []string `json:"args"`
        Stdin string   `json:"stdin,omitempty"`
        Door  string   `json:"door,omitempty"`
    }

The lane writes lane. The shell client writes nothing, because a shell is what
an ask with no door is. A field added to a message has to mean the old thing
where it is absent, and every client older than this one is a shell.

The two structs, verbAsk in the engine and verbCall in the lane, are one thing
written twice, which is wk-e80e5c912a. This change writes the field into both
and leaves that copy where it stands.

The call carries it on, so a verb reads the door the way it reads its flags.

runPull reads it once, after the answer is made. A submission through the lane
is answered with the next token, as now. A submission through any other door is
answered as settled: the token it named, the disposition it carried, and no
second token. What Pull handed on is put down again, because Pull takes a token
up as it hands it and a token nobody asked for must not stay in a hand.

A pull carrying no payload is untouched at either door.

## done when

- a submission piped to se pull at the shell answers the settled token, and hands out no second one
- the same submission through the lane answers the next token, the way it does today
- a pull carrying no payload answers work at either door
- an ask that names no door is answered as the shell, proved by a Go test in src/engine
