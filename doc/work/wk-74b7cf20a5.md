## detail

A parent is in work while any child is in work, and it leaves in_work when the last child does. That is how two tokens are in work at once without an agent holding two.

Nothing pulls a parent, so the rule lives in the engine, at the one place a state change is written.

It also replaces a wrong reading. A parent today looks blocked by its own sub-token, when what is really happening is that the sub-token is how the parent is being done.

## evidence: checked

go test -run for the four parent and queue tests passes, and the whole engine suite passes.

## evidence: finding 1, the parent was pullable

The reviewer is right and the probe is right. The test at pull.go that brings back work already picked up asked assignee and status and never the holder, so a parent raised by this rule, in_work with no holder and ahead on seq, matched first. It now asks the holder too: a token comes back only if this actor actually picked it up. THE HOLDER IS WHAT SAYS AN AGENT PICKED IT UP, and a parent has none because nothing pulls a parent. TestTheQueueHandsBackTheChildAndNotTheParent mints a parent and then a child, in that order, asserts the parent is ahead on seq, puts the child in work, asserts the parent followed, and asserts the next pull answers the child. It fails without the holder test and passes with it.

## evidence: finding 2, a held parent was lowered

Also right, and the fix is the one the reviewer named. followChildren now raises and lowers only a parent whose holder is empty, and the empty holder is exactly the mark that the engine and not an agent put it in work. So a parent an agent pulled keeps its state and its holder whatever its children do. TestAHeldParentIsNotLoweredByItsChild pulls a parent first, mints a sub under it, cycles the sub through in_work and out to submitted, and asserts the parent is still in_work and still held by main.

## evidence: what the rule is now

A parent is raised from open to in_work when a child goes in work, and lowered back when the last child leaves, in both cases only while its holder is empty. A parent already submitted, in review or closed is untouched. A parent an agent holds is untouched. Nothing pulls a parent.

## finding 1 · round 1 · That is how two tokens are in work at once without an agent holding two. · by reviewer

**wrong:** After this change the pull hands the agent the PARENT instead of the child it holds, so the agent is handed two. pull.go:419 selects work already picked up with `if all[i].Assignee != actor || all[i].Status != InWork { continue }` -- it tests assignee and status and never the holder. followChildren (store.go:374) now sets a parent to InWork with the holder left empty, and Tokens() sorts by seq ascending, so a parent minted before its children sits ahead of them and is the first match. I copied the package to a scratch tree and ran a probe rather than reading it: mint a parent (seq 1), mint a child under it (seq 2), set the child to in_work through SaveToken, then call next(r, "main", RoleWorker). It answers the PARENT -- 'the pull handed out wk-dab4afa29d (the whole thing) status=in_work holder=""'. The child, in_work and held by main, is never reached. I checked the same probe against `git show HEAD:src/engine/store.go` in the same tree and it answers the child, so this is new. The seq -1 and -2 on this token and its sibling hide it in the live tree: a person put them ahead of their parent. Mint a parent and a child in the ordinary order and it bites at once. Neither new test calls the pull, which is why both pass.

**satisfies:** Make the parent unpullable, since nothing is meant to pull one. Add the holder to the test at pull.go:419 (`|| all[i].Holder != actor`) so only a token this actor actually picked up comes back, and add a test that mints a parent then a child in that order, puts the child in work, and asserts the next pull answers the child and not the parent.

## finding 2 · round 1 · A parent is in work while any child is in work, and it leaves in_work when the last child does. · by reviewer

**wrong:** A parent an agent really is holding is pushed out of in_work by a child, and the holder is left behind, so the record says a token is open and held at once. token.go:38 defines in_work as 'an actor holds it'. store.go:375-376 moves any unsettled parent from InWork to Open when no child is in work, without asking whether the parent got there by a pull. Probed in the scratch copy: mint a parent with no children, pull it (it comes back 'status=in_work holder="main"'), mint a sub-token under it, put the sub in work, then submit the sub. The parent ends 'status=open holder="main"'. The agent still holds it, the ledger says nobody is working it, and it now sits in the open queue while held. Only the case where the parent was lifted by a child is safe to lower again, and the code cannot tell the two apart because it does not record which it did.

**satisfies:** Lower only what this rule raised. Clear the holder when the parent is put back to Open, or better, refuse to lower a parent whose holder is not empty -- the empty holder is exactly the mark that the engine and not an agent put it in work. Add a test that pulls a parent first, cycles a child through in_work, and asserts the parent is still in_work and still held.
