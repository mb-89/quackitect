## detail

Once level 0 registers the tools inside the harness, the MCP lane is a second door onto the same engine with nothing calling it. What hangs off it is not small. A node stub that answers the protocol while a build runs behind it. A committed snapshot of the tool list the stub answers from. A check that drives the stub cold over a tree with no .bin, and a check that drives the built lane warm. All of it exists so that a server arrives in time, and once no server is spawned none of it has a subject. Copilot was the remaining reason to keep a second door, and the owner has ruled it out of scope. The shape this belongs to is doc/spec/one-core-many-satellites.md.

## proposed action

Remove the lane, the stub, the tools snapshot and the two checks that guard them, once nothing calls them. The engine's verbs do not change: what the lane forwarded, level 0 asks for directly. The cage stops naming an MCP server at all.

## done when

- no file in the tree names an MCP server, decided by a search over .mcp.json, util/cage and the projections
- the se_ tools still answer through level 0, decided by the check that token wk-ed8a995880 leaves behind
- the checks that guarded the lane are removed rather than left green over nothing, and the battery lists one fewer
- sh util/checks/battery.sh reports no new failure against the run before the change
