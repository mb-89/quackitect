## detail

The delete guard counts a read by the harness and not a read through the engine. On a cloud box the write gate refuses the harness's own Bash, so the only door left is se_run, and a file read through it stays unread as far as the guard is concerned.

MEASURED, September 2026, on this box. Three files were read whole through se_run, once with cat piped to wc and once listed in full. The next se_run naming rm on the same three was refused with NOTHING IS DELETED THAT NOBODY LOOKED AT, which nothing has read this turn. Reading the same three with the harness Read tool and running the same rm went through at once.

The guard is right and its reader is too narrow. An agent that follows the cloud card, which says to run every command through the engine, can never satisfy it. An agent that reaches for the harness can, so the guard rewards going round the door the project wants used.

## proposed action

Count a read through the engine. se_run already sees the command it runs, so a cat, a head, a sed -n or a se_find naming the path is a look at it, the same way the harness Read is. The rule stays what it says: nothing is deleted that nobody looked at.

## done when

- a delete is granted after the same path was read through se_run, and a Go test drives read-then-delete over one tree
- a delete with no read before it is still refused, and the same test asserts it
