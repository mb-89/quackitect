A GROUP IS EITHER A QUERY OR A BUCKET, AND THE PAGE SAYS WHICH. THE OWNER'S
WORDS: the groups that are not defined by a user defined bucket, these groups
are queries, and they can overlap with user defined groups, and the queries can
also overlap with themselves. Maybe we can signal that by putting a q slash and
then the name in front of it. Yours is a query. Here is a query. Backlogged,
open. All the things that you display at the moment are actually queries. And an
item could be found by a query and at the same time be in a user defined group.
You could implement this as part of the v3 editor port, even though it is
something new.

WHY IT IS NOT A COSMETIC CHANGE. util/views/work.base says today that the
declared groups take their rows first, in order, so the page is a partition and
no row appears twice. That rule is what makes a query and a bucket the same kind
of thing, and it is wrong: a query is a question asked of every row, not a place
a row lives, so overlap is the ordinary case. A bucket is the only group a
person invents and it is where a row actually sits.

WHAT IT FIXES THAT IS BROKEN TODAY, and wk-8a6f9c8146 carries the measurement.
here is declared as imp_open or imp_in_work and claims those rows first, so an
imp_open group below it would never draw anything, which is why the owner sees
three rows under here and no imp_open group at all. Under the partition rule
there is no way to have both. Under queries there is nothing to choose.

THE SHAPE. A group declared by a filter is a query and draws with a q slash
before its name. A group that is a bucket draws with its own name. A row appears
under every query that matches it and under its bucket, and the counts are per
query rather than per partition.

AND THE SET OF QUERIES IS DERIVED WHERE IT CAN BE. Which states a pull hands
this actor is the engine's answer, so the query called here asks the engine
rather than repeating a list of state names in a view file, because a fifth
state added later would leave a typed list quietly wrong.

AND A RULE BETWEEN THE TWO KINDS, WHICH THE OWNER ASKED FOR AFTER SEEING THE
PAGE. THEIR WORDS: we have the queries, and then we have the groups, and maybe
you can make a separator between them, like the separator between the pinned and
the unpinned, just so it is a bit clearer that no group is something different
and that there are duplicates.

THE RULE SAYS WHAT THE q SLASH ALONE DOES NOT. A row is drawn in every query
that matches it AND in its bucket, so the rows below the rule are the rows above
it again. A reader who does not know that reads the page as a list and counts
wrong, which is what happened: the foot said a hundred and fifty-six over a
queue of sixty.

AND no group IS A BUCKET, not a query that came up empty. That is the other
thing the rule says without a legend.
