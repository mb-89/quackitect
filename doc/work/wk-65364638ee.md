## detail

Split off wk-4ad15a5c86, which carried this criterion and fixed the other half.

A tool call through the lane is given sixty seconds by the harness. se test can run for longer: a run of six tests took more than that, the harness cut the call, and the agent read a cut call as a dead engine and started another. The work went on running behind it, with nothing naming where its answer would land, so the agent had no way to ask again for what it had already paid for.

The engine already has the shape for this and uses it in one place. startBattery in src/engine/battery.go writes a marker, starts the run detached with its output to a file, and answers at once with the path the answer lands in. A later engine reads the marker and puts the outcome in the record. se test does not do this: it runs the chosen tests inside the call and answers when they finish, however long that is.

## proposed action

Give se test the answer startBattery already gives. A run the engine expects to outlive the lane's ceiling is started detached, its output goes to a file under .se/tests, and the call answers at once naming that file and how to read it. A run that fits answers as it does now, because an answer in hand beats a path to one.

What decides which is a number the engine holds, not a guess by the caller.

## done when

- a se test that runs longer than the lane's ceiling answers with where its result lands, decided by: go test -C src/engine -run 'ALongTestAnswersWhereItLands' ./... answers ok
- a run that fits inside the ceiling still answers with its result and not a path, decided by the same test
- the outcome of a detached run reaches the record, the way a battery's does
