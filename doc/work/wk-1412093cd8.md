## detail

Every argument list the extension sends the engine is built in one place and
driven against the real engine.

WHAT THE OWNER SAW: they typed a token called test into the work controls and
it arrived nowhere. The panel sent se work --form test. The engine has no
--form, it has --title, so it printed its usage and minted nothing.

THE CLASS, IN THE OWNER'S WORDS: two halves of the system not working together.
The extension and the engine are two programs, and the only thing joining them
is an array of strings that neither one checks. Nothing anywhere reads that
array against the flags the engine actually has.

WHY NOTHING CAUGHT IT. One check drives the page's own handlers in a DOM, so a
click produces the message it should. That is half the trip. The other half,
the message becoming a call the engine accepts, had no check at all, and it is
the half that spans the two programs.

WHAT IS DONE. The argument lists live in src/extension/engineargs.ts, one
builder per control, with nothing in it that reads a file or knows about the
editor, so a check can call it. .se/scratchpad/engine-args.mjs builds every one
of them and hands it to the real binary in a folder made for the run, and
refuses anything the engine answers with an undefined flag or its own usage. It
also refuses an argument that is not a string, because spawning with one throws
before the engine is asked.

WHAT A PASS MEANS. The engine took the call. A refusal about the content is not
this check's business: an id that does not exist is a real answer to a
well-formed question.

## lesson 2 · round 2 · by reviewer6

**the class:** A PATTERN STANDING IN FOR AN ENUMERATION, WITH A COUNT NOBODY COMPARES WITH ANYTHING. This is wk-1412093cd8's round 1 lesson one step out, which is why the round reads as complete. Told to count from the side that produces the thing -- the right instruction -- the check searches the source with a regular expression. A regular expression matches a SHAPE and the set is defined by a BEHAVIOUR. They agree on the day it is written; then one ordinary refactoring, hoisting an argument into a variable on the line above, changes the shape and not the behaviour, and a member leaves the set with nobody deciding it should. What hides it is that the check prints a count, which reads as a measurement, and nothing compares that number with anything: it is a tally of what the pattern matched, not of what exists. Its anti-vacuity guard asks whether the count is more than zero, which catches the pattern matching nothing and never the pattern matching most. On wk-1412093cd8 the tree has nine spawns of the engine and engine-spawns.mjs reads eight; the one it misses writes its flags at the call site, which is the whole class the token is about, and with the owner's own bad flag put back there the check answers 8 read, 0 failed. The coarse count is allowed to be stupid -- every occurrence of the bare call name, minus what you skip deliberately and by name -- because its only job is to disagree with the clever one. A count printed and compared with nothing is a tally, not a measurement. And make the case the pattern cannot read a failure with its own message rather than an absence: a call whose arguments are not visible to the pattern has not passed, it has not been read, and those are different answers. Before trusting any such check, take the thing it hunts and write it in a second ordinary way -- hoist it into a variable, wrap it in a helper, split it over two lines -- and see whether the check still finds it. ## lesson 4 · round 4 · by reviewer10

**the class:** A CHECK THAT READS SOURCE AND MATCHES ONE OF THE LANGUAGE'S SPELLINGS FOR THE SAME LITERAL, RESTING ON A STYLE THE TREE DOES NOT ENFORCE. A guard is written over source text, the pattern is drafted from the lines in front of the author, and every one of them uses the house style, so the pattern encodes the style without anybody deciding to. It is complete against the code that exists and blind to the code somebody types next, and the difference is one character. It is a sibling of the two-spellings-of-a-path class and the harder half of it: there the producer was a program and could be read, here the producer is a person, and a person may spell a string three ways in TypeScript, two in Python, and in most languages more than one. What hides it is that the check DOES fail for the defect, so it can be watched red and the red is honest. Nobody re-runs it with the same defect written differently. Measured on wk-1412093cd8: the guard over flags written at a call site names extension.ts and fails when the flag carries double quotes, and answers 0 failed when the same flag carries single quotes or backticks, on a token minted because a wrong flag reached the engine from a call site.

**instead:** Two halves, and the first is what stops it being made. Before writing a pattern over source, list the ways the language can spell the thing you are matching, and write the list into the pattern's comment. For a string that is a single quote, a double quote and a template; for a number a separator and a radix; for a name an alias and a re-export. Then either cover all of them or say what makes the missing ones impossible, and impossible means a rule the tree enforces rather than a style everybody happens to follow. A check resting on an unenforced convention is a check resting on a habit, and habits are what new code breaks first. The second half is the check that catches it, and it is a re-run rather than a new test: having watched the guard go red on the defect, retype the same defect in each of the other spellings and watch it again. One red proves the guard can fire. Three reds in three spellings prove it fires for the thing rather than for the typography, and that is the difference between a guard and a coincidence.
