## detail

Several workers work one Go package at once, and the method tells each to write a test and watch it go red before the change. In Go the package is the compilation unit. An identifier a half-finished change has not defined yet fails the build of every test file beside it. While that stands, no worker in the engine can run any test, including ones untouched by the change that broke it. It was seen three times inside twenty minutes, each from a different hand.

The cost is not the breakage but who pays it. The hand that wrote the red test sees the red it asked for. Every other hand is told the binary will not build. It cannot tell its own change from another hand's, cannot earn a red for its own criterion, and cannot show a green to close.

A worktree per worker is ruled out. One engine over many worktrees runs a stale engine, because a worktree changes the engine under it. Each worktree would need a whole copy of the system and a merge back. Parallelism scales by boxes rather than by worktrees on one box.

One package one worker is dead here by measurement. Every file under src/engine declares the same package, and a listing of that folder is the command that counts them. So the rule would mean one worker on the engine, ever.

## approach

Three parts, and the first is a rule.

Red first means the assertion fails, never the build. The failing test lands with the identifiers it names, as stubs, so the package still builds for every other hand. Rule 12 already asks for a red watched for the reason expected, and a build failure is red for the wrong reason.

Then the engine holds the rule. A build failure is never recorded as the red for a criterion, and the answer says the package did not compile.

Then the engine says whose work broke it. WhatThisTokenWrote already proves which files a token wrote, and leftOut already names the changed files belonging to other hands. A build error names a file, so the answer can name the hand holding it.

## note

The test door answered a package that would not compile as a test that failed. Every hand on the tree read that answer, and only one of them had written the change behind it. So a build failure now comes back as a run of kind build, never of kind go, and it says no test ran. It names each file the build error names and the token the record says wrote it, which the undo journal already carried. Rule 12 of the work-token guidance now says the same in prose. The worktree ruling under all of it is in doc/rationale. The record alone names the hand, so no signature moved and no file another hand holds was touched.
