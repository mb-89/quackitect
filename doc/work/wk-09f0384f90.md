## detail

A shell command split by separator characters rather than parsed into statements. search.go's pipeline splits on the pipe, on && and on the semicolon, and not on the newline, so every multi-line command escapes the rule: an agent that writes cd src on one line and the search on the next is allowed straight through, and a multi-line command is how an agent runs more than one thing. The same blind split reads a here-doc body as commands, so writing a script that CONTAINS a search is refused although nothing is searched.

REPRODUCED in .se/scratchpad/reviewer4/probe-the-guard.py, driving the built guard with JSON on stdin. Refused: bare recursive, from the root, behind a pipe, after &&, after a semicolon, -R, egrep. Allowed and should not be: the search on the second line of a two-line command, and on the middle line of three. Refused and should not be: cat > x.sh with a here-doc whose body contains one. I hit that false positive live while writing the probe.

WHAT TO DO: split on the newline as well, which is one entry in the same list and closes the miss. Then decide the here-doc: either skip a body between << and its terminator, or accept the false positive and say in the comment why refusing a write that quotes a search is the lesser cost. The detail already takes a position on false positives, that refusing the permitted case sends somebody looking for a workaround, so the decision belongs there.

THE CHECK, RED TODAY: a two-line command whose second line is a recursive search must be refused, and a here-doc that writes one must not be.
