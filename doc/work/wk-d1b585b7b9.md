## detail

A nudge on the way up, once per step, and declining is fine.

THE OWNER'S SHAPE: when three tokens are open where the walker is and none is
in work, the engine says how about you spawn a subagent. At six it says it
again. At nine again. Once each. The same for the reviewer: when the submitted
line is long and nothing is in review, how about another reviewer.

IT IS A NUDGE AND NOT A REFUSAL. Declining is a legitimate answer, because
sometimes work does not split. Nothing is refused and nothing has to be
claimed. The engine says it once and stops.

ONLY ON THE WAY UP, AND ONLY ONCE PER STEP. What the engine remembers is the
highest step it has already nudged at, per queue. It nudges when the count
crosses a step it has not nudged at, and it forgets a step once the count falls
below it. So a queue that empties and fills again nudges again, and a queue
sitting at seven does not nudge every pull.

THAT NEEDS NO CLOCK, which is why it fits: an arrival is a fact and a clock
guesses.

TWO QUEUES, ONE MECHANISM. Open work where the walker is, and submitted work
with nothing in review. Same steps, same rule, two counts.

WHAT THIS REPLACES OR SITS BESIDE: limits.unreviewed_before_blocked is a wall
at one number that keeps firing until somebody obeys it. Decide whether the
nudge replaces the wall or the wall stays as a last resort at a higher number.
The owner has not said, and it is theirs to say.

## finding 1 · round 1 · detail: ONLY ON THE WAY UP, AND ONLY ONCE PER STEP ... it forgets a step once the count falls below it · by reviewer8

**wrong:** The detail's sentence "it forgets a step once the count falls below it" is not what the engine does, and the function written to do it cannot. src/engine/nudge.go has forgetAbove(r, role, waiting), whose body sets the remembered step to stepFor(waiting) -- the general partial forget, spelled out -- and its only call site is inside `if step == 0`, where step is stepFor(waiting). So forgetAbove is reached only when stepFor(waiting) is already zero, and the general assignment can only ever assign zero: the whole rule collapses to forgetting everything when the queue drops below three, the lowest step. I drove it in a copy of the package rather than reasoning about it: a worker queue taken to six is nudged, dropped to four says nothing, and put back to six says nothing again, while a further climb to nine does speak because nine is above the remembered six. The stated rule says four is below six, so six is forgotten and the return to six speaks. This is live on this tree right now, not only in a fixture: .se/nudged.json holds worker 9 and reviewer 6 for this session, and there are eight tokens open where main is, so the worker queue has already fallen from nine to eight and its memory is still nine -- it can cross six and nine as often as it likes for the rest of this session and be told nothing, which is the owner's "at six it says it again, at nine again" not happening. The suite cannot see it because TestAQueueThatEmptiesIsNudgedAgain drains all the way to zero, which is the one fall the call site actually handles, so the test was written from the same picture as the guard and the two agree about a case neither visits.

## lesson 1 · round 1 · by reviewer8

**the class:** The general case is written and only the degenerate one is ever reached, because the call site's guard makes the callee's answer constant. Nothing is dead in the way a coverage tool would notice: the function runs and the line is covered, but one of its inputs is pinned by the branch it sits in, so the general computation can only ever produce the trivial answer. It survives a careful reader because the helper's name and comment are true of the code inside it and the mistake is one level up, in a condition that reads like a guard against nonsense rather than a restriction on meaning. And the test agrees, because whoever wrote the helper wrote the case, and the case they had in mind is the one the call site allows -- so the code and the check agree about a world neither of them visits.

**instead:** Ask what values a helper's argument can actually take at its call site, not what the parameter's type allows: substitute the branch condition into the body and see what is left, and if it simplifies to a constant, either move the call out of the guard or write the constant, so the code stops claiming something it does not do. And feed the test the case the call site forbids -- when a rule is about crossing a threshold, drive it above, below, back above, and part of the way down, and assert on each, because the case nobody writes is the one the picture in your head does not contain.
