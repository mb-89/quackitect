## detail

The engine returns errors to the agent and keeps no count of them. So how much a session errs can only be read from the Claude Code transcripts under ~/.claude/projects. The engine does not own those transcripts, and they do not always keep what a reading needs. Of the four transcripts in this project's folder, two kept none of their thinking text. One kept 8 of 176 blocks and one kept 0 of 352.

The engine sees every tool result it returns, and whether it refused, so it can count both itself. Without that count the reading in the parent note cannot be repeated on a session whose transcript has been rotated away or stripped.

This is the basic under "end a long session": a budget cannot be watched before the thing it counts is counted.

## proposed action

Have the engine keep, per session, the number of tool results it returned and how many of those were refusals or errors. Report both where the running state is already reported.

## done when

- The engine reports, for the running session, two numbers: tool results returned, and how many of those were errors or refusals. Naming a command that the engine refuses raises the second number by one and the first by one. Naming one that succeeds raises only the first.
- The counts are the engine's own, not a transcript's: they are reported for a session with no file under ~/.claude/projects, and the reported total for a session equals the number of results the engine returned in it.
- The counts survive a compaction. An erroring call before a compaction and one after leave the error count at two, not at one and not reset to zero.
- The two numbers appear together with what is already reported by se_status, so a reader gets them without knowing a new command.

## approach

Two numbers the engine keeps itself, per session, on disk.

Counted in runVerbInside, the one place every lane result passes on its way back. CountResult adds one to returned, and one to wrong when the code is not zero or the verb marked the call refused. An error answers a code. The pull answers a refusal as JSON with exit 0, so it marks the call. se_start and a refusal the lane makes on its own never reach a verb, and are not the engine's results.

Kept in .se/results.json as session, returned and wrong, written under the file lock, keyed by the session the current log names. A new session starts over. A compaction resets the read set and nothing here.

Read by ResultsSoFar. Play carries Results and the screen one line, because the state of play is where the running state is reported. se_status prints the state of play after the config.

Two tests. One drives a verb that answers, one that errs and a pull that refuses, and reads the counts back. The other counts, forgets the reads the way PreCompact does, counts again and sees two.

## note

The engine now counts what it returns. runVerbInside is the one place every lane result passes on its way back. After the verb runs it calls CountResult, saying whether the result was wrong. Wrong is a code that is not zero, or a refusal the verb marked on the call. The pull marks its refusals because it answers them as JSON with exit 0.

The count lives in .se/results.json as session, returned and wrong, written under the file lock and keyed by the session the current log names. A new session starts over. A compaction resets the read set and touches nothing here.

The state of play carries the two numbers as Results and prints one line, results N, M wrong. The lane's se_status prints the state of play after the config, so a reader gets the count where the running state was already reported.
