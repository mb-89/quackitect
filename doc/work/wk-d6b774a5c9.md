## detail

A sweep takes notes off the disk and writes their rows into doc/work/archive.jsonl. Reverting that file puts the rows back and leaves the notes gone, so the tokens are stranded: off the disk, on the branch, and named by no row.

MEASURED, 2026-09-07. A hand ran se archive --sweep, saw it rewrite about 180 rows, judged that far beyond one close and reverted the file untouched. It did not revert the deletions, because nothing said there were any. deleted-notes-have-a-row then read 185 notes off the disk with 153 failing, where the same check had read 25 off the disk and 0 failing an hour earlier.

The 153 were restored from origin/v4 and the check reads 0 failed again. Nothing had landed the deletions, so the branch never lost them. That is luck rather than design: any land naming those paths would have taken them off the branch too.

THE SWEEP IS TWO WRITES AND ONLY ONE IS VISIBLE. The rows are a file a hand can see and revert. The deletions are not listed anywhere, so a hand undoing the sweep undoes half of it.

## proposed action

Have the sweep say which notes it took off the disk, the way a close now says which paths it wrote. A hand can then undo both halves or neither. Where that is not enough, have the sweep refuse to run while the clone is behind the branch, because a sweep decides what is finished by reading a record this clone does not hold.

## done when

- a sweep answers the paths it deleted, and a Go test over a tree with two closed tokens reads both back
- a sweep that deletes nothing answers no paths, proved by the same test
- the answer names them where a person reads it, not only in a field
