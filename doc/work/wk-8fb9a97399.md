## detail

A token in doc/work travels and a token in .se/work does not. A traced token that names a private one hands its reader an id they cannot open, with nothing saying why.

The reader is often a cloud agent. It reads the tree out of git, so .se/work is not there at all. It cannot tell a private note from a deleted one.

Five tokens in doc/work name a token in .se/work today. The index answers that over the link table, joining a from_path in doc/work to a to_path in .se/work.

Nothing refuses it and nothing says it happened.

## proposed action

Write the rule into doc/guidance/work-token.md: a token that travels names no token that does not.

Add a standing check that fails on any link from doc/work into .se/work, naming each one.

Fix the ones that exist, by taking the reference out or by saying in words what the private note held.

- the check fails on a link out of doc/work into .se/work: it is seen red on a token minted for the purpose
- no token in doc/work names one in .se/work: the check runs green over the tree
- the guidance says a token that travels names no token that does not: se_find over doc/guidance/work-token.md answers one hit

## evidence: what the five were

Two shapes, and both would have dangled.

Three traced tokens carried a parent that was a private note. So a reader of the child could not open what it was part of.

Two carried successors that were private notes. So a reader could not open what the work became.

Each reference was removed rather than reworded. A closed local token is now deleted by ruling, so those ids are going away. A sentence naming them would rot in its turn.
