## detail

The search guard splits a command on whitespace, so a quoted pattern holding a space becomes two words. The second word is then read as a path, and a bare word is inside the tree, so the search is refused and sent to se find.

Measured in this tree on 2026-09-05, over a file outside the work tree:

grep '^--- FAIL' /tmp/pop2-all.txt

It was refused with THE TREE IS INDEXED, AND A SEARCH OVER IT GOES THROUGH THE INDEX. strings.Fields gives grep, '^---, FAIL' and /tmp/pop2-all.txt. The pattern is the first bare word, '^---, and FAIL' becomes a path. It is relative, so anyInside answers true, and the outside-the-tree file beside it never decides anything.

The same command with an unquoted single-word pattern goes through, and awk '/^--- FAIL/' /tmp/pop2-all.txt goes through, so the refusal is about the space inside the quotes rather than about where the search reaches.

The damage is that the refusal names a rule the command does not break, and its remedy, se find, cannot read a file under /tmp. It is the shape wk-765c819bd7 just fixed in ALoopThatRemoves: a guard deciding on words it has not finished reading.

## proposed action

Take the quotes into account before the words are split, or stop reading a word that came out of a quoted run as a path. The cases belong beside the search guard's own tests in src/engine.
## done when

- a search whose quoted pattern holds a space, over a path outside the work tree, is not refused: a case added to the search guard's test in src/engine, seen red first
- a search naming a path inside the tree is still refused: the existing cases in that test stay green
