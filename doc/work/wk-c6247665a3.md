## lesson 1 · round 1 · by reviewer5

**the class:** A criterion greps for a literal that encodes a claim about the tree, and the literal was never derived by running the command that establishes it. The check then goes green exactly when the deliverable states something false, because rg proves only that the string is present.

**instead:** Derive every literal a criterion asserts - a commit id, a count, a path, a line number - by running the command that produces it BEFORE writing the criterion, and put that command in the criterion. Where the literal can be derived at check time, derive it inside the check instead of pasting it, so the check goes red when the fact moves.

## lesson 2 · round 2 · by reviewer4

**the class:** A criterion whose sentence is about a set and whose command is about one member of it. The sentence carries the intent -- every one was looked at -- and the command carries a single sample, so the check is green for a report that says outright it looked at three of thirteen. It is the same shape as a test that asserts one element of a list and calls the list covered, and it is harder to see in a spec because the sentence beside it reads as though it were the check. The remedy had already been written out in full in the previous round's finding and what shipped was one line from the middle of it.

**instead:** When a criterion says every, each, all, or the rest, the command has to iterate and fail on the first miss -- a loop with || exit 1, not a sample. Read the sentence and the command side by side and ask what the command would let through: if you can write the document that passes it and fails the sentence in under ten lines, write it, and you have your answer. Derive the set in the command where the tree can answer for it, so the criterion cannot go stale between agreeing the draft and doing the work. And when a previous round handed you the exact command, use it or say why not, because taking half of it is indistinguishable from taking all of it in the diff.

## lesson 3 · round 3 · by reviewer6

**the class:** WORK ADOPTED ON THE STRENGTH OF ITS TESTS, WITH NONE OF THEM RUN AGAINST THE DEFECT IT NAMES. Somebody else's branch is read, the commit messages are good, each commit carries a test, and the verdict is taken. "Each carries its own test" is a claim about those tests and it is made by reading them. A test that is read is green; green is also what a test that cannot fail looks like, and guarding something was the whole reason for adopting the work. Inherited work is where this project's own rule -- a check nobody has watched fail is a check nobody has tested -- is easiest to forget, because the check arrives already green and there is no moment at which anybody had to make it go red. On wk-c6247665a3 the central incoming check, TestNoCommittedProjectionNamesTheMachine, compares a committed file against filepath.Abs's backslash spelling of the root while the projector writes filepath.ToSlash's forward-slash spelling, so it cannot fail on Windows: three committed projections name this machine today and it is green, and at the merge commit itself .claude/settings.json named it on fourteen lines. Under it sits the narrower class -- a check comparing two spellings of one thing, a path with either separator, a name in either case -- written in the spelling of the checker rather than the spelling of the artefact.

**instead:** When you take somebody else's work because it is guarded, break what each guard guards and watch it go red before counting it as a reason, then write what it said into the report beside the commit that brought it. One defect per check, one pass; if a check cannot be made to fail in a few minutes, that is the finding rather than a delay. And when a check compares two spellings of the same thing, open the artefact and see which spelling is actually in it, or normalise both sides before comparing -- never write the comparison in the form your own language hands you and assume the file agrees.
