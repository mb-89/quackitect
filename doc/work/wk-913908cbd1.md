## detail

Publish in src/engine/claim.go commits a claim on top of the local refs/se/claims and pushes. When the push fails it reads the other box's ref with `git fetch --quiet origin refs/se/claims:refs/se/claims` and writes again on top. That fetch is refused by construction: the local ref now holds this box's own commit, whose parent is what the remote held, so whatever the remote holds now is never a descendant of it, and git rejects a non-fast-forward update of a local ref unless the refspec carries a plus. With --quiet the rejection is not even printed, so the answer reads "The push did not run: git fetch: " and names no reason. Seen on this tree after a claim: the local ref had the remote's commit as an ancestor, and a dry fetch into it answered "[rejected] (non-fast-forward)".

So the rebase path Publish describes has never run. Two boxes racing on the ref leave the loser's claim local for good, and the answer does not say why.

## proposed action

Fetch the far ref into a name of its own, such as refs/se/claims-far or FETCH_HEAD, build the next commit on that parent, and drop --quiet so a fetch that fails says why.

## done when

- a Publish whose first push is refused because the far ref moved reads the far ref and pushes a commit whose parent is the far commit: proved by a Go test in src/engine over two local repositories
- a fetch that fails leaves its reason in Published.Says
