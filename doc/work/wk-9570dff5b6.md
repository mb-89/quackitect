## detail

FOUND IN THE VERDICT ON wk-c698d46866, landed as 8b224a63.

Publish's recovery in src/engine/claim.go moves refs/se/claims to the remote's head with update-ref and then calls writeTheClaims, which read-trees that head and adds only the paths in `files`. Its comment says "Moving the local ref loses nothing: what it held is these same files". That holds only when the local ref is ahead by this claim alone.

A box whose push fails keeps its claim on the local ref and nowhere else. That is the state this verdict was given from: the cloud proxy answers HTTP 403 on every push. Claim A lands on the ref unpushed. The next claim, B, pushes, fails, throws the ref back to the remote's head and rewrites with B only. A is gone from the ref, and when a push finally succeeds only B is published.

The damage is what claims exist to stop: this box holds A, no other box can see it, and the queue goes on offering A. The old code kept A, because the fetch failed and it returned early.

## proposed action

Carry the local ref's own notes over the remote's head rather than dropping them: read-tree the remote head, then re-add the note paths the local ref held that the remote lacks, before writing the claim again. Or keep the local head as parent and hand writeTheClaims every unpushed note path. Either way the comment that says nothing is lost stops being wrong.

src/engine/claim.go was under another session's hand when this was minted (wk-4759d90994, claims ride a branch), so read what that landed first.
