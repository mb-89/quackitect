## detail

A FINDING AFTER A CONTAINER RESTART.

Outbound HTTPS on a cloud box goes through an agent proxy on a local port, named in HTTPS_PROXY. A restart moves the port and leaves the variable behind, so every git call reaches a port nothing listens on.

Measured on this box. HTTPS_PROXY said http://127.0.0.1:33243 and nothing answered there. /root/.ccr/README.md named 37347, and its status endpoint answered at once. git ls-remote through 33243 said: unable to access, failed to connect to 127.0.0.1 port 33243. The same call through 37347 answered the branch head.

Nothing said so. se claim reported the failed push as its own trouble, five agents were spawned into it, and RUNME.sh --diagnose says it reports the network.

.se/scratchpad/proxy.sh reads the live port out of the README and confirms it against the status endpoint. That is the whole mechanism, and it belongs in the diagnosis rather than a scratchpad.

## done when

- RUNME.sh --diagnose names a dead proxy port and the live one, decided by running it with HTTPS_PROXY set to a port nothing listens on
- the diagnosis is silent about the proxy when HTTPS_PROXY names the live port, decided by the same run without the override
- a git call the engine makes reaches the live proxy whatever HTTPS_PROXY says, decided by se claim publishing with the variable pointed at a dead port
