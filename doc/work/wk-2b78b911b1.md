## lesson 1 · round 1 · by reviewer7

**the class:** A SNAPSHOT TAKEN AFTER THE WORK HAS ALREADY DRAINED PART OF THE SET IT FREEZES, so the items the work acted on first are the ones its own check cannot see. The method already says to pin a one-time assertion to what existed when the work started, doc/guidance/specifying.md under A ONE-TIME ASSERTION WRITTEN AS A STANDING RULE; what it does not say is WHEN the pin is taken. A worker opens the token, does the two or three obvious items because they are obvious, and only then writes the list down, so the list is the set minus the work already done and it reads exactly like the set, because the sentence above it says as it stood when this started. Every criterion is then written over the survivors, the token closes showing fewer verdicts than it owed, and nothing notices, because the check compares the detail against the list and the list is internally consistent. What makes it hard to see is that the number is usually derived and therefore trusted: on wk-2b78b911b1 the 13 is the correct size of the live backlog at the moment it was counted, and the backlog at the commit the work started from was 17. The error is in the clock and not in the counting, and deriving the number harder does not find it.

**instead:** Take the pin from the state the work started in rather than from the state the work is in when you get round to writing it, and derive it from something with a timestamp rather than from the working tree: the commit the token was opened at, or the ids the engine reported the first time you asked. Where items were settled before the pin was written, put them on the list with their verdicts and say which they are, rather than letting the pin close over them. Say in the detail which state the pin was taken from, by sha or by the command and its answer, so a reviewer can re-derive it, and write the check to enumerate the set at that fixed sha rather than against the live one, so it stays frozen when the token closes.

## lesson 2 · round 2 · by reviewer8

**the class:** One red per criterion, taken on the half that was easiest to break, on a sentence that names two things. The observation is true and it establishes the half that was broken, and the half that gets broken is always the cheap one, because that is what makes it quick to watch. This used to be a small weakness and is now the whole of the evidence: the spec gate lets a green command criterion through when it carries its red, so a red taken on the easy half is not weaker evidence than a red the engine ran, it is a claim about a different sentence. And an observation is itself a citation, so one whose file and line cannot be followed leaves the criterion with nothing behind it.

**instead:** Count the properties in the criterion's sentence and take one red for each: where it says A and B, break A, watch it, put it back, break B, watch it, and where the field holds only one observation, split the criterion, because a criterion needing two reds was two criteria. Break the expensive half first, since the half that is awkward to break is the half the check is least likely to be looking at, which is exactly why it is awkward. And record the file and line the assertion is really at, re-read against the file as it stands before submitting, rather than the line it sat on while the file was being written.
