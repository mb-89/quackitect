## detail

The claims ref carries the whole token markdown file for every token ever claimed. SyncClaims reads each one only to parse two frontmatter fields, claimed_by and claimed_at. So full documents are carried for two values. writeTheClaims reads the parent tree and adds to it, so nothing ever leaves: the tree holds every token ever claimed, for ever, and every sync walks it. At the scale this is heading for, tens of thousands of tokens, that is a tree of tens of thousands of entries listed on every read. A lapsed claim needs no deletion, because the engine ignores it, but it is still carried and still walked.

## proposed action

The ref carries one file, holding one line per live claim: the token, the claimant, and when. SyncClaims reads that one blob instead of listing a tree and showing each file. Claims that have lapsed are dropped when the file is written, so the ref holds what is live rather than what has ever happened. What happened is the record's job, and the record is not this ref.

## approach

The ref carries one file, claims, one line per live claim: the token id, the claimant and the stamp, space separated, sorted by id.

Writing. writeTheClaims reads what the parent commit holds through readClaimsIn, drops every claim that lapsed would ignore, and writes this box's tokens over it. A token claimed sets its line, a token released removes it. The text goes to a blob with hash-object, into a fresh index with update-index --cacheinfo, then write-tree, commit-tree and update-ref as before. No note is added, so the tree holds the one file.

Reading. SyncClaims fetches as before and reads head:claims through the same readClaimsIn. A head with no such file is the old shape. readClaimsIn then walks its tree and parses each note's claimed_by and claimed_at, once. The next write folds what it read into the one file, so a box holding the old shape is migrated by its own first claim.

Tests. One drives the real git: a claim, then ls-tree over the ref answers claims alone. One drives nextClaimsFile with a lapsed line and sees it gone. One feeds the sync a one-line file. The old-shape fed tests stand as the migration path.

## note

The claims ref now carries one file, claims, with one line per live claim: the token id, the claimant and the stamp. writeTheClaims reads what the parent commit holds through readClaimsIn and drops every claim lapsed would ignore. It writes this box's tokens over the rest and puts the text into git as a blob in a fresh index. No note is staged, so the tree holds the one file and a release takes its line out.

SyncClaims reads head:claims through the same readClaimsIn, one git show instead of a listing and a show per note. A commit with no such file is the old shape, and readClaimsIn walks its tree once the old way. The next write folds what it read into the file, so a box holding old claims is migrated by its own first claim.
