## detail

The claims ref carries the whole token markdown file for every token ever claimed. SyncClaims reads each one only to parse two frontmatter fields, claimed_by and claimed_at. So full documents are carried for two values. writeTheClaims reads the parent tree and adds to it, so nothing ever leaves: the tree holds every token ever claimed, for ever, and every sync walks it. At the scale this is heading for, tens of thousands of tokens, that is a tree of tens of thousands of entries listed on every read. A lapsed claim needs no deletion, because the engine ignores it, but it is still carried and still walked.

## proposed action

The ref carries one file, holding one line per live claim: the token, the claimant, and when. SyncClaims reads that one blob instead of listing a tree and showing each file. Claims that have lapsed are dropped when the file is written, so the ref holds what is live rather than what has ever happened. What happened is the record's job, and the record is not this ref.

## done when

- the claims ref holds one file and no token markdown, decided by ls-tree over the ref after a claim
- a lapsed claim is absent from the file the next write produces, watched red first against a fixture whose claim is older than the window
- SyncClaims reads other boxes' claims from the one file, and the fed-git tests still hold the ahead-box and refused-fetch cases
- a box holding claims written the old way still reads them once, or the change says how they are migrated
- sh util/checks/battery.sh reports no new failure against the run before the change
