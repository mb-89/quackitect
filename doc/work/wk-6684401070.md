## detail

A rejection mints the lesson's token, and the engine does it rather than the
reviewer.

THE OWNER'S WORDS: if the reviewer sends something back, the engine only
accepts that if the reviewer can name the new tokens it minted, and that should
be automatic.

TODAY IT IS NOT MECHANICAL. A rejection carries its findings and its lesson,
the engine writes both onto the token being fixed, and nothing mints anything.
The lesson names a class of mistake and what to do instead, and then it sits on
a note somebody may read. Every rule an agent has to remember is a rule an
agent forgets, which is what this queue is built on.

WHAT THE ENGINE DOES. On a rejection it mints a backlogged token from the
lesson, and the answer the reviewer gets back names its id. A reviewer that
cannot be given an id has sent something the engine did not accept.

ONE TOKEN PER LESSON AND NOT PER FINDING. A finding is already written on the
token being fixed and the worker is about to fix it, so a token for it would be
the same work twice. The lesson is the part that outlives the token, and it is
the part that has been evaporating. The owner has been offered v3's rule of a
token per finding as well and has not asked for it.

THE SAME CLASS IS NOT MINTED TWICE. A class is the key, so a lesson about a
check that cannot go red makes one token however many rounds name it, and the
answer names the one that already exists.

THE TOKEN IS BACKLOGGED. It is visible and nobody is doing it, which is what
the owner asked for: sent to the backlog, or into the current work if it can be
done directly and is not a giant fix.

## evidence: one token per class

A class is the key. The class sentence is written into the token on a line of its own, and a rejection naming the same class again finds it rather than minting a second. The check proves that: two rejections with the same class, and the second answer names the id the first one made.

## evidence: one token per lesson and not per finding

A finding is already written on the token being fixed and the worker is about to fix it, so a token for it would be the same work twice. The lesson is the part that outlives the token and it is the part that has been evaporating. The owner has been offered v3's rule of a token per finding as well and has not asked for it.

## evidence: the check, proved red

## evidence: the token is backlogged

It is visible and nobody is doing it, which is what a lesson is until somebody decides to act on it. It carries the class, what to do instead, and which token and round taught it.

## evidence: what the engine does now

A rejection mints the lesson's token, and the answer the reviewer gets back names its id. The reviewer writes the class and what to do instead, and the minting is the engine's. A reviewer that cannot be given an id has sent something the engine did not accept.

## evidence: where the id rides

On the answer, in a field called learned. A rejection settles and then the queue hands out whatever is next, so the id is carried onto that answer rather than being an answer of its own. A reviewer sees it on the same call it sent the verdict on.
