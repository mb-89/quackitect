## detail

The engine resolves util/views and util/icons.json from its own location rather
than from --work. A command told to work on one folder wrote into another.

A reviewer isolating itself with --work pointed at a copy still wrote into the
live util/views/work.base twice: a nobody pin and a changed grouping, which the
owner then saw on their board.

WHAT IS WRONG IS THE ROOT IT PICKS. ViewPath reads r.Private("views") and
r.Method plus util/views. Method is where the method lives, and it is right for
a shipped view. It is wrong the moment somebody says --work and means it.

DECIDE WHAT --work OWNS. The likely answer is that a view file found under the
work folder wins, and the method's copy is the fallback, which is what the
comment on ViewPath already claims: a project may keep its own beside the ones
the method ships, and its own wins. That is not what the code does when --work
names a folder that is not the method.

The same question covers util/icons.json, which is read from Method with no
project override at all.

## evidence: the defect

A command told to work on one folder wrote into another. A reviewer isolating itself with --work pointed at a copy still reached the live util/views/work.base twice, and the owner saw the change on their board. Only r.Method was searched for a shipped view, and Method is where the method lives rather than where the work is.

## evidence: the marks too

source/engine/icons.go reads util/icons.json from the work folder before the method, for the same reason. The token named it as part of the same question.

## evidence: what --work now owns

source/engine/query.go: viewDirs answers where a view is looked for, nearest first. The work folder's .se/views comes first, then the work folder's own util/views, then the method's. A tree carrying a copy of the method is worked on by itself, which is what --work means, and the method stays the fallback for a project that ships none. Views and ViewPath share that list, so a listing and a lookup cannot disagree about what exists.
