names a folder that is not the method.

## lesson 1 · round 1 · by reviewer2

**the class:** Fixing a lookup and calling it a fix for a write. The token was about a write landing in the wrong tree; the change made reads prefer the work folder and left the writes to follow whatever the lookup handed back, so the harm stops only for the inputs that happen to resolve locally and continues for every input that falls through. The reproduction was then run on an input that resolves locally, which is the half that already worked.

**instead:** When a resolution rule is changed because a WRITE went to the wrong place, say the rule for reading and the rule for writing separately - a fallback that is fine to read from is rarely fine to write to. Reproduce on the input with NO local copy, because the fallback branch is where the bug is. And read the test you are relying on: one that asserts the old reach is correct cannot go red for it.

## lesson 2 · round 2 · by reviewer4

**the class:** Containment asked as a string question. The fix split the lookup from the write, which was right, and then expressed 'inside the folder being worked on' as strings.HasPrefix on two paths. Path containment is not string containment: a sibling whose name begins with the parent's name passes, and folders named exactly that way are how a person keeps two versions of one project side by side -- which is what this machine has, and which is the situation the token was minted about. The check could not catch it because its fixture came from two t.TempDir() calls, and two temp directories are numbered siblings that can never be a prefix of one another, so the fixture excluded the failing case by construction.

**instead:** Never answer 'is this path inside that one' with a string operation. Use filepath.Rel and refuse a result of ".." or one starting with ".." and a separator, on cleaned absolute paths, and grep the tree first: this project already had that shape written correctly twice, in hook.go's underPrivate and move.go's inRoot, and the third instance was written from scratch and got it wrong. When a rule already exists in the codebase, copy the instance rather than the idea. Then choose the fixture to contain the adversarial case rather than a convenient one: a helper that hands you fresh directories hands you names that are alike in the ways that never fail and different in the ways that never matter, so for any test about how two paths relate, build the two paths by hand and name the relation you are testing -- sibling, nested, prefix-alike, differently cased.
