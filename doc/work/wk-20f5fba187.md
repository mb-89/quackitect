doc/work/wk-c7d3a72daa.md line 120 says: "7b85042f is no object in this clone, so the change reads against HEAD."

It is an object in this clone, and it always was. `git cat-file -t 7b85042f` answers commit. It is held by the local ref refs/se/steps/7b85042fb562, and its parent e7ba69b9 is on group/tests, so the engine wrote it on this box when the work was taken up. Nothing fetched it in later.

The span it dismisses is the clean one. `git diff 7b85042f 7ffca29b` is exactly this token's change and nothing else: doc/work/wk-c7d3a72daa.md and src/engine/testedgate_test.go, two files. The second began snapshot, 07cb4edb, is the one that cannot be used, because its span to ended sweeps in other agents' work from the shared tree.

The damage is on the review rather than the code. [[reviewing]] tells a reviewer to read every hunk of the named span, and a note saying the span is unreadable sends them to HEAD instead. reviewing.md is explicit about the cost: a reviewer who takes such a claim at its word has reviewed the note. Here the authoritative diff was sitting there and the note said it was not.

The sentence looks carried over from wk-4e91c7b3f8, where it is true: 78a9007e really is absent there. It was not rechecked here.

Fix: say which snapshot is unreadable after asking git, or drop the sentence. A note claiming a snapshot is no object should have run `git cat-file -t` on it first.
