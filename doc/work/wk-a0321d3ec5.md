## detail

se_apply matches bytes. Against a CRLF file, an old text joined by bare newlines matches nothing. The refusal reads "the old text is not in the file. Read it and copy the bytes exactly". That sends the reader back to re-read a file they read correctly. The bytes that differ are invisible, and the refusal names none of them.

Measured here on util/parameters.json, which is CRLF. `head -c 60 util/parameters.json | od -c` answers `{ \r \n`. Four applies were refused across three files before anyone suspected the line endings. Each old text matched at once with a carriage return in it.

The trap is that the usual way to read a file makes the difference disappear. `sed -n '261,263p' util/parameters.json | od -c` answers `{ \n`, because sed on this box strips the carriage return. cat does not, and neither does the engine. So a reader who reaches for sed is shown LF, copies LF, and is told the copy is wrong.

This is one line of one message. It costs an attempt every time somebody edits one of the CRLF files in this tree.

## proposed action

Retry the match with the file's own line endings when an apply is refused. Where that match succeeds, name the file's endings and the ones the old text carried.

## done when

- an apply refused for line endings alone names them, decided by: send a bare-newline old text against util/parameters.json and read the refusal
- every other refusal reads as it does today, decided by: send an old text absent under either ending, and read the refusal
