## detail

A CHECK BUILT AFTER THE WORK, FROM THE WORK, CANNOT GO RED.

The voice token took five rounds. Every round fixed the instance the reviewer
named and left the class standing, and the class was the same every time: the
claim was not checkable at the moment it was made, so the reviewer became the
check.

FOUR SYMPTOMS, ONE CAUSE. All four are a check shaped by the fix rather than by
the defect.

- A check asserting what the fix happens to produce. One tested for a class
  name nothing writes, so it passed with the defect on screen.
- A check in the wrong language. A Go fix guarded by a JavaScript test stayed
  green when the defect was put back.
- A word list built from the sentences already deleted. It reports zero by
  construction and cannot go non-zero for anything phrased differently.
- A scope drawn around what was touched rather than around what the claim
  covers. Two files were enumerated and called all of them.

THE CURE IS ORDER, NOT EFFORT. Write the check first. Run it against the defect
and watch it go red. Then do the work. A check nobody has seen fail is a check
nobody has tested.

WHAT THIS TOKEN IS FOR: the rule is written in doc/guidance/reviewing.md, in
the section on findings, where a REVIEWER reads it. It is not written anywhere
a WORKER reads before submitting. So it is guidance a reviewer applies after the
fact rather than a rule that shapes the work.

WHAT WOULD SETTLE IT: the same rule in doc/guidance/behaviour.md, under
Evidence, in the worker's own words. And better, the engine refusing a
submission whose evidence does not name a check that was seen to fail, which is
what wk-bc3c5ba905 builds when a token carries its acceptance criteria.

THESE TWO TOKENS ARE ONE THING FROM TWO ENDS. That one puts the criteria in
front of the work. This one says why the criteria have to exist before the work
rather than after it.
