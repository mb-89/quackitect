## detail

startBattery sets OK true the moment the process starts, at battery.go:106, and again where a battery is merely already running, at battery.go:77. Nothing in it reads the result. tests.go appends that entry to out.Ran and builds out.OK from it, so a whole-battery se test answers ok before a single test has run. The verdict is read later and elsewhere, by RecordFinishedBattery through batteryPassed, which writes to the session log and returns to nobody. So a caller cannot learn whether the battery passed. Nothing gates a close on tests today: the standard process has a row saying se test answered ok, and an agent ticks it by hand.

## proposed action

A battery answers ok only when it has finished and passed. A battery still running answers that it is running, which is neither ok nor a failure, so nothing reads a start as a pass.

## done when

- A battery that has started and not finished does not answer ok, and a test drives one and reads what it says.
- A battery that finished with failures does not answer ok, and a test drives one and reads the failure count.
- A battery that finished with none failed answers ok, and a test drives one and reads it.
- se test over a whole battery does not answer ok before the battery has finished, and a test drives that.

## approach

The battery cannot be awaited. It builds the engine and replaces the one that started it, so waiting for it is waiting inside the process it kills.

So there are three answers rather than two. Passed, failed, and still going. Only the first is ok, and ran carries Pending for the third.

A run whose marker names a process that has ended is read, and the battery's own verdict line is the answer. Asking again once it has finished is how a caller learns the outcome.
