Quackitect around the index

The index is one process that owns every value quackitect knows. Modules compute values and doors connect to the outside, each in its own process. The sidebar, the TUI, the CLI, hooks and any script read a value by name from the index; none of them compute it themselves.

Decided so far

The index is the modelThe whole central model. Files are one topic in it, files/.
One owner per nameEach name has one provider and a default. Alternative calculations are chosen by config at start-up, and no names are added at runtime.
Three kinds of processOne doors process, one index process, and one process per module topic, so a machine with many small cores runs them side by side.
Go core, JS satellitesJS stays only where a JS runtime is required: the VS Code extension and the function-hook module.
Huma for the HTTP doorOpenAPI 3.1 and the /docs page come with it. A module is one file that registers itself.
Pure-Go SQLite, one Go moduleNo cgo and no Zig. Measured at 1.3k, 20k and 50k files: about 1.2–1.4× slower than cgo, under 1 ms per query either way. One module, with packages for boundaries.
Watchdogs on everythingEvery process and door has a dead-man switch. Silence past its deadline marks its names stale, restarts it, and raises an alarm. The cage refuses while the index is down.
Linux and WindowsCloud boxes run Linux, and some people work on Windows. Both behave the same, and CI tests both.

Today

Five long-running processes, four of them with their own loopback port, in two languages. Three of them parse tickets on their own. The red path is how the sidebar's open-task count is computed today.

Target

A door is anything that crosses the boundary, so each one is drawn half inside and half outside. Inbound doors let the outside reach quackitect: LSP, hooks, MCP, HTTP, SSE. Outbound doors let quackitect reach the outside: disk, git, processes, the clock, file watching, Vale, Biome. All doors run in one doors process, which translates between each outside protocol and the internal one. The index process holds the model. Each module topic runs in its own process, reads names from the index, and provides names back to it.

Why separate processes

Go doesn't need separate processes to use every core. Inside one Go process, the runtime spreads goroutines over as many OS threads as the machine has cores. So the reason to split is isolation, not speed:

  • A crash stays in one module. If the retro process dies, the index keeps running, and retro/* names show their defaults marked as not provided until it restarts.
  • A changed module restarts alone. Edit a file in modules/work/, and only the work process rebuilds and restarts. The index stays warm with every file already loaded.
  • The boundary is enforced by the OS, not by discipline. A module process has no way to reach disk or git except through the doors process.

The cost: every read by a module crosses a local socket, which takes tens of microseconds, and values must be serialized. Someone also has to supervise the processes. The index can do that: it starts the module processes, restarts them, and knows which names each one provides.

A module is one file

A topic folder is one module process. Drop a file into modules/work/, and the work process picks it up at its next build: Go compiles every file in the folder into the same package, and init() registers the name. The module never mentions Huma, MCP or VS Code; only the doors know about those.

// modules/work/open_tasks.go, the whole module
package work

import "quackitect/index/q"

type openTasksIn struct {
	Places Places `q:"work/places"`            // input: declared, delivered as one snapshot
}

var OpenTasks = q.Derived("work/open-tasks", 0,
	q.Doc("The tickets this box can take: the number in the work tab's brackets."),
	q.Show(q.Badge{On: "work/editor"}),
	func(in openTasksIn) (int, error) {     // processing: pure, no index access
		return in.Places.Takeable, nil          // output: committed at once
	})

// an alternative calculation lives in its own file,
// open_tasks_cloud.go, and config picks one at start-up:
//   q.Provide(OpenTasks, "cloud", cloudCount)
// input · processing · output: one snapshot in, pure work, one commit out.
// `quack why work/open-tasks` shows this file, its inputs and its readers.

Views are declared once

Generating one tab per topic doesn't work: quackitect has two real views today, log and work, and neither is a form. So views are declared, not generated. The work editor already is half-declared. spec/views/work.base names its columns, flag letters, presets, filters and sorts, and src/tui/tree draws any base file. What the file doesn't say yet is which name the view reads and which actions its buttons and keys call. Adding that makes the view complete:

# spec/views/work.base: what it holds today (excerpt)
columnSize: { name: 44, flags: 6, queue: 6 }
flags:
  - { letter: U, key: urgent, tone: bad }
  - { letter: C, key: cloud }
groups:
  - name: queue
    pressed: true
    filters: [ { queue: /./ } ]
    sort:    [ { key: queue } ]

# sketch: what makes it a complete view
reads: work/rows
actions:
  - { key: p,     calls: work/place }      # the place chord
  - { key: enter, edits: cell }
  - { button: pull, calls: work/pull }

A renderer implements "base view" once, and every declared view works in it. The TUI is the first renderer. A web renderer, or the VS Code webview, could come later and show the same work editor from the same file.

The TUI

pylib's idea carries over: the TUI is the CLI with tabs, and nothing is written twice. Tabs on the left are declared views. Tabs on the right are generic and the same in every tool built on quackitect:

  • index: every name with its value, provider, and whether it's provided or still the default, updating live.
  • cli: the full command tree, as in pylib.
  • help.

Operations: a handle for every action

An action that takes longer than a moment (a pull, the check, a review, a retro collect) returns a handle at once instead of making the caller wait. The operation itself is a name in the index, ops/<id>, with its state, progress, deadline and result. They are called operations because "ticket" already means a work ticket here.

  • Callback or poll, with nothing new to learn. The caller subscribes to ops/<id> to be called when it finishes, or reads it to ask for the state. It is the same get and watch every other name uses.
  • States: queued → running → done, or failed, or cancelled. Each move is pushed to subscribers.
  • The watchdog owns the deadline. An operation that misses its deadline is failed loudly and its undo steps run. The handle alone doesn't prevent hanging; it moves the hang somewhere a watchdog can see it and end it.
  • One writer at a time. Writing operations queue per tree, so a git hook calling back in while a hand-back runs waits in the queue instead of deadlocking.
  • It outlives the caller. A hook that times out, or a closed terminal, leaves the operation running and readable. Another client can pick up the result.
  • Only recent operations are kept. Running and queued operations are never evicted. Finished ones stay for a window (the last few hundred, or a few days, set in config), and failed ones stay longer, so a loud failure is still there when someone looks. Every state change is also written to the session log, so the history outlives the window.
  • Not for reads. Values are already pushed, so reading a name never needs a handle. The cage's allow-or-deny answer inside a hook call stays synchronous too, because the harness waits for it.

Watchdogs and dead-man switches

A part that has stopped working must never look like a part that is working. So every process, door and provider holds a lease that its own work loop renews. When the loop stops, the renewals stop, and the watchdog acts.

  • The heartbeat comes from the work loop itself, not from a separate timer. A loop that hangs while a timer keeps ticking is exactly the case a dead-man switch must catch.
  • Alive is not enough. A provider with a pending input change must commit a result within its deadline, and an action must finish within its deadline. A run that misses its deadline is cancelled, the action's undo steps run, and the process restarts.
  • Silence is visible. When a lease expires, every name that provider owns is marked stale since <time>. It never quietly falls back to its default. Subscribers get the change: the badge greys out, and the TUI and quack why show it.
  • Restart, then escalate. The index supervises its processes and restarts them with backoff. After repeated failures it raises an alarm name (session/alarms), which the sidebar shows and the hook module adds to the agent's context.
  • The watchdog is watched too. The doors process and the hook module both watch the index's lease and restart it when it goes silent. While the index is down, the cage refuses, and the refusal names the alarm. Failures should be loud, so they get fixed early.
  • Deadlines are declared. Each name and action states its deadline in its declaration (q.Deadline(2*time.Second)), with a default for every kind, so no part runs without one.

Doors, one file each

A door is an interface, a real implementation and a fake, all in one file. The doors process picks the real one in use and the fake one in tests. A new adapter (say a Slack door, or a second VCS) is one more file; the index and the modules stay the same.

    work/  pull/  hold/  ask/  check/  retro/  guidance/  vehicle/  …

// doors/out/git.go: one adapter with its fake inside
package out

type Git interface{ Run(args ...string) (string, error) }

type realGit struct{}                            // runs the git binary
type fakeGit struct{ Answers map[string]string } // answers from a table

func init() { q.Door[Git]("git", realGit{}, &fakeGit{}) }

What changes for the agent

Once the system stands, most work is content, not infrastructure. Content work means adding or changing a module, a view or a door, and each of those is one file with a known shape. The context the agent needs shrinks to that file plus the names it reads, which the index lists.

This only holds if the rules below hold. As soon as a door or a renderer special-cases one name, the 20-files problem comes back. Infrastructure work, such as changing the index, the protocol or a renderer, stays broad. It should also be rare, and done in tickets of its own.

Rules the build enforces

  • Only doors cross the boundary, in either direction. Each door carries its own fake. An outbound fake answers from a table. An inbound fake replays recorded traffic, such as a hook event or an HTTP call.
  • Doors and renderers import no module. They see only the registry, so they can never special-case one name.
  • Only providers write a name. Everyone else reads it or watches it. Only the watch door feeds files/, and actions change files, never derived values.
  • Modules touch nothing outside. They read file contents from files/ and act on the world by calling a door.
  • Views get data only by reading names. A view decides how things look, never what they mean.
  • The index refuses to start on a broken catalog: a duplicate name, a missing default, two active providers for one name. CI starts it, so these failures show up before merge.
  • Linux and Windows. Loopback TCP plus the standing file, no Unix sockets, no named pipes, and a Windows job in CI.

Still open

  • The internal protocol. Every peer inside is Go, so gRPC streams (typed, no broker) and NATS (the index embeds the server; subjects as names, request/reply and watch built in) are the two candidates. The outside never sees it, because the doors translate.
  • The LSP door. VS Code expects to start its language server itself. Either a thin quack lsp relays stdio into the doors process, or the extension connects to the doors process's port.
  • Which views exist. Work and log today. The work view's reads and actions need to be written down before the TUI renderer can be generic.
  • Running old and new side by side. The Go CLI hands verbs it doesn't know to cli.js until each topic is ported.
  • The pilot slice. work/open-tasks end to end: the watch door → files/ → tickets/ → work/places → the badge and the TUI header.
