# Why

A retro reads a window of the record. Collect puts that window in one place
before anybody reads it, so every later step reads one folder and runs nothing.

The shape the owner set:

| where | what stands there after collect |
|---|---|
| `.se/.runtime` | the state a session throws away |
| `.se/.retro/<retro>/input` | everything else the private folder held, plus the transcripts, the memory and the scratchpads |
| `.se/.retro/<retro>/collected.json` | when this collect ran, which is where the next window opens |

Read this note again on any of three signs:

- a later step reads a file outside the input folder
- `.se` holds a third thing after a collect
- a count reads zero where the owner saw work happen

## 1. Nobody else holds work

Collect moves folders, and a move takes the file a working hand reads. One run
while somebody was mid-task deleted what they were reading. So the verb refuses
while another hold stands, and passes the hold of its own retro.

A retro reading a red battery reads what broke today and no pattern, and a
warning is a fault somebody left standing. So collect opens on a stamp green at
this commit, with no warning, as a push does.

## 2. One folder holds all

The retro before this one read its numbers off a copied log, and opened no
transcript. The command line carried no door naming where the transcripts stood.

It reported zero refusals, a shell count far below the truth, and a thought
length of zero in every chapter. Each zero was an instrument reading nothing.
The report presented each one as a finding.

An input a step goes looking for is one the next retro also goes looking for. So
the fix lands in the verb, and a step reading around the folder hides the gap.

### What stays outside the tree

The memory is standing state and no event, so collect copies it whole, whatever
its age. The transcripts and the scratchpads are events, so collect copies what
changed since the last collect. A retro with no collect before it takes
everything.

The harness names a transcript folder after the path a session starts in. A
session started from a folder inside the tree names one of its own. So collect
takes every folder whose name opens with the tree's own.

## 3. The count stands printed

A short answer reads like a whole one. v3 lost a whole session to a log that
rotated mid-retro. The live file held 103 records where 1413 stood, and the
answer looked right.

So collect prints the count for each source, and the owner reads it against what
they saw happen.

## 4. Dot folders stay

Collect moves everything past the dot folders, a move and no copy. So the next
retro starts empty, and nothing counts twice. A folder under a dot name is one
the owner keeps out of every retro.

The log is the one dot folder collect drains. A running session writes it
through the whole retro, so its dot keeps the private folder empty meanwhile.

A third thing standing after a collect is a writer putting a file where it does
not belong. The collect names it and answers one.

## 5. History stands apart

Runtime state is what a session throws away: the index, a hold, a stamp, a built
binary. The log is history, so the retro collects it, and it stands outside the
runtime folder.

A writer spelling a runtime file straight under `.se` breaks the collect. The
index binary did exactly that after the runtime move. Its build predated the
move, and the install asked only whether the binary stood.
