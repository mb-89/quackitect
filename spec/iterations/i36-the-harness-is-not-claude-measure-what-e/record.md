se_house WAS A BAD BUNDLE, NOT A BAD NAME. It merged two jobs: se_reload and se_prompt_place both make the live system take up what changed on disk, while se_panel opens the mirror and points a highlight at a surface for a person. Replaced by se_refresh {what: engine|prompt} and se_mirror {op: open|point|shoot}, the second absorbing se_shoot, which stood alone only because nothing else did. The verb count is unchanged at 19.

THE 2 KB CAP AND BUNDLING ARE TWO DIFFERENT PROBLEMS AND THE REPORT RAN THEM TOGETHER. The cap is PER TOOL, so merging five verbs ADDS their descriptions: bundling does not remove one byte, the total stays 19,538 at 34 tools or at 19, and it makes the cap HARDER to meet. Bundling buys COUNT against Cursor's 40 across all servers. Shortening descriptions is the independent fix and it helps everywhere at once. THERE IS A PRINCIPLED WAY TO SHORTEN: the same rules are delivered twice today, once in the 43,008-byte prompt layer and again in the tool descriptions. se_pull's 2,425 bytes re-teach the whole loop, and walking.md and lane.md already teach every part of it. So the tool description becomes a SCHEMA NOTE — arguments, answer names, what a wrong call gets — and the loop stays in the prompt layer, which is not capped. That takes se_pull under 2 KB without losing a rule, and the same argument covers se_run, se_test and se_file_read, which are over half the budget between them.

THE HOOKS ANSWER IS BETTER THAN THE EARLIER PART SAID, and Part 9 is corrected. First, the MODEL never decides which files are read: running Claude inside Copilot changes nothing, because the HARNESS reads files and the model only reasons. Copilot CLI DOES read .claude/settings.json for a documented cross-tool subset that includes hooks, with PascalCase events and Claude's payload shape — se-hook-stop.ts already relies on it. VS Code DOES run .github/hooks/*.json BY DEFAULT: chat.useHooks defaults true and chat.hookFilesLocations ships .github/hooks true. The preview flag chat.useClaudeHooks gates only the .claude-format files. So no single hook file reaches all four surfaces, but TWO FILES REACH ALL FOUR BETWEEN THEM and both are committable: .claude/settings.json for Claude Code, .github/hooks/*.json for the whole Copilot family. Generate both from one source. AND MAKE EVERY HOOK SCRIPT IDEMPOTENT, because Copilot CLI reads BOTH and fires the same script twice — that is happening today and only se-hook-stop.ts survives it, on a bites-once valve keyed on stop_hook_active. se-hook-start.ts and se-hook-websearch.ts have no such valve. AND A NINTH MILESTONE, THE TOKEN BILL, ASKED BY THE OWNER AND WRITTEN UP AS PART 18. FIRST THE NUMBER THIS REPORT GOT WRONG: it said 43,008 BYTES and that is not 40,000 tokens. Measured on the wire, tools/list is 68,244 bytes and the prompt layer 43,008, so the standing prefix is 111,252 bytes or roughly 29,300 tokens, with boot's four documents another 36,911 once per session and again after every compaction. Every token figure is an ESTIMATE at 3.8 bytes per token and step one is to replace them all using the API's own count_tokens, never a byte ratio and never a third-party tokenizer. THE GOOD NEWS IS THAT IT IS NOT PAID PER CALL: prompt caching is a PREFIX MATCH over tools then system then messages, a cache read costs about 0.1x against a write at 1.25x, and the documents the pull serves arrive as tool results inside messages, so once served they ARE part of the cached prefix. The owner's question answers YES and is already true in principle. THE QUESTION IS THEREFORE WHAT BREAKS THE PREFIX. AND THE UNCOMFORTABLE HALF: WE DO NOT CONTROL cache_control. The harness owns the API call and this is an MCP server behind it, so we cannot place a breakpoint, cannot pick a TTL, and cannot read usage.cache_read_input_tokens back to see whether anything worked. The only lever is SHAPE, meaning stable and deterministic and few. THE SINGLE BIGGEST ITEM IS ONE STRING: the narration update argument's description is 888 bytes and it is shipped 34 times, once per verb. That is 30,192 bytes, 65% of all schema and 44% of the entire tools/list payload, roughly 8,000 tokens, at position 0, in every session, gaining nothing. Shortening it to a pointer is a bigger win than the whole of Part 14's bundling. THREE MORE THINGS BREAK THE PREFIX AND THEY ARE OURS. The 20-BLOCK LOOKBACK: a breakpoint walks back at most 20 content blocks, and this system's loop is pull-do-pull, with one turn of the session that wrote this running 605 lane calls between two narration updates, so every turn past 20 blocks re-pays for everything. The TOOL ORDER: deterministic by Map insertion accident and pinned by no test, so a reordering refactor silently invalidates every session, and the 2026-07-28 spec says servers SHOULD return deterministic order for exactly this reason. And the PROMPT LAYER'S HASH-STAMPED HEADER, which is correct behaviour and means every guidance edit costs one full re-prime for everybody. The fourth is compaction and is not ours. WHAT IS ALREADY RIGHT AND MUST NOT BE OPTIMISED: tools/list does NOT vary by state, because states grant tools at dispatch under SE-C-110 and the served list stays whole. Filtering it per state would look like a saving and would invalidate the entire cache at every transition. AND ONE STANDING CAUTION: all of this is the Claude API's caching model. The other harnesses cache too and none publish the same mechanics, so the honest scope is to make the bytes stable and few, which helps under every scheme, and not to tune for one vendor's breakpoints we cannot even set. AND THE OWNER'S SKILLS PROPOSAL RIDES THE SAME MILESTONE, evaluated as PART 19. THE IDEA: package the guidance as skills, have the pull NAME the skill to load rather than ship the text, and keep the read-proof afterwards. IT IS THE RIGHT SHAPE, and for a reason beyond tokens. WE ALREADY BUILT PROGRESSIVE DISCLOSURE BY HAND AND CALLED IT read — the pull serves one method document when the walk reaches the state that wants it, proves it, and serves the next. Skills are the harness-native version of a mechanism already here. AND SKILLS ARE ALSO THE PORTABILITY ANSWER: SKILL.md is the one artifact roughly twenty platforms parse identically, and both install-time generators the scan looked at, spec-kit and BMAD, converged on emitting skills. That lines up exactly with the installer ruled on in Part 13. BUT CACHED IS NOT THE MECHANISM. A skill body is not a separate cache tier: when it loads it becomes content in the conversation and is cached like any other history, exactly as the pull's documents already are. Within a session a document is served once either way, because the reading credit already stops a second serving. THE GAIN IS THAT AN UNUSED DOCUMENT IS NEVER SENT AT ALL. And it dies in a compaction like everything else; whether a harness re-surfaces a skill more cheaply than our re-read is UNKNOWN and must be measured. THE COST MOVES RATHER THAN DISAPPEARS: every skill's name and description sits in context from session start, and Claude Code budgets it explicitly, truncating description plus when_to_use at 1,536 characters per skill with skillListingMaxDescChars and a skillListingBudgetFraction over the whole listing. So the constraint INVERTS — the problem stops being long documents and becomes eighteen long DESCRIPTIONS, permanently resident. Each must be one trigger-shaped line. THE SPLIT IT FORCES IS THE USEFUL PART AND IT ALREADY EXISTS IN THE CODE. The always-true rules CANNOT be skills: contract.md, walking.md, method/lane.md and voice.md bind BEFORE the agent knows what it is doing, and a rule that loads on demand can be skipped by not demanding it. Those four are exactly promptlayer.ts's PROMPT_SOURCES, they are the 43,008 bytes, and the only lever on them is shortening. Everything else is situational — front-desk, retro, cloud-runner, overhaul, tour, machine-authoring, engineering, software, ux — and is a perfect skill. THE READ-PROOF SURVIVES THE MOVE AND IS WHAT MAKES IT ENFORCEABLE: the server cannot make an agent load a skill, but the proof does not care how the text arrived, so naming a skill plus demanding its last words converts please load into prove you loaded. WHAT IT DOES NOT FIX: the 68,244-byte tools/list is untouched, because skills carry guidance and not tool definitions. That half needs the update description that is 44% of the payload, plus tool search, which Claude Code already applies by default and which APPENDS rather than swaps so it preserves the cache. Do not let the skills idea crowd out the schema work — the schema half is bigger, cheaper and needs no new mechanism. TWO HARD CONSTRAINTS BEFORE BUILDING: skills-over-MCP is SEP-2640, in review on the extensions track and NOT shipped, so a lane cannot serve a skill today and the installer must emit them as files; and the paths differ per harness, with Claude Code reading .claude/skills/ and NOT .agents/skills/, Copilot reading .github/skills/ and .claude/skills/ and .agents/skills/, and JetBrains reading none. THE RECOMMENDATION IS ONE DOCUMENT, NOT EIGHTEEN. front-desk.md first: self-contained, purely situational, and the desk already knows when it is wanted. Convert it, measure the listing cost against the saved body cost with count_tokens, and only then decide about the rest — because the honest summary is that this trades a large occasional cost for a small permanent one, and whether that wins depends on numbers nobody has yet. AND PART 20 SHARPENS IT INTO A DESIGN WITH ONE RULE THAT DECIDES WHERE IT PAYS: A HOP PAYS WHEN IT MOVES CONTENT FROM ALWAYS-ON TO ON-DEMAND, AND IT COSTS WHEN THE CONTENT WAS ALREADY ON-DEMAND. Everything follows from that. WHAT IS PAID WHEN: the prompt layer's four files are 43,008 bytes EVERY TURN and are the only every-turn cost; tools/list is 68,244 once at position 0, of which 30,192 is the update description in 34 identical copies; boot's four documents are 36,911 and are ALREADY on demand; the other fourteen guidance documents are about 130,000 and are only sent if the walk needs them. AND WITH AN INTACT PREFIX NONE OF IT IS RESENT AT FULL PRICE — it is paid once at about 1.25x then read at about 0.1x — so the re-sending worry is mostly answered by caching already, and what remains is the real one: SENDING THINGS THAT ARE NEVER NEEDED AT ALL. WHERE THE DESIGN PAYS, IN ORDER. ONE, the update description, which is the owner's idea applied exactly: 34 copies of an 888-byte paragraph become 34 one-line pointers plus one copy elsewhere, roughly 30,192 bytes down to 2,700, about 7,200 tokens at position 0, no new mechanism and no extra hop. TWO, the prompt layer, the only every-turn cost, where the design's question is exactly right — how much of this binds BEFORE the agent knows what it is doing. Contract.md's thirteen rules do not all answer the same: the lane is the only door, walk the state in your hand, autonomy is the person's dial, finish it before you judge it, disagree and commit, and walk do not ruminate are always-true; never open a record unasked, never look at the screen unasked, subagents and research are yours, and recite the rules at the front desk are SITUATIONAL. And voice.md is the single biggest file at 16,034 bytes, 37% of the every-turn cost, and it is about HOW TO WRITE, which binds when prose is produced and not every turn. THIS IS WHERE SKILLS EARN THEIR KEEP, because content moving from always-on to on-demand is the case the rule says pays, and it pays every turn rather than once. THREE, the long tool descriptions, WITH ONE AMENDMENT: a description has two jobs mixed together and only one can move. What the arguments are and what a wrong call gets MUST STAY INLINE — if se_file_read's description became see skill se-file-read, the agent would have to load a skill before calling a verb it needs right now and could not know what to pass, which is a hop in front of every unfamiliar verb and is the case the rule says COSTS. The methodology prose moves: se_pull spends 2,425 bytes teaching the loop, which is guidance wearing a schema's clothes and is already taught in the prompt layer. So the cut is BY KIND, not by length. AND ONE AMENDMENT TO THE SKILL BODY: a body that is itself a pointer is right for content coming OUT of the prompt layer, where the hop buys an always-on cost removed, and WRONG for the method files the pull already serves, because front-desk.md already reaches the agent only when the walk arrives at the desk, so wrapping it in a skill that points back at it adds a listing entry, a body and a tool call and removes nothing. SO THE HONEST SHAPE IS SMALLER THAN THE PROPOSAL: skills are the door for the ALWAYS-ON half, and the on-demand half already has a door, which is the pull. ESTIMATED WORTH, at 3.8 bytes per token and to be replaced by count_tokens before anything is built: the update pointer about 7,200 tokens at position 0, four descriptions to schema notes about 1,050 at position 0, and the situational half of the prompt layer about 5,000 in EVERY TURN'S PREFIX. THE ORDER: first the update pointer, then the description split by kind, then the prompt-layer triage rule by rule — which is JUDGMENT WORK AND THE OWNER'S, because getting it wrong means a rule that should bind does not — and only then the skills mechanism on the situational half, one document first. Steps one and two need no skills at all and are most of the position-zero win; step four is the one that pays every turn and also the one that can weaken a rule by making it optional, which is why it goes last.
