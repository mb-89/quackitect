# Prior art for the one-door principle

Six systems were read at their own documentation, not at articles about them.
Each one makes some code go through a chosen door and refuses the rest.

THE QUESTION ASKED OF ALL SIX: how do you declare an exception, and does the
system force you to give a reason?

THE ANSWER, ACROSS ALL SIX: one forces a reason, and it is an opt-in
third-party plugin. Every other exception mechanism in the set accepts silence.

## The scoreboard

| System | How you declare an exception | Reason forced? |
| --- | --- | --- |
| dependency-cruiser | edit `pathNot`, set `severity: "ignore"`, or generate a baseline file | No |
| ArchUnit | freeze the rule into a violation store, or an ignore-pattern file | No |
| ESLint boundaries | `// eslint-disable-next-line` with an optional `-- reason` | Only with a plugin |
| Rust lints | `#[allow(...)]`, optionally `reason = "..."` | No |
| Go internal packages | there is no exception | Not applicable |
| Bazel visibility | add the package to a `visibility` list or a `package_group` | No |

## dependency-cruiser

WHAT IT DOES BETTER: it validates a rule against a JSON schema before running
it, so a malformed rule fails at load rather than at use. It also reports
`--metrics`, giving each folder an instability number, so a boundary can be
argued from a measurement rather than an opinion.

THE EXCEPTION MECHANISM IS THREE THINGS, AND NONE CARRIES A REASON.

- Narrow the rule with `pathNot`. The rule changes, so nothing records that an
  exception was made.
- Set `severity: "ignore"`. The reference says this means dependency-cruiser
  "will not check the rule at all".
- Generate a baseline. `depcruise-baseline src` writes every current violation
  to `.dependency-cruiser-known-violations.json`, and thereafter the tool
  "will lower the severity to `ignore`" for each one.

THERE IS A `comment` FIELD, AND IT IS DOCUMENTED AS INERT. The rules reference
says of it: "You can use this field to document why the rule is there. It's not
used in any rule logic." It also sits on the RULE, never on the exception.

THE BASELINE IS THE INTERESTING FAILURE. It is generated by a machine from
whatever happens to be broken today. Nobody writes a line of it, so nobody can
be asked why any line is in it.

Primary: `doc/rules-reference.md` and `doc/cli.md` in `sverweij/dependency-cruiser`.

## ArchUnit

WHAT IT DOES BETTER: `FreezingArchRule` ratchets. A frozen rule accepts today's
violations and refuses tomorrow's, and it shrinks the stored set as violations
get fixed. That is a mechanism for getting a large codebase onto a rule
gradually, and the one-door principle has no equivalent.

THE EXCEPTION MECHANISM CARRIES NO REASON FIELD AT ALL. The stored file is a
Java properties file mapping a rule's English description to a UUID:

    no\ classes\ should\ depend\ on\ classes\ that\ reside\ in\ a\ package\ '..service..'=a81a2b54-5a18-4145-b544-7a580aba0425

The UUID names a second file holding the violation lines. There is nowhere in
that format for a person to say why.

The other hatch, `archunit_ignore_patterns.txt`, is a list of regular
expressions. Same shape, same silence.

Primary: `example-junit5/src/test/resources/frozen/stored.rules` in
`TNG/ArchUnit-Examples`.

## ESLint, and eslint-plugin-boundaries

WHAT IT DOES BETTER, AND IT IS THE BEST IDEA IN THE WHOLE SET: the exception
EXPIRES. `reportUnusedDisableDirectives` defaults to `"warn"`, so a disable
comment that no longer suppresses anything is itself reported. An exemption
that has quietly become unnecessary gets found by the tool rather than by a
person auditing a registry.

THE REASON SYNTAX EXISTS IN CORE AND IS OPTIONAL. A description goes after two
or more consecutive dashes:

    // eslint-disable-next-line no-console -- Here's a description about why this configuration is necessary.

The core documentation ASKS for one under the heading "Document the Reason",
and asking is all it does.

FORCING IT TAKES A THIRD-PARTY PLUGIN.
`@eslint-community/eslint-comments/require-description` "warns directive
comments without description". It is opt-in, it is not part of ESLint, and it
requires ESLint 7 or later.

SO THE ONE SYSTEM THAT CAN FORCE A REASON DOES IT AS AN ADD-ON, and the reason
it captures is free text nothing reads.

Primary: `eslint.org/docs/latest/use/configure/rules` and the
`require-description` rule page at `eslint-community.github.io`.

## Rust lint levels

WHAT IT DOES BETTER: `#[expect(...)]` is an exception with an expiry date built
into the compiler. The rustc book says that if the lint "is not emitted, the
`unfulfilled_lint_expectations` lint triggers on the expect attribute,
notifying you that the expectation is no longer fulfilled".

That is stronger than ESLint's version, because it is in the compiler and on by
default, not a setting.

WHAT IT DOES SECOND BEST: `forbid` cannot be overridden downward by any
attribute. A rule can be made genuinely un-exemptable, which no other system
here offers.

THE REASON IS OPTIONAL AND IT IS DISPLAYED. "All lint attributes support an
additional `reason` parameter, to give context why a certain attribute was
added. This reason will be displayed as part of the lint message." Displaying
it is more than any other system in this set does with a reason.

NOTHING REQUIRES IT. Millions of bare `#[allow(dead_code)]` lines are legal.

THERE IS ALSO A BLANKET HATCH. `--cap-lints allow` turns everything off, and
Cargo passes it when building dependencies.

Primary: `doc.rust-lang.org/rustc/lints/levels.html`.

## Go internal packages

WHAT IT DOES BETTER THAN EVERYTHING ELSE HERE: there is no configuration. The
rule is the directory name. A package under `internal/` "may not be imported by
packages outside the source subtree in which they reside", and the check is the
`go` command's, not a linter you have to remember to run.

Nothing to install, nothing to configure, nothing to keep in sync.

THERE IS NO EXCEPTION MECHANISM. None. You move the code, or you export it
properly, or you do not import it. The Go 1.4 notes describe the mechanism and
name no hatch.

THAT IS A REAL DESIGN POSITION AND IT DESERVES TO BE TAKEN SERIOUSLY. A door
with no exceptions needs no registry, no reason field, no expiry and no audit.
The cost is that the boundary must be cheap enough to obey, which is why it is
a directory rename.

Primary: `go.dev/doc/go1.4`, section "Internal packages".

## Bazel visibility

WHAT IT DOES BETTER: exceptions are named groups, not per-callsite marks. A
`package_group` is a first-class target that several rules can point at, and
the documentation's own guidance is to "use a `package_group` instead of
repeating the list in each target's visibility attribute. This increases
readability and prevents the lists from getting out of sync."

That is a real advantage over a per-site exemption list. One edit changes who
is allowed, everywhere.

IT ALSO HAS A DEPRECATION MODE WE DO NOT. "You can also use visibility when
deprecating a public API to allow current users while denying new ones." An
allowlist frozen at today's consumers.

NO REASON IS CARRIED ANYWHERE. A package name goes in a list. A comment beside
it is a comment.

TWO BLANKET HATCHES EXIST AND BOTH ARE UNRECORDED FLAGS.
`--check_visibility=false` and `--check_bzl_visibility=false`. The docs say
neither "should be done for production usage in submitted code", which is
advice, not enforcement.

Primary: `bazel.build/concepts/visibility`.

## What ours sheds

THE REASON IS THE PRODUCT, NOT A COMMENT. Every system above treats the
justification as optional metadata. Where an exemption registry demands a
reason per entry, the reason is the thing the registry stores, and an entry
without one is not an entry.

WE SHED THE MACHINE-GENERATED BASELINE. dependency-cruiser and ArchUnit both
let a tool write the exception list. A registry a person must type is smaller
and slower to grow, and it cannot contain a line nobody chose.

WE SHED THE BLANKET FLAG. Rust has `--cap-lints allow`. Bazel has
`--check_visibility=false`. dependency-cruiser has `severity: "ignore"`. Our
existing widget precedent has no equivalent switch, and adding one would undo
the rest.

WHAT WE DO NOT HAVE, AND THREE OF THEM DO.

- NO EXPIRY. Rust's `#[expect]` and ESLint's unused-directive report both find
  an exemption that has stopped being needed. Ours does not, and a registry
  without expiry silts up. This is the clearest thing to steal.
- NO RATCHET. ArchUnit's freeze gets a large codebase onto a rule gradually.
  With 79 engine modules importing `node:fs` directly, that is not an academic
  gap.
- NO GROUPING. Bazel's `package_group` names an exception once for many
  callers. A flat per-site registry repeats itself.

## Where the comparison stops

FOUR THINGS THE OWNER NAMED WERE NOT COMPARED, and saying so is the honest
answer rather than filling the space.

- Ports and adapters, and the anti-corruption layer, are SHAPES rather than
  systems people run. Neither has an exception mechanism to compare, because
  neither is enforced by anything.
- Capability-based security was not reached at a primary source in this pass.
- "Architecture fitness functions" names a practice, not a tool with a hatch.

NAMING THE BOOK A SHAPE CAME FROM PROVES ONLY THAT IT WAS BORROWED. That is the
owner's ruling of 2026-08-06, and it is why these four are listed as not
compared rather than written up.
