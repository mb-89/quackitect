## gap_claim

THE GAP: a system that drives a project needs its state, its method and its entry point to live somewhere a person never has to think about — and today ours needs them to re-run a script to stay current.

WHAT EACH ALTERNATIVE SHEDS, scanned live at this state.

A SEPARATE INSTALLER SCRIPT, which is what we have. It sheds CURRENCY. It can install a runtime, which nothing inside the editor can. What it cannot do is tell anybody when to run it again, so the person re-runs it on a hunch and the owner's own complaint is exactly that.

AN EXTENSION WITH NO INSTALLER. It sheds the BOOTSTRAP. An extension needs the runtime in order to run at all, so it can never be the thing that installs one. This is not a preference, it is an ordering constraint.

THE PLATFORM'S OWN BOOTSTRAP. The editor installs extensions silently on first boot from a folder inside its installation directory. It is real, it is documented, and it solves a DIFFERENT problem — it delivers extensions, not the toolchain an extension then needs. It sheds our whole question.

AND IT CARRIES A WARNING WORTH TAKING. A published security writeup uses that same silent mechanism to load extensions without prompting. Silent bootstrap is a known abuse shape, which is the instinct behind the owner's own retraction of auto-seeding an hour earlier.

WHAT OURS SHEDS, since a comparison finding us better at everything was not a comparison. We keep a one-time installer, so we do NOT get zero manual steps ever. One remains, deliberately, because the runtime has to come from somewhere.

AND WHAT THE SCAN DID NOT FIND. No system where an editor extension installs and refreshes its own toolchain on activation. Either it is rare, or the search did not reach it. That is a finding rather than a blank, and the stored sweep from the previous iteration is the better corpus for a second pass.

## why_now

NOTHING MATURED TECHNICALLY. What matured is the model, and it matured today.

THE OWNER RULED WHAT A PROJECT IS. The folder open in the editor IS the project. Before that ruling, "opening the editor gets the folder everything it needs" had no well-defined subject — which folder, and how would anything know? Now the sentence means something checkable.

THE EXTENSION IS ALREADY WHERE ACTS HAPPEN. The previous iteration moved both producing acts out of the launcher and into buttons, on the owner's instruction, and deleted them from the script. So the direction of travel is set and this finishes it rather than starting it.

THE PER-FOLDER MACHINERY ALREADY EXISTS. Placing the cage and starting the lane are already done per folder rather than per machine. What is missing is that they run on the editor opening rather than on a script being remembered.

AND THE COLLAPSE MAKES IT CHEAPER TO DO NOW THAN LATER. Every path that assumes a level above the project is being re-read in this iteration anyway. The launcher's paths are in that set. Splitting the entry-point work into a later record would mean reading the same paths twice.

WHAT WOULD MAKE IT WRONG TO DO NOW. If the launcher's steps turn out not to divide cleanly into one-time and every-time. That inventory is the first act of the design milestone, and it is in scope precisely because the answer is not known yet.
