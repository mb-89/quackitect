From today's tree to the index

This is the order of the work, and the decisions it rests on. The architecture is on its own page, Quackitect Around the Index, and the folder-by-folder findings are on Quackitect Migration Inventory.

How every slice moves

Everything lands on main, because cloud boxes and routines pull only main, and the cage guards every session, so main never breaks. The new system grows next to the old one and takes over one slice at a time.

StageWhat happensDone when
buildThe new module is on main, and nothing reads it yetits tests and the generic contract tests pass
shadowOld and new both compute; every mismatch is written to the session logzero mismatches for an agreed time
switchOne config key per slice (old / shadow / new) moves the readers over. Rolling back is one committhe readers run on the new path
deleteThe old code and its tests are removed, in the same ticket groupno reference to the old path remains

Each slice is one ticket group in the existing process. The retro counts files touched per content ticket before and after, to check that changes really do become local.

Decided

DecisionWhy, in one line
The index is the central model, and grows in placeIts watcher and SQLite already are the input layer; a second one would be the duplication we are removing
One owner per name, with a default; alternative providers are chosen by config at start-upNo value is computed in two places, so no two numbers can disagree
Input, processing, outputEvery run reads one consistent snapshot, costs one round trip, and commits all its outputs at once
The wiring analyzer, quack whyAny name answers who writes it, who reads it, where it comes from, and which file holds the function
Doors on both sides, one file each, with the fake insideOnly doors cross the boundary; adding an adapter adds one file
Go core; JS only for the extension and the hook moduleThose two run inside VS Code and Claude Code
Huma and OpenAPI 3.1 for the HTTP doorA module stays one file, and /docs and openapi.json come with it
modernc (pure-Go SQLite). cgo is outNo C compiler and no Zig, one static binary. Final; not to be reopened
One Go modulePackages separate the code, and a module is only a release unit. Final; not to be reopened
Views are declared, not generated per topicWork and log are real views; .base files grow reads and actions
Watchdogs and dead-man switches on every partA silent part turns stale and loud; it never looks healthy
The cage refuses while the index is downFailures should be loud, so they get fixed early
Only Go writes frontmatter, after one normalising commitFive parsers and three writers become one of each
Every pair of duplicate implementations is reviewed as golden files before its JS copy goesSeveral pairs already disagree
Prose checks move to GoThey are the last runtime reason for Node. golem agrees with wink on 97–99% of the decisions measured
Operations: every longer action returns a handle (ops/<id>)The caller never blocks. The watchdog ends a stuck operation loudly. Writes queue one at a time per tree. Only recent operations are kept; the session log keeps every state change for good
How modules are split into processes is the system's choiceModule authors and users never see it. A module is always one self-contained file, and the system places modules in processes so the cores are used well and a crash stays contained
A group in the cloud is marked in its ticket on mainSending a group to the cloud writes cloud: true into its ticket on main; merging it back, or releasing or closing the branch, clears it. The queue and the count read only files
Git is archive and transport, never live inputNo live value in the index depends on git state. Commits and pushes are actions through the git door. Reading the archive (old logs, closed work, history) is an explicit operation through the git door, which the caller asks for by name; it is not in the index
Linux and Windows behave the sameCloud boxes run Linux; some people work on Windows
