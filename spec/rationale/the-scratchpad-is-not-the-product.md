## decided

A write inside the scratchpad goes through with nothing in hand.
The gate asks the path rather than the text of the path.
A call that names no path stays gated.

## why

Nobody reviews a file in that folder, nothing ships from it, and the retro drains it.
So the gate cost something there and bought nothing.
An agent with nothing in hand could not write the note it was reasoning in.
That was the one place the rule made the work harder without making the queue truer.

filepath.Rel answers how to get from the folder to a file, and a route that starts by climbing out is not inside it.
A prefix match on the string would have taken a file merely named like the folder out of the gate.
So would anything reached through two dots.

A shell command has no one file it writes.
Nothing could say it stays in the folder, so it went on being gated.
That is the honest half rather than a gap, and it is why the carve-out is written where a path is known.

## costs

A shell command that only touches that folder is still refused, so the carve-out helps the write tools and not the run door.
Work written there is outside the record, so a change that drifts into it leaves no trace on any token.
Two doors now decide one question, the one that knows a path and the one that knows a command.

## revisit when

- a shell command can say which file it writes, so the carve-out reaches the run door
- that folder starts carrying work a reader needs later, so it stops being outside the product
