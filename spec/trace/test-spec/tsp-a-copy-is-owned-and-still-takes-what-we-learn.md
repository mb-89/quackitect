## Scope

THE VENDORING CLAIM, WHICH IS THE ONE THAT SEPARATES A COPY FROM A FORK. A fork
gets you your own guidance and loses every improvement from the day you take
it. This demonstration asks whether the difference is real.

IT IS A DEMONSTRATION AND NOT A TEST because its first step is a machine that
has never held the parent. That machine is the whole point, and no hermetic
fixture can be one.

IT VERIFIES NO REQUIREMENT, ON PURPOSE. The producing half is already carried
by a test-method spec. The UPDATE half has no requirement any built mechanism
answers, because the runner does not exist. A spec claiming to verify a row
nothing implements would be fabricated coverage.

WHAT IS DELIBERATELY OUT. The isolation rules, which are
[[tsp-a-vehicle-cannot-reach-what-it-came-from]]'s. Driving a foreign project,
which is [[tsp-a-vehicle-is-made-and-then-drives-something-else]]'s.

## Approach

THE DESIGN METHOD IS SCENARIO-BASED, and the extreme is time: the run pretends
to be an owner three months in, who has changed things and now wants what the
parent learned since.

THE LEVEL IS ACCEPTANCE, and the pass is what the owner can still do.

DEPTH IS ONE PASS. The claim is whether the thing works at all.

## Procedure

FIVE STEPS, and each names what is WATCHED as the pass.

- ONE. Take a produced vehicle to a machine that has never held the parent, and
  bring it up. OBSERVED: what it costs to start. THE INSTALL IS RECORDED RATHER
  THAN WAIVED — the copy excludes `node_modules`, so a network install is
  expected here, and the step passes only if the README already told the owner
  to expect it.
- TWO. Read the front door. OBSERVED: the desk greets under the copy's own
  name, and no surface below the root still says the parent's name.
- THREE. Edit files the parent wrote — a guidance chapter, a method card, an
  engine file. OBSERVED: nothing refuses, the edits stay, and the system keeps
  running on what is left.
- FOUR. Ask the copy what it made its own. OBSERVED: it lists what was written,
  changed and removed since its first commit, and the list matches step three.
- FIVE. Take an update from the parent. OBSERVED — AND THIS STEP IS EXPECTED TO
  FAIL AS THINGS STAND. No update runner exists, so the honest observation is
  that there is nothing to run and the step is recorded as unmet rather than
  skipped.

STEP FIVE IS THE ONE THE STORY EXISTS FOR. Steps one to four describe a good
fork. Only step five makes it a vendored copy, and it is the step nothing
answers today.

## What this demonstration cannot settle

WHETHER THE OVERLAY RESOLVES CORRECTLY, because there is no overlay. Step three
proves the owner may change anything. It says nothing about a card of theirs
being served over one the parent also ships, which is req-overlay-resolution
and has no mechanism at all.

AND WHETHER A THREE-MONTH GAP BEHAVES LIKE A SAME-DAY ONE. The run compresses
the time, and drift that only appears across many parent releases is invisible
to a single sitting.
