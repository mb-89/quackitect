## Rationale

THE JUDGMENT IS i35's AND THE NODE WAS NEVER WRITTEN. That iteration's
derive-functions evidence says it in as many words: "THE CLUSTER IS NEW:
the-arrival. Every existing cluster in the corpus assumes a lane already up, so
none of them could hold these."

SEVEN FUNCTIONS WERE STAMPED AND NOTHING RECEIVED THEM. Each
`fn-arrive-on-a-machine.*` node carries `cluster: the-arrival`, pointing at a
node that did not exist.

SO THIS RECORDS A CALL ALREADY MADE, rather than making a new one. It was
written at i16, whose partition-functions had to name every cluster in the
matrix and found eight clusters with seven names.

## Why sequence

THE SEVEN FORM A CHAIN AND THE MATRIX SHOWS IT. Placing the cage feeds raising
the lane. Raising the lane feeds handing over the means to call. Handing over
feeds accounting for the arrival.

THREE MORE FEED THE SAME ACCOUNT. Judging the runtime, supplying the
dependencies and resolving the cited refs each report into it, and judging the
runtime also feeds supplying the dependencies.

EVERY EDGE RUNS ONE WAY AND NONE RUNS BACK. The cluster is a tree draining into
one function, with no cycle anywhere in it. That is what separates it from
[[cluster-the-walk]], where serving a step, resolving a path and holding the
method feed each other in a loop.

THE ORDER IS A PRECEDENCE RATHER THAN A PREFERENCE, and i35 said so while
sequencing its own build: "each link is a real precedence rather than a
preference. `the-arrival` has to exist before a hook can fire it."

WHAT GOING OUT OF ORDER COSTS. A cage placed after the lane is up has already
failed, and it fails silently. i35's own test file names the state it is
guarding against: an agent holding native tools while believing it is caged.

## Why not shared-data, which is the near miss

SIX OF THE SEVEN TOUCH `flow-arrival-account`, so a reader could call this one
shared flow and stop there.

THE FLOW IS THE DRAIN, NOT THE BOND. What actually holds the seven together is
that each has to have finished before the next may start. Two functions writing
to one report are coupled far more weakly than two where one cannot run until
the other has.

## What it shares with the-bootstrap, and why they stay two clusters

BOTH RUN ONCE AT A BEGINNING AND NEVER AGAIN. That is a real similarity and it
is why the two sit next to each other in the order.

THEY ACT ON DIFFERENT THINGS.

- [[cluster-the-bootstrap]] PRODUCES A TREE that did not exist before.
- This one PREPARES A MACHINE for a tree that already does.

A CANDIDATE MAY ALLOCATE BOTH TO ONE ELEMENT. Nothing here forbids it, and the
partition records the adjacency so that the choice is visible rather than
accidental.

## The eighth function, added at i36

IDENTIFY-THE-HARNESS JOINED AFTER THE SEVEN ABOVE WERE COUNTED. Every count in
the sections above is a count of the original seven, and it is left standing
rather than restated, because each of those claims was measured against them.

IT EXTENDS THE SEQUENCE RATHER THAN BRANCHING IT. It consumes the same
`flow-arrival-request` the rest of the cluster starts from.

ITS OUTPUT LEAVES THE CLUSTER. `flow-harness-profile` crosses into
[[cluster-the-walk]]'s serve-a-step, so the arrival hands off to the governed
walk exactly as raising the lane already does through `flow-live-lane`.
