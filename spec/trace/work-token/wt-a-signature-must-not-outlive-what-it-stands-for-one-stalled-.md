## Why it stands

A signature must not outlive what it stands for. One stalled round holds a signed build form naming seven engine files; three are absent from the tree, and five distinctive symbols it describes match nothing anywhere. Either the work sits on a branch nobody merged, or it was undone and no check objected. Trust in this product is carried by signatures, so one that outlasts its subject weakens every other.

## When it comes back

ready when iteration nine is walked, where the git verb is legal and the history of those paths can be read

## Corrected the same day it was minted

THE ALARM WAS TOO STRONG. Checking the round's four goals against the tree shows
three of them plainly satisfied: the machine-state folder sits inside the
product, a single named file inside it is committed as the marker while the rest
is ignored, and the exclusion is written per file rather than per folder.

SO THE OUTCOMES ARE THERE. What is missing is the set of module names the build
form listed. The work landed under other names, or was folded into other modules
afterwards.

WHAT SURVIVES AS A FINDING, and it is narrower. A build form names the files it
wrote, and those names are not a reliable way to find the work later. That makes
the form's own file list decorative rather than checkable.

WHAT IS NO LONGER CLAIMED. That a signature stands over work nobody can find.
The work is findable by its effects; only the names do not resolve.

THE FOURTH GOAL IS GENUINELY UNMET and moved elsewhere: the engine still has two
readers over one corpus.
