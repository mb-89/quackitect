## detail

The owner asks, September 2026, that lazy evaluation and caching become a standing principle. Build it when somebody asks a question that needs it, keep the answer, and hand the kept one back until something makes it wrong.

Both halves of the busy index defect were failures of exactly that. The test map was rebuilt for a question nobody asked, and the cache write was allowed to fail the work it was caching.

Two cautions belong beside it, or the next reader applies it wrongly.

A CACHE HAS TO KNOW WHEN IT IS WRONG. An honest one says what makes it stale before it is built. The test map keys on a file's hash, which is why it can be trusted. A cache with no such key is a stale answer waiting to happen, and this tree has been bitten: a session read the engine's source and explained a failure with code that was not the program running.

A CACHE WRITE IS NEVER ON THE CRITICAL PATH. Where keeping the answer can fail the question, the cache costs everything and saves nothing. That is the five second wait the owner kept asking about.

Whether this belongs in the standing layer every session reads is the owner's call, which is why it waits for one.

## proposed action

Decide whether lazy evaluation and caching, with its two cautions, becomes an actionable in the software guidance.
