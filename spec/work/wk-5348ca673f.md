## detail

A file the harness loads must not begin with a byte order mark.

MEASURED 2026-09-08. A plugin was written on this box with PowerShell 5.1's `Set-Content -Encoding utf8`, which emits EF BB BF. plugin.json and SKILL.md still parsed, so the plugin's command appeared in autocomplete and everything looked well. The hooks module did not load: no tool was registered, no line was written, and nothing anywhere named a fault. It reads exactly like a feature that is not present, and it cost a session to find.

The installer writes files on Windows. Set-Content -Encoding utf8 and Out-File -Encoding utf8 both emit the mark on Windows PowerShell 5.1, which is the shell a fresh box has; only PowerShell 7 offers utf8NoBOM. So this is not a mistake somebody made once. It is the default on the platform the installer targets.

## proposed action

Write files through [IO.File]::WriteAllText with a UTF8Encoding that emits no mark, and add a standing check that no file the harness reads begins with one.

## done when

- every file the installer writes on Windows begins with a byte other than EF: a check in util/checks that reads the first three bytes of each file the installer names
- a planted mark under .claude, .github or a plugin folder is refused: `sh util/checks/battery.sh` reddens with one planted and is green when it is removed
- the refusal names the call that writes a mark and the call that does not, so it is a menu rather than a diagnosis
