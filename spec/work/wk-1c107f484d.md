## detail

A token can pass every criterion it wrote and deliver nothing a person asked for.

MEASURED, on wk-b0c70384a4, "commands mirror the keywords", process standard, status done. Its six done-when lines each decide the FILE: one file per line, no file that no line answers, the body is that line, a bracketed value becomes $ARGUMENTS, the frontmatter says generated, and a hand-edited file fails a check. All six pass today.

The gain that token wrote at step 1 was "The cloud reaches every control, in a completing menu." The cloud reaches no control. The harness submits the literal /se-ctrl-control-god-off, the keyword matcher sees a slash and moves nothing, and thirty-three generated commands have never done anything. The owner pressed one twice and read the panel as broken, because the panel was the only half telling the truth.

The step 1 checklist asked for the gain and got a true answer. Nothing then required a criterion that could fail if the gain were absent. So the gain was stated, believed, and never decided.

This is not confined to that token. A criterion about the shape of the implementation passes whether or not the thing works, and the guidance does not say so.

## approach

Say it in the guidance first.

A CRITERION MUST BE ABLE TO FAIL WHEN THE GAIN IS ABSENT. That is the test to put to a criterion, and it is readable at step 1 with nothing running. A criterion that decides the shape of the implementation, rather than what a person can observe, cannot fail that way and is refused. An exception is named as one rather than assumed: a generated file's shape is worth pinning where a person reads it, and never instead of the behaviour it is generated for.

Put the question on the step 1 checklist in the words that catch it. Which criterion fails if the gain in the detail is absent? A token that cannot name one is not ready to be worked.

Then, and only if the guidance says it and tokens still ship shape-only criteria, put a reviewer on the design input rather than on the finished work. A reviewer at step 1 costs less than a feature that was signed off and never ran.

## done when

- doc/guidance/work-token states that a criterion must be able to fail when the gain is absent, and names a shape-only criterion as refused, decided by: the owner reading that file
- The step 1 checklist carries a row asking which criterion fails if the gain is absent, decided by: the owner reading the step 1 rows on a freshly minted standard token
- wk-b0c70384a4 is named in that guidance as the measured case, with the count of its shape-only criteria, decided by: the owner reading that passage
- A token whose done-when lines all decide the shape of the implementation is refused at step 1 rather than worked, decided by: the reviewer on the next standard token to reach step 1
