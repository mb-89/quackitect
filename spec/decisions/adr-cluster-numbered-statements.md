## Rationale (not load-bearing)
Owner rulings 2026-07-10. Mechanism 1 shrinks the DATA where concerns genuinely belong together; mechanism 2 shrinks the READING everywhere the shape is regular (the canonical case: one usecase fanning to five requirements, each with exactly its test and design, an ADR pointing at one member - one box, uc and adr as boundary inputs, the adr edge labeled with its sub-target). Render collapse reuses the i16 theme-cluster interaction and touches NO data - so the count target serves reviewability without forcing semantic mergers; where a fan is regular but distinct, the box does the work and the nodes stay. The SAME render fold applies by AGE (owner 2026-07-10): everything older than the last five iterations collapses behind a click in the renders - shipped history stays one interaction away, never in the default view. Test granularity follows re-verification economics (split when invalidation forces unrelated rework; cluster when cheap to rerun whole; one benchmark may validate ten requirements). Deliberate ISO 29148 singularity divergence, mitigated at statement level. WHOLE-GRAPH extension (owner, 2026-07-10): TEST nodes cluster the same way - one node may run several selftests (all must pass; the re-verification economics rule governs grouping), and merged SHIPPED tests carry a tests_red exemption citing this ADR (their birth reds stand in the ledger under the origin ids). DESIGN nodes stay data-unmerged by decision: a region IS a coherent code span; merging would surgery code for zero reading gain - their visual weight is render-side, handled by the folds and the i16 onion. Usecases and needs cluster opportunistically where their whole fan merged.
