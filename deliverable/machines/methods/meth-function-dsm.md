## Situation

M4's partition-functions. Cluster the function structure BEFORE enumerating candidates, because the morphological chart needs the partitioned functions as its rows.

The matrix is a projection over the function notes. Nothing is stored separately.

## THE RELATION IS FIXED HERE, AND THAT IS A DEPARTURE #work

Lindemann's method says pick one relation meaning per matrix, from many, and never mix two. The general rule stands and this system settles it once.

EVERY EDGE COMES FROM A FLOW. A [[flow]] is a node, picked at M3 derive-functions, and an edge exists where one function's output is another's input. So the meaning is `passes_data_to` and there is nothing to choose.

WHY THAT IS SAFE. The rule exists so that a cluster or a feedback loop means one thing. One relation, fixed, satisfies it more strictly than a choice would.

Other meanings would each need their own edge data, which this system does not carry:

- `depends_on`
- `controls`
- `shares_state_with`
- `must_be_synchronous_with`

Adding one means adding its edges first.

## Procedure #work

- Cluster ([[meth-dsm-clustering]]). Strongly-coupled functions group; inter-cluster coupling is minimised.
- Confirm each proposed placement, or move the function and say why.
- Name each cluster, and class its coupling: shared-data, sequence, timing, shared-failure-mode, same-actor, same-policy, same-external-interface, same-lifecycle.

Sequence with [[meth-dsm-partitioning]] where ordering matters. Band with [[meth-dsm-banding]] for parallelism. Neither is this state's duty.

## A CLUSTER IS NOT AN ELEMENT #work

The clusters are groups of FUNCTIONS. The static cut into elements is per candidate and comes later.

The two look alike on a page, and confusing them hands M5's decision to M4.
