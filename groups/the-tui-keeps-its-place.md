5. [low/robustness] src/q/store.go:66 — Commit decides which names moved against a snapshot taken before the lock, so concurrent commits can skip a wave and leave derived values stale
   Finding: Commit takes `before := s.Snapshot()`, then commits under s.mu, then computes movedIn(before, values) after the lock is released. Two commits to the same name from different goroutines (e.g. an IO module committing from a tick and from a request) can interleave as follows. The name x holds A. G2 takes before={x:A}. G1 commits x=B, which counts as moved, and its wave settles readers off B. G2 then commits x=A and compares it with its stale before (A), so it counts as not moved and starts no wave. The store holds x=A, but every derived reader still holds the value computed from B until something else moves x. The early-cutoff rule ('a name whose JSON form stays starts no wave') then turns into a lost update.
   Verifier: The race is real, but it is hard to hit, so I rate it low rather than medium. In src/q/store.go:65-78, Commit takes `before := s.Snapshot()` without holding the lock through the write. commit() then takes s.mu again, and movedIn(before, values) runs after the lock is released. Nothing serialises Commit calls to the same name. The scheduler's moved() handler (scheduler.go:197) only queues the names it is given. A wave takes its view with store.Snapshot() when it starts (scheduler.go:265), so a commit that movedIn wrongly counts as not moved starts no wave and nothing repairs it. Under the A->B->A interleaving the store ends at A while readers keep the value computed from B. Two things make this hard to reach today. First, it needs two concurrent commits to the same name, with the second restoring the exact old JSON value (ABA). Second, G1's wave must take its snapshot inside G2's short gap between Snapshot() and commit(), which holds only owner and type checks (microseconds). Otherwise G1's wave reads A and settles correctly, or, if a wave is already running, the names join a later iteration that also reads A. Most writers already serialise commits per name: the hooks door under d.mu, the Dog's publish under d.mu, the files watcher's single event loop, git/clock ticks, and bus commits per instance. Files content also carries Changed (mtime), which makes an exact ABA unlikely. The one realistic concurrent path I found is the LSP: Handle runs per connection in separate goroutines (lsp.go:485), and writes() releases s.mu around Store.Commit (lsp.go:278-282). Two editor connections writing the same buffers/<path> could interleave. The proposed fix is correct and cheap: compute moved names inside commit() under s.mu, against the previous cell or the owner's default, honouring the down mark as Snapshot.Read does.
   Fix sketch: Compute the moved names inside commit() while holding s.mu, by comparing each value with s.values[name] (falling back to the owner's default) just before overwriting it. Return them alongside the heard hands, and call the move hands with that list. Remove the outer Snapshot.
