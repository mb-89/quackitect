## Situation

Every record is input, process, output.

The input phase pulls: the retro onboards, the kickoff sizes, and the
machine is compiled from the LIVE rigor matrix and pinned into the record.

The output phase ships. It must also EMIT — back to the shared method the
record was built from.

Owner ruling 2026-08-13. Without the emit, every record relearns what the
last one already knew.

## What travels by itself, and what does not

THE PULL SIDE ALREADY WORKS. A record's machine is compiled at the kickoff
bless from the matrix as it stands that minute, then pinned. So an
improvement that has LANDED in the matrix reaches the next record with no
further act. Nothing needs copying.

THE PUSH SIDE IS THE GAP. Nothing carries the learning from the record that
had it to the matrix that needs it.

`promotions` on [[M0_10_onboard-retro]] is the only existing catch, and it
fires at the NEXT record's opening. The knowledge has to survive the seam in
somebody's head or in a note.

## The record cannot write the method, and that is deliberate

SE-C-134 refuses a method write while a record is bound. These are SHARED:

- guidance
- machines
- matrix rows
- templates
- the engine
- the tests

The reason is not caution. A write to one while bound lands in that record's
worktree and fans out from there, pushing the record's copy over trunk. It
happened twice on 2026-08-07, and the first time it deleted two lane verbs.

SO THE EMIT IS A CAPTURE, NEVER A WRITE. The record names what should change
and why. The change itself is made unbound.

## How to emit

At `package`, fill `emit_back`. One line per improvement, naming the target
and the change.

    matrix M3_10 — set question for behaviour models, after the claim gap
    meth-ears — the exempt clause needs an example
    guidance/refusals.md — SE-C-134 wants the escape call spelled out

State `none-found` plainly where there is nothing. A blank reads as done and
is worth less than a named gap.

WHAT COUNTS AS AN IMPROVEMENT TO EMIT:

- A state whose guidance was wrong, missing or misleading while you walked
  it.
- A form that asked for the wrong evidence, or asked twice.
- A method card that did not answer the question it exists for.
- A refusal that blocked you without an executable remedy.
- A check that should exist, proved by a defect that reached the field.

WHAT DOES NOT: anything about this record's own subject. That is the
record's output, not the method's.

## Where it lands

The list is a HANDOFF, not a change. Two things consume it:

- The next record's `promotions` field at onboard-retro, which is where the
  look is owed.
- Whoever is unbound at the desk, who can make the edit immediately.

The second is faster and is preferred when the change is small and settled.
An escape, an edit, and an aim back is one turn.

## Later

When the rendering system lands, this becomes mechanical: the emit produces
a diff against the template rather than a line of prose, and the promotion
is reviewed rather than retyped.

EMITTING BACK TO IMPORTED MODULES IS NOT BUILT AND NOT SPECIFIED. The
overlay work (i16) specifies import as one-way — a vehicle overrides by
placing a file in its overlay, and import never touches it. Drift is
REPORTED by `req-overlay-drift-reported`; nothing sends a change upstream.
That is a separate demand and it does not exist yet.
