## big_idea

THE VISION IS INHERITED AND IT DOES NOT BEND. The resident vision is a machine that drives its own development and knows the conditions it is running under: the harness in front of it, the rules that bind it, the record of what it did. i38 adds one more condition to that list and changes nothing about the axiom, so this packet inherits and states the delta rather than rewriting a goal.

THE DELTA IN ONE BREATH: the machine should know how hard each of its own steps is, and say so, so that the strength of the hand doing the work is a decision the machine makes rather than an accident of who started the session.

WHY THIS IS A DELTA AND NOT A NEW IDEA. i36 taught the machine to know its HOST. i38 teaches it to know its own WORK. Both are the same move — a condition that used to be invisible becomes something the machine reads and acts on — and the second is unremarkable once the first has landed.

## to_be_world

A WALK BEGINS AND THE MACHINE ALREADY KNOWS WHAT IT IS ABOUT TO ASK FOR. Before a milestone is walked it says what the work costs in judgment, names the driver that fits, and hands that outward. Whoever is driving performs the spawn; the machine never does.

AN AGENT ARRIVES AT A STATE THAT TRANSCRIBES A DECISION SOMEBODY ELSE ALREADY MADE, and it is not the same hand that arrives at a state which must find the right frame. Today it is, and the record cannot tell the two apart afterwards.

A READER OPENS A FINISHED WALK AND CAN SAY WHO DID WHAT. Every call carries the model that answered it, so a walk that went badly can be asked whether it was walked by something too weak for it, and a walk that cost too much can be asked which states were driven harder than they needed.

THE OWNER MAINTAINS ONE LIST BY HAND, in the repo, and reads the same answer on every machine. Nothing is discovered at runtime and nothing behaves differently on one box than another.

AND THE MACHINE ARGUES BACK IN ONE DIRECTION ONLY. Asking for a stronger hand than recommended needs no reason. Asking for a weaker one needs a reason, and the reason is on the record.

## goal_system

1. THE MACHINE SIZES ITS OWN WORK. Every state says how hard it is, rated with evidence rather than asserted.

2. THE ANSWER IS THE SAME EVERYWHERE. One fixed list in the repo, no runtime discovery, no per-host roster.

3. THE MACHINE SAYS AND SOMETHING ELSE DOES. The milestone names the driver; the spawn belongs outside the lane, exactly as pushing and opening records do.

4. A WALK CAN BE ATTRIBUTED AFTERWARDS. The model that answered is on the call.

5. A FAN-OUT IS NEVER A FLEET. A submachine takes the maximum over its items and one walker strong enough for the hardest walks all of them.

CONFLICT ONE: determinism against fitness. A fixed table gives the same answer every time and can never learn it was wrong; a live estimate fits each item and cannot be reproduced. RULED FOR DETERMINISM, because this is an auditable engineering process and a walk that cannot be replayed is worth less than a walk that is occasionally over-driven. THE COST IS ACCEPTED WITH ITS NAME ON IT: the drift is registered as a standing risk, not waved away.

CONFLICT TWO: correctness against cost, inside a submachine. Taking the maximum over items is right for correctness and wrong for spend, because one hard item drags N easy ones up with it. RULED FOR CORRECTNESS, and the per-item values are kept precisely so a reader can see what the maximum cost.

CONFLICT THREE: the machine deciding against the agent judging. RULED AS A RECOMMENDATION rather than an order, with the asymmetry doing the work — stronger needs no argument, weaker needs a recorded reason. A rule that let a cheap model rule itself sufficient would be the failure the whole idea exists to stop.

PRIORITY ORDER when they cannot all be had: 3 before 1, because a mechanism that reaches outside the lane is a worse thing to get wrong than a rating that is too coarse. Then 1, then 5, then 4, then 2.

## moore_pitch

FOR the owner and the agents walking Quackitect's own development, WHO today run every state of a fifty-three state process on whatever single model happened to start the session, THE complexity ladder and its fixed driver list IS a sizing layer inside the machine THAT rates each state's difficulty, names the model that fits, and records which model actually answered.

UNLIKE a runtime router, which predicts a difficulty score per request and is corrected by outcomes, OUR PRODUCT declares the rung in the repository, so the same milestone names the same driver every time and a finished walk can be replayed and audited.

WHAT WE GIVE UP, SAID IN THE PITCH BECAUSE IT BELONGS THERE: per-item resolution and any signal that a rung is wrong. The shipped routers have both. We are buying reproducibility and disclosure with them, and that is the trade this process is for.
