# Evidence form / spike-does-a-backgrounded-lane-survive

## current_situation

The spike ran on this machine and the assumption falls, before any cloud host is involved.

A CHILD SLEEPING 45 SECONDS held its launching command for 45,600 ms. Every detachment flag node offers was set.

THE CHILD SURVIVED. Nothing reaped it. What failed is the other half: the command that started it never returned.

## follow_up

- THE ENTRYPOINT'S `start` STEP CANNOT WORK AS DRAWN. It is the third of seven, and the four after it never run if start does not return.
- THE FIX IS AN EXPLICIT PLATFORM DETACH, not a background flag. What that is per platform is the next thing to settle, and it is build work rather than another spike.
- ONE HALF STAYS OWED: whether a Linux host reaps the lane with its session. That needs the machine this one cannot make.
- THE ASSUMPTION TANGLED TWO QUESTIONS and should be split. Releasing the caller is a spawn question and is now answered. Surviving the session is a host question.
- nothing is parked from this state

## anything_else

### Why the timebox was not needed

THIRTY MINUTES WERE BUDGETED AND TWO RUNS SETTLED IT. The measurement is a wall clock against a known sleep, so there is nothing to interpret.

### What was faked, said plainly

THE CHILD WAS NOT THE ENGINE. It was a bare node process sleeping, so this measures the SPAWN mechanism rather than the engine's own startup.

THAT IS THE RIGHT SCOPE FOR THE QUESTION. If the mechanism cannot release its caller with a trivial child, it will not do better with a heavy one.

### The fallback was agreed before the run

WRITTEN INTO THE NODE BEFORE THE RESULT: if a launched process cannot release its caller, the start step uses an explicit platform detach, proven by this same measurement before anything downstream is built.

THAT IS NOW THE PATH rather than a rationalisation, because it was chosen while the answer was still open.
