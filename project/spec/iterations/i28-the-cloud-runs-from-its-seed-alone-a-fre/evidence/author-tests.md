## anything_else

### Why six requirements added no new spec

A SPEC IS ONE VERIFICATION CONCERN, and each of the six already had one.

- [[tsp-engine-lifecycle]] takes the console requirement. It already covers reload, port fallback and loopback, and a lane that survives its stdin closing is the same concern.
- [[tsp-claim-lane]] takes the holder requirement and the offline one. It already covers claiming, racing and reconciling.
- [[tsp-record-lifecycle]] takes the list-from-git, worktree-lifetime and entry-repair requirements. It already covers opening a record and binding its tree.

MINTING THREE NEW SPECS WOULD HAVE SPLIT THREE FAMILIES to keep this iteration's work together, which is filing by author rather than by concern.

### Why the seventh needed its own

[[req-one-command-starts-an-unattended-machine]] VERIFIES BY DEMONSTRATION, and the method must match. No standing spec demonstrates a bare machine reaching a walking agent.

THE CLAIM IS ABOUT A MACHINE NOBODY PREPARED. A test on a prepared machine cannot make it, because the preparation is the thing under test.

### What the new spec already knows

ITS PROCEDURE NAMES THE STEP THAT WILL FAIL FIRST. The spikes measured that `start` does not release its caller on Windows, and found that Linux takes a branch which has never executed.

SO THE DEMONSTRATION IS ALSO THE FIRST RUN OF THAT BRANCH. Writing that into the spec before the run means a failure there is an expected finding rather than a surprise, and the reader knows where to look first.
