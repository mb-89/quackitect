## neutrality

ONE FUNCTION WAS DERIVED HERE AND IT PASSES, and I checked it against the trap I had already fallen into twice today.

fn-run-a-governed-walk.resolve-a-path - decide which tree a call's path names, and say so.

COULD TWO HONESTLY DIFFERENT DESIGNS BOTH DO THIS? Yes, and at least three can.

- Bind the lane's root to the record, so the answer is always the bound tree.
- Judge each path against the record, so a wrong one refuses.
- Resolve as today and NAME the result, so an ambiguous path stops being silent.

THE FUNCTION CHOOSES NONE OF THEM. It says the decision must be made in one place and stated, which is what leaves M4 a real space to enumerate.

WHY THAT CHECK MATTERED HERE MORE THAN USUAL. Twice today I wrote the mechanism into something that should have been solution-neutral - once into the iteration's goal, once into its scope - and the owner caught both. The first draft of this function was going to be called bind-the-root. That name IS a design, and it would have collapsed M4's space to one point before anybody compared anything.

THE SECOND HALF OF THE STATEMENT IS NOT DECORATION. And say so - naming the resolved tree - is what makes a wrong answer findable. A resolution nobody can see is one nobody can check.

NO RESIDENT FUNCTION NEEDED CHANGING for neutrality. The five requirements that attached to existing functions attached without moving what those functions say.
