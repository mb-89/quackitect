## big_idea

INHERITED, not rewritten. The resident vision stands at project/spec/trace/value-prop/vp-the-engine.md and this iteration serves it rather than bending it.

ITS BIG IDEA, unchanged: draw YOUR process as a state machine and the engine gives it teeth, for any number of agents and machines at once. The engine attaches CONSEQUENCES to the drawing — a state refuses tools, a gate refuses passage, a claim refuses collision.

THE DELTA THIS ITERATION ADDS, in one breath: the drawing's teeth reach the FILE SYSTEM. Until now a state could refuse a tool and a gate could refuse passage, while every path the agent wrote still resolved against one fixed root. So the cage governed WHAT you may do and never WHERE it lands.

WHY THAT IS the same idea rather than a new one. A claim refusing collision is the vision's own success criterion, and it is not achieved by the ledger alone. Two machines can hold two different claims and still collide, because both their walks resolve into the same trunk. The ledger stops two agents taking one record; only the binding stops two records reaching one tree.

## to_be_world

POINTER PLUS DELTA. The to-be world of vp-the-engine is alive already and this changes one thing inside it.

WHAT IT LOOKS LIKE FROM THE OUTSIDE, and it is an absence rather than a feature. Nobody steps out. An agent working a record never types a path that lands somewhere else, never syncs mid-walk to fetch a file it could not see, and never discovers at a merge that the same thing was built twice. The question where did that land stops being asked, because there is only one answer available.

WHAT THE PERSON SEES. A finished record leaves no folder on disk. Opening the board on a fresh clone shows the same records in the same states as the machine that seeded them, because status comes from the record rather than from what happens to exist locally. Today a fresh clone showed all nineteen pushed records as archived, none ever started — that is the world this ends.

WHAT IT COSTS TO LIVE THERE, said plainly. This product cannot join it. Quackitect edits its own engine, and an engine cannot serve from a tree it is not running from, so this one record type walks on trunk forever. The to-be world has exactly one house that stays outside it, and that house is ours.

## goal_system

INHERITED from vp-the-engine's success criteria, with one conflict this iteration makes visible rather than creates.

THE GOALS IT SERVES, both already stated there.

- Two machines ship two iterations concurrently without collisions, target zero double-claims. The binding is the half the ledger cannot do.
- A new machine joins with one install and one claim. A machine that cannot address trunk cannot corrupt it, so joining stops being risky.

THE CONFLICT, NAMED OPENLY. Isolation fights self-hosting, and they cannot both be had.

The stronger the binding, the safer every product is and the less this product can develop itself inside its own record. Perfect isolation would mean Quackitect's own iterations cannot touch the engine at all, which is every iteration it has.

HOW IT IS RESOLVED, and it is a carve-out rather than a synthesis: this product declares itself self-hosting and gets no worktree. The resolution rests on one claim — a product never works on Quackitect, so the exception has exactly one member and no other product can drift into it.

THAT CLAIM IS AN ASSUMPTION AND IT IS REGISTERED, at raid-asm-engine-serves-from-the-bound-tree, with the probe that would settle it. A goal system that hides its unresolved conflict is worth less than one that names it.

A SECOND, SMALLER TENSION. Binding the root removes the shell's reach around the guard, which is a security win nobody asked for and a convenience loss somebody will. Every measured step-out was waste; that does not prove the next one would be.
