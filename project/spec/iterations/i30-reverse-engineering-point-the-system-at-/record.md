# i30-reverse-engineering-point-the-system-at-

## Goal

Reverse engineering: point the system at work that was never driven properly and recover the needs, the requirements, the use cases and the trace it should have had.

## Rough vision

THE OWNER'S ORDER, set 2026-07-29 and now reached. Systematic runs first, then the trace graph, then this, then reverse engineer a proper trace out of our own work. Steps one and two are done — the iterations lane runs and the trace graph stands — so the condition this waited on has come true.

THE FUNCTION. Point it at existing material and it works backwards to a proper product: the needs, the requirements, the use cases, filled in so the result meets the rigor this system asks for everywhere else. Ideally it writes the documentation too.

TWO CASES, AND THE SECOND PAYS FIRST.

- THE OUTSIDE CASE. Somebody has twenty years of engineering lying around. They dump it in and ask for a proper product to be recovered from it. This is what makes it a PRODUCT function rather than an internal tidy-up: Quackitect drives products, and this is how a product that was never driven properly gets adopted at all.
- THE INSIDE CASE. We apply it to ourselves, wherever we did lazy work. Everything run straight from idle with no record and no trace gets recovered into what it should have been. That is probably also how past EXPEDITIONS fold into the trace graph, rather than a separate migration nobody wants to write.

IT PAIRS WITH IMPROVEMENT, and the owner named the pair himself. Reverse engineering RECOVERS what should have been there; the second pass says what to do better. The overhaul function already covers three jobs — throw out what should not be there, replace bad METHODS with good ones, replace bad STYLE with good style — and the methods half is the one that needs a recovered trace to judge against.

THE OPEN QUESTION THIS ITERATION SHOULD SETTLE, carried in with note-e36bbe64133a and unresolved by the owner deliberately. He proposed a DAY EXPEDITION: open one each morning as the bucket for work with no goal of its own, close it at night, then make an ITERATION that cleans it up. He said plainly he was unsure whether that is the best mode of operation, so it is a proposal and not a ruling.

WHY IT BELONGS HERE. That cleanup iteration may BE a reverse-engineering run rather than a hand-written pass, and the owner said so when he raised it. If the function exists, the day bucket becomes cheap. If it does not, the cleanup is manual and the proposal costs more than it saves. So the two decide together.

WHAT IS ALREADY SETTLED and should not be reopened: an expedition is roughly a day of agent work, an open one is the first place small work goes, and a single small fix never earns its own record. That landed in front-desk.md and software.md after the desk seeded a record for a one-file bug fix.

SIZE WARNING. The outside case is plausibly product-scale rather than iteration-scale. The inside case is not, and it is the one with evidence. Scope this to our own corpus first and let the outside case follow.

FROM THE POOL, 2026-08-13. Two more, and the first binds how the whole mine is read.

THE V1 FRAME (owner ruling, note-569b8229d05c). v2 and v3 exist BECAUSE V1 DID NOT WORK, so v1 is an unreliable source like any other, and a decision being written down there does not make it good. MINE V1 FOR FEATURES, NOT FOR AUTHORITY: v1 has many features v3 lacks because v3 spent its time on the foundation, and that is what to extract. Four v1 decisions are ruled NOT authoritative - the pivot argument that autonomy is a future knob, trunk-owned notes, the guidance description catalog, and killer checks. The owner's diagnosis of the pivot is the opposite of v1's own: the mistake was teaching a SPECIFIC PROCESS without teaching how to walk a process at all, so the walking failed as a consequence rather than as proof it cannot work. ONE IDEA SURVIVES: types, especially for build steps, and v3 is not empty here since a state carries tags and guidance joins to them. THE DISCIPLINE: every v1 item is a candidate, earning its place on what it does for v3, and where a v1 decision contradicts a v3 one that is information about what v1 tried rather than a reason to reopen anything.

PRODUCT SELECTION AT LAUNCH, the dogfooding item that has waited since 2026-07-27 (note-792c32b5425e): the product folder is swappable. It is the same capability this iteration needs to point the system at anything that is not itself.
