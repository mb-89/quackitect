## anything_else

WHY THE AFFORDANCE IS AN EXTENSION AND NOT A USE CASE, since a reader who saw scope grow would expect a third node.

A USE CASE HAS ONE ACTOR AND ONE GOAL. The goal of pressing create-vehicle is HAVING A VEHICLE, which is uc-vendor-and-overlay's goal. The goal of naming a project is DRIVING IT, which is the other one's. Neither is a new goal, and a use case per route would model the routes rather than the goals.

THE METHOD SAYS SO DIRECTLY: where a new story fits an existing use case's extension, extend rather than add.

AND THE NO-UI-MECHANICS RULE SHAPED THE WORDING. The extensions say the act is OFFERED WHERE THE BUILDER ALREADY IS and that it ENDS WITH THE BUILDER INSIDE THE RESULT. They do not say button, panel or window. A use case survives a rewrite of every screen it touches, and these will.

### What the extension deliberately keeps and what it drops

KEPT: that the act asks for the same things the command asks for. That is a real constraint — two ways in that ask different questions are two features, and the owner's own framing was the SAME arguments.

KEPT: that it ends with the builder working in the result. Producing a tree and telling somebody where it went is a different, worse act, and the difference is the whole point of the story under it.

DROPPED: which surface, and what it looks like. Those are the screens M4 and M5 design.

### One thing this pass moved from an extension to a step

THE SYSTEM COMING UP IN A FOREIGN TREE was going to be an extension, and it is a STEP. Extensions are branches that can happen; this happens on every single pass of driving somebody else's product. Putting it in the branch list would have made the hardest crossing in the iteration read as an edge case.

AND ITS OWN EXTENSION 2y CARRIES THE REASON IT IS HARD: the driven tree carries none of the system's method, so the method comes from a recorded pointer rather than from the tree being worked on.
