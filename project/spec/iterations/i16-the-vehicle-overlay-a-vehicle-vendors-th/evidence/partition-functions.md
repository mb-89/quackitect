### Why the-bootstrap's coupling changed, and why it then held

IT WAS `same-lifecycle` AND IS NOW `shared-failure-mode`. That is not a judgment overturned. A cluster of one has no coupling to class, so the old value was standing in for an answer rather than giving one.

WHAT THE MEMBERS ACTUALLY SHARE is a hazard. Each acts on a whole tree from outside it, and each fails the same way when it stops halfway: something that looks finished and is not.

- `stand-up-a-product` carries req-setup-stops-before-partial, and its own rationale says a half-installed machine is worse than an uninstalled one because it looks finished.
- `bring-forth-a-vehicle` and `bring-forth-a-project` carry req-an-act-writes-only-the-tree-it-produced, whose refuse-rather-than-half-do facet is that same rule applied to a tree.
- `take-an-update` fails it hardest, because its half-done state is invisible. flow-applied-change records the shape: a migration that runs, succeeds and produces something wrong.
- `report-what-the-vehicle-changed` fails it quietly. A report missing a path reads like a report where that path did not change.

THE CLASS WAS RE-ASKED WHEN THE CLUSTER WENT FROM THREE TO FIVE, and it survived. The alternative on the table was `shared-data`, because the cluster gained its first internal flow at the same moment. One edge among five members is thin, and cluster-the-walk shows what shared-data looks like when data is really the force: three flows and the matrix's only cycle.

SAME-LIFECYCLE STOPPED BEING EVEN SECOND-BEST. It was true while all three members ran once at the birth of a tree. Two of the five now run over and over, so it is false rather than weaker.

### The cluster's name had to widen with it

IT SAID "producing a tree that did not exist, from outside it, in one act or none". Two of the five members do not produce a tree at all. Taking an update rewrites one that already exists, and reporting what a vehicle changed writes nothing.

IT NOW SAYS "acting on a whole tree from outside it, where half-done looks finished". The unit and the hazard are what survived; producing was never the binding part, it was just what the first three happened to do.

### The finding worth carrying into M4

`bring-forth-a-vehicle` IS THE ONLY EDGELESS FUNCTION IN THE MATRIX. It has neither an incoming nor an outgoing edge, and that was re-checked rather than carried when two functions joined its cluster.

THAT IS THE ITERATION'S FATAL RULE SHOWING UP IN THE STRUCTURE. All three of its flows cross the system boundary: flow-repository and flow-intent arrive from outside, and flow-vehicle leaves to nbr-descendant. If any function consumed flow-vehicle, this system would hold a data path into its own descendant, which req-nothing-a-copy-does-reaches-its-source grades fatal.

THE TWO NEW MEMBERS RUN THE OTHER WAY AND SO DO NOT TOUCH IT. Both run INSIDE a vehicle, on that vehicle's own tree. `take-an-update` writes the tree it stands in and `report-what-the-vehicle-changed` reads it. Neither reaches a descendant.

THE SIBLING IS THE CONTROL. `bring-forth-a-project` outputs flow-driven-tree and `resolve-a-path` consumes it, because a driven tree stays under this system's hand. The two functions are nearly identical in shape and differ exactly where the rule says they must.

I CHECKED IT AS A SUSPECTED HOLE AND IT IS NOT ONE. An edgeless function usually means a flow was never wired. Here it means the wiring would have been the defect.
