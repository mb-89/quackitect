# i20-judgment-emit-book-the-whole-product-as-

## Goal

JUDGMENT — emit.book: the whole product as one book, with the comment layer that lets a reader mark it up and send it back, and the AI-involvement marks European law will require.

## Rough vision

NEEDS THE OWNER. This is a big load of work and it covers the WHOLE PRODUCT, not one iteration. Study v1's book before designing, and compare against StrictDoc — a comparison with both sides, per the evidence rule.

V1'S BOOK DESIGN, ready to weigh whole. TRUTH LIVES ONLY IN THE SPEC SOURCES and all judgment happens there; everything downstream is deterministic. The emitter renders truth to ONE self-contained HTML with transclusion at emit time. It MAY materialise assembled chapter markdown as an EPHEMERAL review surface, regenerated every emit, never committed, never a source of truth.

Its own sentence for why: JUDGMENT UPSTREAM, DETERMINISTIC DOWNSTREAM. The reader corrects the SOURCES, never the projection, and the next emit proves the correction took.

The book stays ONE FILE with client-side paging, because multi-file output breaks the portable single-file identity. Derivable sections render as CANNED QUERIES. AGENT-DRAFTED SECTION PROSE IS REJECTED because it drifts and duplicates.

THE THREE LAWS bind every view: derived over authored, no green ocean, one screen by default.

NO GREEN OCEAN IN ACTION, and it is the best thing in v1. Its V and V chapter OPENS WITH THE EXCEPTIONS, not the matrix. The verified mass is ONE DERIVED COUNT and every unverified requirement is named FIRST. With zero exceptions the whole block is ONE GREEN SENTENCE. Its reason: A HOLE NEVER HIDES ON PAGE NINE OF A GREEN TABLE. And the trace renders ONE PAGE PER NEED rather than one giant graph, reusing the grouping the report already bakes.

THE COMMENT LAYER LANDS HERE, and the owner wants it back. Comments in ONE embedded W3C Web Annotation island inside the single file. Anchors are a unit id plus quote and position selectors, valid within the copy they were made in, and THE QUOTE DOUBLES AS HUMAN-READABLE CONTEXT at triage. Highlights render through the CSS Custom Highlight API so THE CONTENT DOM IS NEVER MUTATED, degrading to no highlights where the API is absent while the sidebar still works. Save is in-place where granted and a download elsewhere, rewriting ONLY the island, so AN UNCOMMENTED SAVE IS A BYTE-IDENTICAL NO-OP. The read-back prints a LIST of note candidates with AUTHOR NAMES ALREADY REPLACED BY THE READER ROLE, and the agent mints the keepers. A BULK IMPORTER STAYS REJECTED: nothing enters the ledger without judgment.

THE AI-INVOLVEMENT MARKS LAND HERE TOO, and the reason is external: European legislation requires AI-generated text to be marked, so documentation will carry them. v1's design is complete. The marks measure INVOLVEMENT ONLY — three is fully generated, one is slightly touched — never trust or review. The author owns all published content and no unreviewed state exists to render. THE AI ADJUSTS THE MARK AT WRITE TIME on the surface-versus-core line: surface touches leave it, core touches raise it, and DOUBT LEANS HIGHER. The human only reduces it by judgment. It renders as small vertical icons in the text margin. Two alternatives were rejected with reasons: a faceted review axis, and a bare textual AI label as the proven-worst format.

ONE THING TO RULE BEFORE BUILDING: v1's fundamentals state the marks more strictly than its ADR — a person's rework removes robots, and ANY AI TOUCH RESETS THEM TO THREE. The ADR says core touches raise it to the real share. Pick one.

ALSO HERE: the SELF-REFERENCE QUARANTINE. One chapter is the only place the document may speak about itself, and v1 CHECKED THAT MECHANICALLY. Our voice guidance already states the rule and nothing checks it. And presets, which v1 shipped as four-line manifests listing chapters in reading order, were ruled NOT wanted — do not build them.

FULL CONTEXT: project/spec/version-planning.md, section J2.

FROM THE POOL, 2026-08-13. Three more, and the first settles what the export gap actually is.

THE EXPORT IS DEFERRED, NOT MISSING (owner ruling, note-93ddc77bf9ae), and the distinction is the point. v1 built the book over three iterations readable at ref main, plus the reader's own instructions. The design exists and is readable, the absence is a choice with a stated reason, and the re-entry condition was that the feature iterations begin - which they now have. THE COMPARISON STILL STANDS: StrictDoc exports and we do not, today. What changed is that the gap is scheduled rather than unexamined.

WHAT THE STRICTDOC COMPARISON OWES (note-262cd7dfd40d). NOBODY HAS RUN IT - everything known is a claim from one comparison article, and that is exactly the state the note exists to fix. Both sides are owed: actually run it and generate its export, read v1's book OUTPUT rather than its build plan, and say what StrictDoc does better FIRST, because a comparison that finds ours better at everything was not a comparison. Name what each sheds - ours is a book for a reader, theirs a document set for an auditor, and the better one depends on who is asking. THE SCOPE GUARD MATTERS AS MUCH AS THE TASK: we are not a documentation generation system, and a finding here is an input, never a reason to rebuild around somebody else's model.

NO OUTSIDE READER HAS EVER VALIDATED IT (note-6ba748959a02). v1 recorded that gap as OPEN about its own book: only the owner and the driving agent had read it, and the mitigation was to hand it to one outside stakeholder and treat their read as the probe. The same is true of v3's spec today, which carries newcomer requirements nobody outside the loop has tested.
