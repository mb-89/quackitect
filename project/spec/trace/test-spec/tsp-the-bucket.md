## Scope

The bucket, both ends. The permission that lets a state sign with a defect
recorded, the guard that makes the disposition agreed rather than asserted, and
the close that will not pass while one stands.

WHAT IS DELIBERATELY OUT: which of the register's eight status values count as
open. That is owed by raid-asm-an-entry-status-says-whether-it-is-open and
cannot be settled until the close-side reader exists.

## Approach

Component level against a real booted server. Every case drives `se_pull` or
`se_exp_close` and fails on an assertion rather than on an import, because a
test that fails at load takes the whole battery with it and produces a red
nobody can read.

FAULT-BASED AROUND THE GUARD, which is where the harm is. Two of the three
cases attack the disposition rather than the permission: a reference that
resolves to nothing, and a close attempted with one standing.

## Steps

Every case in the referenced file is one step, and the case name states its
claim.

- An owed item naming no open register entry does not stamp. This is the
  guard, written first because the permission without it is strictly weaker
  than the unchecked box it replaces: `- [ ]` reads as unfinished, `- [owed]`
  reads as dispositioned.
- A state carrying a well-formed owed item signs and the walk moves on. This is
  the permission, and the whole point of the iteration's one new story.
- A close refuses while an owed item still stands, and names it.

## The third case tests something that does not exist yet

req-close-refuses-loose-ends IS A MUST GRADED FATAL WITH NO IMPLEMENTATION.
The probe is recorded at raid-asm-an-entry-status-says-whether-it-is-open:
searching the engine for a loose-end computation returns nothing, while the
requirement's own Detail says the engine shall refuse the close while any
finding stands without a recorded ruling.

THE OWNER RULED IT INTO SCOPE the same day, in as many words: "you're building
the close site in this iteration. There's no way around it."

SO THIS SPEC VERIFIES A ROW OLDER THAN THE ITERATION, deliberately. Test-first
means the spec defines how it will be verified before the build; here the
requirement was written in i1 and the verification is being written now.
