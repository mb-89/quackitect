WHY THIS SECTION EXISTS. An independent must-check held all ten musts against

### The fail-open switch is set to REFUSE

`opt-a-declared-class-with-a-named-fallback-pool` ships "an explicit switch
saying whether an unmatched class falls through to it or refuses". This line
picks it and never said which way the switch is set.

IT REFUSES. `req-an-unmatched-rung-names-itself-and-publishes-no-driver` demands
that the milestone publish no driver, name the unmatched rung, and never fall
back to whatever model is currently running. Fail-open contradicts it outright.

SO THIS LINE TAKES HALF THE OPTION, AND SAYING OTHERWISE WAS A REDEFINITION.
An earlier version of this section argued that a named default entry is "a MATCH,
not a fallback". THAT IS NOT WHAT THE OPTION SAYS. Its statement calls the
default the fall-through branch — "an explicit switch saying whether an unmatched
class falls through to it or refuses" — and its Detail argues FOR fail-open: "a
NAMED, LOUD fallback is distinguishable, and it keeps work moving where refusing
would stop it." A cold reader found the section resolving a design question by
asserting the option means something other than what it says.

WHAT IS ACTUALLY TAKEN is the option's first half: the no-match case is a
configured decision written down rather than a surprise. WHAT IS DECLINED is its
fall-through branch, because the must forbids it.

AND DECLINING IT COSTS SOMETHING THIS LINE WAS NOT CHARGED FOR. The option's own
argument includes "a default pool is what a host without the named worker falls
to" — a host-portability claim. A line that refuses instead of falling through
does not have that. WHETHER THAT MOVES THIS LINE'S HOST-SWAP SCORE IS NOT
DECIDED HERE, and it is not decided here on purpose: the hand that made the
change does not re-score the axis it changed.

SO THE TOTALITY CHECK AND THE SWITCH DO DIFFERENT JOBS.
`opt-the-mapping-is-checked-for-totality-when-the-machine-compiles` catches the
hole at compile. The switch says what happens to a hole totality cannot see —

## Why this one

EVERY REQUIREMENT THIS RECORD WROTE ASSUMES THIS SHAPE. It is the design the
register was built against, so it starts with the fewest standing claims to
reopen, and it is the baseline the other three have to beat rather than a
proposal competing from scratch.

IT TAKES THE TWO CHEAPEST REPAIRS THE FINDERS FOUND AND NOTHING ELSE. The
complexity rides the matrix cell, on a path probe 4 found already compiled;
totality is checked when the column compiles, so the unmatched case is a
refusal to pin rather than a surprise at state forty. Both are small edits to
code that runs today.

IT LEAVES TWO AXES AT THE INCUMBENT, DELIBERATELY. The difficulty is declared
rather than derived, and the unit is the milestone. Those are the two the
other candidates attack, and holding them here is what makes the comparison
mean anything.

## How it works

obtain-a-step-s-difficulty reads a value off the compiled state, put there by
compileColumn from a third cell key beside `applies` and `<column>_note`.
reduce-a-milestone-to-one-difficulty takes the maximum, as the seed says.
resolve-a-difficulty-to-a-driver reads two records — a mapping of difficulties
to rungs that moves when we change policy, and a roster of models filling each
rung that moves when a vendor ships — with a named pool per rung.
publish-the-driver-outward emits only when the answer differs from the standing
one.
